# Sources — инструкции для исходного кода

## Область действия

Этот файл дополняет корневой `AGENTS.md` для исследования, создания и изменения исходного кода внутри `Sources/`. До первого практического изменения кода прочитай `Tasks/AGENTS.md`, найди или создай соответствующую карточку и прочитай её вместе со связанными артефактами. Если работа основана на архитектурной карточке, также прочитай `Documents/AGENTS.md` и саму карточку полностью.

## Структура и границы

- `Sources/<Project ID>/` — отдельный Git-репозиторий рабочего приложения.
- `Sources/old/` — старые проекты для исследования. Не изменяй их без явного запроса Parad.
- `Sources/Architectures/` — общий репозиторий эталонных реализаций и архитектурных шаблонов; это не каталог рабочих приложений.
- Не добавляй исходники вложенных проектов в Git-репозиторий vault.
- Не инициализируй новый Git-репозиторий, не создавай GitHub-репозиторий и не меняй remote без явного запроса Parad.
- Не сохраняй токены, пароли, connection strings с секретами и другие credentials.
- Если имя папки и репозитория различается, сохрани оба точных значения и связь между ними в карточке задачи.

## Работа по архитектурным карточкам

- `Documents/Architectures/` является источником истины для согласованных архитектурных решений.
- Перед созданием проекта найди карточку по точному названию, прочитай её полностью и задай только отсутствующие обязательные вопросы.
- Не смешивай правила разных архитектур без явного решения Parad.
- Для кубика с режимами сначала определи режим: интеграция изменяет указанный существующий solution; автономный режим создаёт отдельный solution и не меняет существующие проекты.
- Сначала согласуй описание, затем создавай и проверяй эталон. Автоматизированный шаблон создавай только после успешной проверки и подтверждения повторного использования.
- Каждый файл с объявлением `public interface` помещай в папку `Interface/` соответствующего проекта.
- Реализации `IView` и производных интерфейсов помещай в папку `View/`.
- Реализации `IPresenter` и производных интерфейсов помещай в папку `Presenter/`.
- Более конкретные правила runtime, DI, структуры solution, библиотек и именования бери из выбранной архитектурной карточки и локального `AGENTS.md` проекта, если он существует.

## Читаемость кода

Читаемость человеком является главным приоритетом для всего пользовательского кода, который Codex создаёт или изменяет. Порядок действий должен быть виден из кода без мысленного разбора сложной конструкции.

- Одна конструкция должна выражать один понятный шаг. Не объединяй в одном сложном выражении несколько самостоятельных операций, например получение данных, преобразование, проверку, ветвление, изменение состояния и внешний вызов.
- Если выражение скрывает этапы выполнения, раздели его на последовательные инструкции. Дай промежуточным значениям, условиям и самостоятельным действиям точные имена; при необходимости выдели действие в небольшой метод.
- Предпочитай простой поток управления, умеренную вложенность и конструкции, которые удобно пошагово отлаживать. Не используй цепочки вызовов, вложенные тернарные операторы, плотные LINQ-выражения или другие сокращения, если для понимания требуется одновременно удерживать несколько операций.
- Краткая конструкция допустима, когда она выражает одну очевидную операцию и действительно остаётся понятнее развёрнутого варианта. Не дроби код механически и не запрещай возможности C# только из-за их современности.
- Не жертвуй корректностью и явно заданными требованиями производительности, но не усложняй код ради предполагаемой оптимизации без подтверждённой необходимости.

Основание этого правила — не только то, что код читается чаще, чем пишется. Простые и явно названные конструкции поддерживают порядок, быстрее объясняют намерение, легче проверяются, пошагово отлаживаются и безопаснее рефакторятся.

Правило применяется к написанному вручную пользовательскому коду. Не переписывай ради него автоматически сгенерированные файлы, сторонние библиотеки и неизменяемый код старых проектов.

В качестве общего ориентира используй традиции написания кода Microsoft и ясный, прямолинейный стиль её примеров для .NET. Примеры Microsoft для .NET Framework являются особенно понятным эталоном требуемого уровня читаемости, но не ограничивают выбор версии .NET или допустимых возможностей C#.

## Проверка и передача результата

- Проверяй изменения в объёме, соответствующем риску и типу проекта: как минимум сборку изменённых проектов, а при наличии релевантных тестов — и их выполнение.
- Не исправляй несвязанные проблемы без запроса; сообщи о них отдельно.
- Записывай пути, результаты проверки, Git commit и ссылку в карточку задачи.
- После завершения реализации переводи карточку по workflow `Tasks/AGENTS.md`, а не объявляй код завершённым отдельно от задачи.

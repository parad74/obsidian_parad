## Стартовый solution

Имя сервиса `<Service>` запрашивается в начале и задаёт имя solution, префикс проектов и namespaces. `<Service>` означает выбранное Parad имя; проект Model — `<Имя сервиса>.Model`. Логическое имя БД выбирается отдельно и определяет имя контекста `<ИмяБД>Context`, например `WarehouseDbContext` для `WarehouseDb`. Имя БД не переименовывает проекты или namespaces; имя файла и расширение не входят в имя контекста.

До создания solution с ExportImport задаются начальные вопросы по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]: каждый необходимый незаданный параметр имеет предлагаемый вариант и редактируемое поле для своего значения. До создания solution/проектов сначала спрашивается СУБД со списком для выбора и свободным вводом; после ответа отдельным вопросом предлагается список совместимых провайдеров с семейством EF, пакетом и версией. Оба выбора ожидаются до создания. Логическое имя БД и базовое имя файла спрашиваются отдельно; файл вводится без расширения (`monitor` или своё значение), расширение определяется СУБД (в текущем SQLite-профиле `.db`). Стартовая сводка показывает сервис, БД, контекст и полный путь/подключение раздельно. Вопросы идут по одному, уже выбранное не спрашивается повторно; для одного Model вопросы о БД не нужны.

Запрос создать `<Service>.Model` создаёт `<Service>.sln` с двумя проектами:

```text
<Service>.sln
├─ Service.Model.EF.SelectParam
└─ <Service>.Model
     └─ ProjectReference → Service.Model.EF.SelectParam
```

Запрос создать `<Service>.Model.<DataStore>.CodeFirst.ExportImport` создаёт готовый `<Service>.sln` с тремя проектами:

```text
<Service>.sln
├─ Service.Model.EF.SelectParam
├─ <Service>.Model
│    └─ ProjectReference → Service.Model.EF.SelectParam
└─ <Service>.Model.<DataStore>.CodeFirst.ExportImport
     ├─ ProjectReference → <Service>.Model
     └─ ProjectReference → Service.Model.EF.SelectParam
```

При интеграции используется прямо указанный существующий solution. Текущий первый образец сохраняет своё существующее имя `Monitor.Model.Sqlite.CodeFirst.ExportImport.sln`; для новых автономных применений действует имя `<Service>.sln`.

`Service.Model.EF.SelectParam` физически копируется с исходным кодом в рабочий Git-репозиторий приложения, включается в solution и не заменяется внешним `ProjectReference` на `Sources/Architectures` или пакетом. Копируются `.csproj` и исходники без `bin`, `obj` и Git-метаданных. Существующая локальная копия не дублируется. Ссылка добавляется во все проекты, где используются типы `SelectParam`, и не добавляется в остальные.

В `<Service>.Model` включаются готовые `CommandResult` и `CommandResults`, необходимые перечисления, все пять интерфейсов из образца, `NoEntityAttribute.cs` и ссылка на локальный SelectParam. В ExportImport для стартового `CommandResult` включаются Entity, Fluent API-конфигурация, DbSet, MappingEF и EF-репозиторий. Гибкий кубик применяется к последующим объектам и дополнениям и не сокращает стартовый комплект.

Parad ориентируется на код в solution. Отдельный паспорт применения не создаётся. Машина восстанавливает состояние по solution, проектам, `.csproj`, коду и существующей задаче; дополнительный контекст для своей преемственности хранит в задаче или рабочих заметках без обязательного формата. Обычное сопровождение практической работы Obsidian-задачей сохраняется; отдельная карточка применения не является условием завершения.

## Технологический профиль

Используются шаблоны `<Service>.Model`, `<Service>.Model.<DataStore>.<Approach>.ExportImport`, namespace `<Service>.<DataStore>.<Approach>`, контекст `<ИмяБД>Context` и solution `<Service>.sln`. Имя сервиса и логическое имя БД — независимые значения; контекст определяется именем БД, остальные перечисленные имена — сервисом и выбранным технологическим профилем.

`SQLite` и `MSSQL` — примеры СУБД, а не полный список. `EF Core` и `EF6` — разные семейства Entity Framework. Пакет провайдера выбирается для конкретной пары «семейство EF + СУБД» и проверяется на совместимость с целевым .NET, Code First и нужными операциями со схемой. Другой provider, другое семейство EF или другая СУБД без решения Parad не подставляются.

Если необходимые параметры нового применения не указаны, задай начальные вопросы по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]. Значения первого образца предлагаются для выбора: Model/SelectParam — `netstandard2.0`; ExportImport — `netcoreapp3.1`, EF Core 3.1.9, SQLite, `Microsoft.EntityFrameworkCore.Sqlite` 3.1.9 и `Microsoft.Extensions.Logging` 3.1.9. Без ответа они не применяются автоматически. В существующем solution выбранный профиль проверяется на совместимость; версии других проектов автоматически не перенимаются и не обновляются.

## Согласование модели и создание классов

Машина разбирает входное описание и готовит Excel со всеми объектами, полями, типами, defaults, ограничениями, предложениями и вопросами. Parad проверяет, при необходимости исправляет и возвращает книгу.

Возвращённый утверждённый Excel разрешает создать весь указанный в запросе комплект одним проходом без новых промежуточных согласований. По умолчанию классы создаются в Model и ExportImport; если Parad прямо ограничила запрос, создаются только классы названного проекта или состава. После создания Машина собирает solution и показывает итоговые файлы для вычитки.

## Проверка результата, migrations и БД

Тестовые проекты и автоматизированные тесты на текущем этапе не создаются. После создания solution Машина собирает его и сообщает фактический результат. Затем она выдаёт точные отдельные команды для создания migration `InitialCreate` и отсутствующей БД.

По умолчанию команды запускает Parad; Машина может выполнить каждую только по отдельному явному запросу. После выполнения migration проверяются наличие БД, запись в migration history и ожидаемая схема. Создание migration и применение migration к существующей БД — разные действия. Существующая БД автоматически не обновляется; `EnsureCreated()` для рабочей БД не используется.

## Общий принцип зависимостей

Нижний общий проект может использоваться более высокими слоями приложения, но не ссылается на них обратно:

```text
Front / UI
Business
Application services
Repositories
    → <Service>.Model
```

`<Service>.Model` не зависит от frontend, business, реализаций репозиториев или конкретной СУБД. Его ссылка на `Service.Model.EF.SelectParam` нужна интерфейсам, использующим `SelectParams`.

## Терминология моделей

- `DomainObject` — внутренние данные приложения, доступные репозиториям, прикладным сервисам, бизнес-логике и frontend/UI.
- `Entity` — представление таблицы и столбцов БД внутри конкретной EF-реализации.

Архитектурная роль не добавляется к предметному имени класса. Например, обе стороны могут называться `CommandResult`, оставаясь разными типами в разных проектах и namespaces.

Namespace EF-проекта строится как `<Service>.<DataStore>.<Approach>` и не зависит от структуры папок. Для первого профиля это `Monitor.Sqlite.CodeFirst`.

## <Service>.Model

Проект и корневой namespace называются `<Service>.Model`. Он содержит DomainObject, их коллекции и контейнеры, перечисления, value objects и общие операции над внутренними данными, которые не зависят от конкретной внешней технологии.

DomainObject могут использоваться на всех более высоких слоях приложения без создания отдельной копии только ради каждого слоя.

### Шаблон DomainObject по умолчанию

DomainObject, создаваемые из описания в чате или файле, размещаются в `<Service>.Model/Domain/<Имя>` и предназначены для хранения в БД. Папка `Domain` является границей автоматического создания Entity; типы вне неё автоматически в Entity не преобразуются.

Для нового DomainObject действуют правила:

- первое свойство — обязательное `public long ID { get; set; }`, в конструкторе `ID = 0`;
- `Code` обязателен и используется для `Equals` и `GetHashCode`, но не становится первичным ключом БД;
- рядом создаётся `<Имя>s : ObservableCollection<<Имя>>` с `FromEnumerable`, `CurrentItem`, `CurrentChanged` и `TotalCount`;
- состав остальных полей берётся из утверждённого Excel, а не из предметных полей `CommandResult`;
- атрибуты из опционального столбца `Attributes` добавляются на свойства DomainObject; `[NoEntity]` исключает свойство из Entity, конфигурации и всех методов маппера по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]];
- типы и defaults, отсутствующие во входе, предлагаются в Excel и согласуются возвратом книги.

Если состав полей нового DomainObject вообще не задан, минимальный набор по прежнему согласованному шаблону — `long ID` и строки `Code`, `Name`, `Description`, `Tag`. Покажи этот набор в Excel для проверки; он не подменяет поля переданного описания и не сокращает полный готовый стартовый `CommandResult`.

Конструктор явно инициализирует все свойства. Базовые значения шаблона — `0` для `int`/`long` и `""` для `string`; другие значения из источника или предложенные варианты явно показываются в Excel. Значения конструктора и DB defaults не считаются одним и тем же.

После возврата утверждённого Excel все описанные объекты создаются одним проходом в согласованных проектах. Отдельных подтверждений каждого класса, объекта или этапа нет.

Готовые `CommandResult`, `CommandResults`, перечисления и пять интерфейсов являются стартовой опорой для чтения и генерации модели. Они не удаляются на этапе создания только из-за отсутствия использования. Их последующее удаление выполняется на этапе бизнес-правил по отдельному запросу Parad после проверки зависимостей.

Единичный DomainObject и Entity объявляются обычными классами без автоматически добавленного IEquatable; парная коллекция — отдельный ObservableCollection. Контракты использования и различие равенства по Code и идентичности записи: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Единичный объект и коллекция]].

### Сравнение DomainObject по Code

Шаблон на примере `CommandResult`; для нового предметного объекта используется его имя класса:

```csharp
public override bool Equals(object obj)
{
    if (ReferenceEquals(null, obj))
        return false;
    if (ReferenceEquals(this, obj))
        return true;
    if (obj.GetType() != typeof(CommandResult))
        return false;
    return this.Equals((CommandResult)obj);
}

public bool Equals(CommandResult other)
{
    if (ReferenceEquals(null, other))
        return false;
    if (ReferenceEquals(this, other))
        return true;
    return Equals(other.Code, this.Code);
}

public override int GetHashCode()
{
    return this.Code != null ? this.Code.GetHashCode() : 0;
}
```

### Парная коллекция DomainObject

Согласованный состав коллекции на примере `CommandResults`:

```csharp
public class CommandResults : ObservableCollection<CommandResult>
{
    public static CommandResults FromEnumerable(System.Collections.Generic.IEnumerable<CommandResult> List)
    {
        CommandResults commandResults = new CommandResults();
        foreach (CommandResult item in List)
        {
            commandResults.Add(item);
        }
        return commandResults;
    }

    public CommandResult CurrentItem { get; set; }

    public System.EventHandler CurrentChanged { get; set; }

    public long TotalCount { get; set; }
}
```

Коллекция находится рядом с DomainObject в `Domain/<Имя>` и использует namespace `<Service>.Model`. `FromEnumerable` создаёт типизированную коллекцию, `CurrentItem` хранит текущий объект, `CurrentChanged` — обработчик изменения текущего объекта, `TotalCount` — полное количество записей после фильтрации до paging.

### Согласованная граница с EF

Путь чтения:

```text
СУБД → EF / Entity → MappingEF → DomainObject → верхние слои
```

Путь записи:

```text
DomainObject → MappingEF → Entity → СУБД
```

`Entity`, `DbContext`, tracking state и provider-specific типы не выходят из EF-проекта. `SelectParam` применяется к `IQueryable<Entity>` до материализации. `TotalCount` вычисляется после фильтрации и до paging, затем возвращается в парной коллекции DomainObject.

Маппер знает обе стороны и находится в конкретной EF-реализации. `<Service>.Model` не содержит Entity, DbContext, migrations или provider-specific код.

### Направление зависимостей

- `<Service>.Model` ссылается на локальный `Service.Model.EF.SelectParam`.
- ExportImport ссылается на `<Service>.Model` и на локальный SelectParam, поскольку использует оба проекта.
- Остальные проекты получают ссылки только при фактическом использовании соответствующих типов.

## Тип 2 — пары request/response

Готовые HTTP request/response-типы находятся вне `Domain` и не входят в цепочку объектов из Excel. Они добавляются только по прямому выбору Parad.

Пара хранится в собственной папке:

```text
<Имя>/
├─ <Имя>Model.cs
└─ <Имя>Result.cs
```

По запросу «найди тип данных для `<назначение>`» Машина показывает прямые и близкие варианты, точные имена классов, полноту пары, зависимости и исходные пути, объясняет различия и ждёт выбора. Ничего не добавляется до выбора. Выбранный исходный код переносится без изменений, кроме namespace по контексту.

Связанные базовые типы не добавляются автоматически вместе с парой. Машина показывает найденные зависимости, а переносит только прямо запрошенные или отдельно выбранные Parad типы.

## ExportImport

ExportImport содержит Entity, DbContext, конфигурации, MappingEF и реализации репозиториев для выбранного технологического профиля. Его полный стартовый состав и зависимости создаются вместе с Model и SelectParam в `<Service>.sln` по правилам раздела «Стартовый solution».

### Первый шаг создания EF-проекта

Перед созданием определяются имя сервиса, имя БД, выбранные СУБД, семейство EF и provider. Имя сервиса не выводится из имени БД. Если Model или локальный SelectParam отсутствуют, они создаются или копируются и включаются в тот же solution.

Для базы создаётся папка `<ИмяБД>`, внутри неё — папка каждого Entity. Во всём EF-проекте используется namespace `<Service>.<DataStore>.<Approach>`; имена папок не становятся его частями.

Состав свойств стартового Entity соответствует свойствам парного DomainObject без `[NoEntity]` по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. Первое свойство каждого нового Entity — `long ID`, назначенное первичным ключом таблицы. Парная коллекция `<Имя>s` остаётся в Model и в EF-проект не копируется.

### Шаблон конфигурации Entity для EF Core

Для каждого Entity создаётся один `<Имя>Configuration.cs` с `IEntityTypeConfiguration<<Имя>>`. Entity не содержит Data Annotations схемы БД. Таблица, первичный ключ, генерация значения и свойства столбцов задаются Fluent API в единственной конфигурации типа.

`ID` назначается первичным ключом через `builder.HasKey(p => p.ID)`. Для стартового SQLite-профиля значение генерируется при добавлении. DbContext подключает конфигурации через `ApplyConfigurationsFromAssembly(typeof(<ИмяБД>Context).Assembly)`.

Для EF6 используется соответствующий API `EntityTypeConfiguration<T>` и `DbModelBuilder`; API EF Core механически в EF6 не переносится.

### Шаблон Context для EF Core

Контекст хранится в `Context/<ИмяБД>Context.cs`, получает `DbContextOptions<<ИмяБД>Context>` через конструктор и не содержит `OnConfiguring`.

Для каждого Entity добавляется `DbSet<<ИмяEntity>> <ИмяEntity>Datas`. Суффикс `Datas` отличает DbSet от парной коллекции DomainObject `<Имя>s`. `OnModelCreating` только подключает конфигурации текущей assembly.

Connection string, migrations, создание БД и seed data в DbContext не помещаются. Первоначальной инициализацией отсутствующей БД занимается `Context/DbInitializer.cs`.

### Источник модели и migrations

Текущий процесс — Code First. Существующая БД или Entity-модель может служить входом для Excel; после проверки и возврата книги применяется тот же workflow.

При создании или дополнении объектов утверждённый Excel задаёт модель. Весь запрошенный комплект классов и изменений создаётся одним проходом в Model и ExportImport либо только в прямо указанном проекте. Существующие поля не переименовываются, не изменяются и не удаляются автоматически.

Создание migration и её применение к существующей БД выполняются только по отдельным явным запросам либо вручную Parad. До первого запуска должна существовать проверенная migration `InitialCreate`. `DbInitializer` применяет подготовленные migrations только для создания отсутствующей БД; существующая БД автоматически не обновляется.

## Внутренняя организация кода

При организации кода приоритет — чтобы Parad могла быстро прочитать его и понять поведение. Общую часть стоит выделять в отдельный метод, когда она представляет самостоятельную, понятную по смыслу операцию с единым контрактом для всех мест использования.

Само совпадение нескольких строк не является достаточным основанием для выделения метода. Если два участка относятся к разным операциям и могут независимо развиваться, допустимо сохранить похожий код отдельно, чтобы не связывать их изменения.

Это ориентир для инженерного решения, а не абсолютный запрет на повторение или выделение методов.

Например, `ToString()` или `ParseToObject()` уместны как отдельные операции, если у них определён общий смысл: какой формат представления или разбора они обеспечивают. Их реализация может меняться, но все вызывающие места должны ожидать именно этот контракт. Похожие присваивания при создании и обновлении объекта не обязательно объединять: правила создания и обновления могут различаться и меняться независимо. Эти примеры не предписывают добавлять названные методы в каждый класс.

При выборе организации кода Машина проверяет:

- Это одна и та же операция по смыслу или просто похожий код?
- Выделение метода помогает Parad читать код или заставляет переходить между файлами ради нескольких очевидных строк?

## Библиотеки и смена версий

Если решение работает и задача не требует изменения библиотек, сохраняй используемые библиотеки и их версии. Не обновляй и не заменяй зависимости только ради более новой версии или предпочтения Машины.

Если Машина считает необходимым добавить, заменить или удалить библиотеку либо изменить её версию, сначала объясни Parad, что предлагается изменить, зачем это нужно и как может повлиять на работоспособность решения. Покажи конкретные библиотеки и версии, когда они определены, и дождись согласия до изменения зависимостей. Изменение библиотек не должно быть неожиданностью для Parad. Выбор обычного метода уже используемой библиотеки отдельного согласования зависимостей не требует.

Если Parad сама требует перехода на другую версию, её запрос разрешает этот переход; повторно спрашивать разрешение на уже указанный переход не нужно. До изменения проверь совместимость, затем адаптируй зависящий код и проверь сборку и затронутые рабочие сценарии. Цель — сохранить работоспособность решения после перехода, а не только изменить номер версии. Если для этого нужны дополнительные изменения библиотек вне запрошенного перехода, объясни их и согласуй с Parad заранее. Непроверенное поведение и оставшиеся проблемы укажи явно.

Это правило касается библиотек и их версий и не разрешает автоматически менять базовые классы, публичные интерфейсы или состав проектов.

## Улучшение закреплённого паттерна

Если Машина видит более подходящий вариант, она может предложить отступление от закреплённого паттерна или образца. В предложении объясни конкретное изменение, его пользу и последствия для решения. Применяй предложенное отступление только после согласия Parad.

Согласованное отступление зафиксируй для конкретного проекта. Оно не становится автоматически правилом всех будущих проектов и не заменяет общий паттерн.

Если Parad отдельно просит изменить общее правило, обнови его и связанные инструкции в согласованной области применения. Согласие на такой запрос не нужно спрашивать повторно. Само одобрение локального решения не является просьбой изменить общее правило; изменение общего правила также не запускает автоматическую переделку ранее созданных проектов.

## Интерфейсы по потребностям задачи

Состав интерфейсов определяется задачей. Если согласовано, что нужна функция, Машина добавляет её в подходящий интерфейс и реализацию, когда это соответствует назначению функции. Отдельное согласование самого добавления метода в интерфейс не требуется; не каждый вспомогательный метод должен становиться частью интерфейса.

Интерфейс не зависит от конкретной реализации, но его контракт используется вызывающим кодом и другими реализациями. При изменении контракта проверь эти зависимости и согласованность сигнатур; необходимые сопутствующие изменения выполняй в рамках задачи. Если возникает неоднозначность поведения или несовместимость с использованием вне доступного проекта, покажи последствия и уточни недостающее решение. Не считай интерфейсы неизменяемыми только потому, что они уже созданы.

Интерфейсы развиваются по потребностям задачи без отдельного вопроса для каждого изменения интерфейса. Это не разрешает автоматически менять библиотеки или общее архитектурное правило. После создания всего согласованного комплекта итоговый код предоставляется для вычитки.

## Образец как опора при создании модели

На этапе создания модели сохраняй предусмотренный стартовый комплект: `CommandResult`, парную коллекцию `CommandResults`, необходимые перечисления и все пять интерфейсов. Для Parad это опора при чтении и построении модели, даже если часть комплекта пока не используется в предметной задаче или относится к другому провайдеру.

Включай комплект с учётом согласованных правил конкретного проекта: адаптируй namespaces, ссылки на типы и соответствующие сервису имена; сохраняй согласованные правила библиотек и совместимость. Состав новых предметных объектов определяется их входным описанием; поля `CommandResult` не становятся обязательными полями других моделей.

Не исключай и не удаляй части этого комплекта на этапе создания модели только из-за их неиспользования. После создания модели, на этапе бизнес-правил, Parad отдельно попросит удалить ненужное. Тогда проверь фактическое использование и зависимости и выполни согласованное удаление. Сам переход к бизнес-правилам не является командой очистки. Существующий эталон сохраняется.

## Согласованные правила развития и вычитки

Таблицы этой архитектуры независимы. Повторы Code допустимы. Удаление по Code удаляет все совпадения; чтение и обновление по Code выбирают запись с минимальным техническим ID. Обновление по ID выбирает запись только по ID и переносит данные, включая Code, без проверки совпадения кодов. При обоих способах обновления ID записи в БД сохраняется. Политика не требует повторного согласования для каждого проекта. Равенство состава DomainObject/Entity относится к стартовому шаблону с исключением свойств DomainObject, помеченных `[NoEntity]`; последующие бизнес-различия описываются и отображаются явно. Достаточно описанные дополнительные методы реализуются, неизвестное поведение оставляется явно обозначенной заглушкой. Подробности: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

После создания согласованного комплекта показывай созданные из описания или интерфейса файлы/классы целиком для вычитки. Отметки CodeReview добавляй только по явной просьбе Parad для текущих изменений или дополнений («при изменениях пометь как TODO», «при дополнениях пометь как TODO» или равнозначная формулировка). По умолчанию, включая первую генерацию, создание, миграции и добавление данных, комментарии вычитки не добавляются.

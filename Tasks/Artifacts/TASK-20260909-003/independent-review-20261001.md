# Независимое ревью workflow SelectParam — 2026-10-01

Источник: отдельная задача Codex «Независимое ревью workflow SelectParam», ID `01a0f77d-7655-7cb0-b6e8-ed53aa9e3cc8`. Ревью выполнено только по документам и указанным в них исходникам, без передачи переписки.

После получения отчёта повреждённая фраза о связанных типах приведена к действующему правилу, а результирующий документ решений очищен от прежних предложений, закрытых вопросов и планов выполненных шагов. Полная цепочка относится к объектам утверждённой Excel-модели, а готовые HTTP request/response-пары находятся вне `Domain` и добавляются только по прямому выбору.

Замечания 1 и 2 закрыты решением Parad 2026-10-01. Новый автономный ExportImport создаётся как `<Service>.sln` из трёх проектов с полной стартовой цепочкой `CommandResult` в Model и ExportImport. Тестовые проекты и автоматизированные тесты на текущем этапе не рассматриваются: обязательны сборка solution, выдача точных отдельных команд `InitialCreate` и создания отсутствующей БД, а после их выполнения — проверка БД, migration history и ожидаемой схемы. Выполнение каждой команды Машиной требует отдельного явного запроса Parad.

Замечание 3 закрыто решением Parad 2026-10-01. `Service.Model.EF.SelectParam` копируется с исходным кодом внутрь рабочего Git-репозитория приложения, включается в `<Service>.sln`, а `ProjectReference` на локальный проект добавляется каждому проекту, где используются типы `SelectParam`. Внешняя ссылка на checkout `Sources/Architectures` и пакет вместо проекта не используются; существующая локальная копия не дублируется.

Замечание 4 закрыто решением Parad 2026-10-01. Отдельный паспорт применения и обязательный формат не нужны. Для Parad состояние видно в solution, названиях проектов, `.csproj` и коде; дополнительный рабочий контекст Машина может хранить в существующей задаче или своих заметках так, как ей удобно, не создавая новый тип карточки.

Ниже сохранены замечания исходного отчёта; номера строк относятся к состоянию на момент ревью. Прежнее поклассное согласование заменено позднейшим решением Parad: Excel, проверка и возврат книги, затем создание всего запрошенного комплекта одним проходом в обоих проектах либо только в прямо указанном проекте. Проверка первичной переписки 2026-10-02 установила, что прежнее правило действительно было согласовано 2026-09-21; ошибкой было его сохранение после изменения процесса, а не отсутствие у него исторического основания.

## Существенные замечания

1. **Не определён объектный состав нового ExportImport-проекта.**

   Пользовательская инструкция говорит брать состав файлов из готового образца ([Wiki, строка 68](<W:/obsidian/_parad/Wiki/HowToDo/Create Project Domain Model by Step.md:68>)), а карточка образца включает `CommandResult` Entity, конфигурацию, маппер и репозиторий ([карточка ExportImport, строка 25](<W:/obsidian/_parad/Documents/Architectures/LibProject/netcoreapp3.1/Monitor.Model.Sqlite.CodeFirst.ExportImport.md:25>)). Одновременно кубик требует создавать только выбранные этапы и запрещает запуск полного комплекта от запроса одного этапа ([кубик, строки 32–36](<W:/obsidian/_parad/Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository.md:32>)).

   Последствие: на запрос «создай `<Service>.Model.Sqlite.CodeFirst.ExportImport`» один исполнитель перенесёт весь `CommandResult`-комплект, другой создаст только инфраструктурную оболочку и станет ждать входную модель.

   Минимальное устранение: одной фразой определить состав именно проектного запроса:

   - либо инфраструктура без объектных Entity/Mapper/Repository;
   - либо инфраструктура плюс стартовая цепочка `CommandResult`.

   После этого уточнить, что запросы объектов управляются кубиком независимо.

2. **Тесты обязательны для результата задачи, но их проектная архитектура не определена.**

   Задача требует общих тестов `SelectParam` и интеграционных тестов настоящего провайдера ([задача, строка 74](<W:/obsidian/_parad/Tasks/Items/dotnet_architecture_examples/TASK-20260909-003-design-selectparam-guided-workflow.md:74>)), а для каждого поддерживаемого профиля — интеграционных тестов ([строка 115](<W:/obsidian/_parad/Tasks/Items/dotnet_architecture_examples/TASK-20260909-003-design-selectparam-guided-workflow.md:115>)). При этом базовые solution описаны только как два или три production-проекта ([команда, строка 30](<W:/obsidian/_parad/Commands/Create Project Domain Model by Step.md:30>)); фактический первый ExportImport solution также содержит ровно три проекта ([solution, строки 6–10](<W:/obsidian/_parad/Sources/Architectures/LibProject/netcoreapp3.1/Monitor.Model.Sqlite.CodeFirst.ExportImport/Monitor.Model.Sqlite.CodeFirst.ExportImport.sln:6>)).

   Не определены имена тестовых проектов, target framework, тестовый framework, место в solution и момент создания.

   Минимальное устранение: либо явно вынести тесты в отдельный запрашиваемый этап и признать текущий эталон неполным, либо описать минимальные тестовые проекты как часть эталона. Без этого нельзя однозначно выполнить критерии приёмки TASK-003.

3. **Не определено, как `SelectParam` попадает в рабочий репозиторий приложения.**

   Каждый рабочий проект приложения должен жить в собственном Git-репозитории, а `Sources/Architectures` — отдельный репозиторий эталонов ([AGENTS.md, строки 45–46](<W:/obsidian/_parad/AGENTS.md:45>)). Команда требует прямой `ProjectReference` на `Service.Model.EF.SelectParam` ([строка 81](<W:/obsidian/_parad/Commands/Create Project Domain Model by Step.md:81>)), но не говорит, следует ли:

   - копировать проект в репозиторий приложения;
   - ссылаться на checkout `Sources/Architectures`;
   - публиковать/использовать пакет;
   - создавать отдельную общую локальную библиотеку.

   Первый эталон использует соседний относительный путь ([Monitor.Model.csproj, строка 8](<W:/obsidian/_parad/Sources/Architectures/LibProject/netstandard2.0/Monitor.Model/Monitor.Model.csproj:8>)), что работает внутри репозитория архитектур, но не определяет переносимый вариант для `Sources/<Project ID>`.

   Минимальное устранение: зафиксировать отдельное правило для рабочего приложения. До этого первое применение вне `Sources/Architectures` требует решения Parad.

4. **Не определены место и полный формат паспорта применения.**

   Задача требует хранить в паспорте режим, runtime, EF, провайдер, состав проектов, способ создания БД и тестовые данные ([задача, строки 54–62](<W:/obsidian/_parad/Tasks/Items/dotnet_architecture_examples/TASK-20260909-003-design-selectparam-guided-workflow.md:54>)). Кубик добавляет источник, последовательность, пути, подтверждённые добавления и результаты проверки ([кубик, строка 116](<W:/obsidian/_parad/Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository.md:116>)). Но рабочая команда говорит сначала предложить место ([команда, строка 88](<W:/obsidian/_parad/Commands/Create Project Domain Model by Step.md:88>)), а Wiki откладывает решение до первого проекта ([Wiki, строка 131](<W:/obsidian/_parad/Wiki/HowToDo/Create Project Domain Model by Step.md:131>)).

   Последствие: исполнитель должен либо придумать новый тип карточки, либо поместить неполные сведения в обычную задачу.

   Минимальное устранение: определить, является ли паспорт существующей карточкой задачи или отдельным артефактом, и дать один обязательный перечень полей. Для минимальности разумно переиспользовать существующую карточку, но это решение должно принять Parad.

5. **Прямое расхождение в правиле связанных request/response-типов.**

   Рабочая команда содержит повреждённую фразу «Связанные тидобавляются автоматически» ([команда, строка 135](<W:/obsidian/_parad/Commands/Create Project Domain Model by Step.md:135>)). Wiki говорит обратное: связанные базовые типы показываются отдельно и не предполагаются автоматически ([Wiki, строка 244](<W:/obsidian/_parad/Wiki/HowToDo/Create Project Domain Model by Step.md:244>)); документ обсуждения также сообщает, что автоматическое добавление не согласовано ([строка 485](<W:/obsidian/_parad/Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md:485>)).

   Минимальное исправление очевидно: заменить повреждённую фразу формулировкой из Wiki.

   Раздел «Предлагаемая граница» по-прежнему говорит, что чистая граница Model требует согласования ([строки 364–375](<W:/obsidian/_parad/Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md:364>)), хотя актуальная команда уже задаёт её как инвариант ([команда, строка 41](<W:/obsidian/_parad/Commands/Create Project Domain Model by Step.md:41>)).    Верхнее предупреждение о приоритете кубика помогает, но команда одновременно называет этот документ источником точных шаблонов. Минимальное устранение — пометить такие разделы «Историческое, заменено…» и дать ссылку на актуальное правило.

## Восстановленный результат по сценариям

| Запрос | Однозначно определённый результат |
| --- | --- |
| Создать `<Service>.Model` | Новый `<Service>.sln` с `<Service>.Model` и `Service.Model.EF.SelectParam`. Оба проекта — `netstandard2.0`; Model ссылается на SelectParam и использует `System.ComponentModel.Annotations` 4.7.0. В Model добавляются `CommandResult`, `CommandResults`, необходимые перечисления и пять интерфейсов с адаптацией `Monitor` → `<Service>`. Entity, DbContext и EF-код не входят. |
| Создать ExportImport | Новый `<Service>.sln` с ExportImport, `<Service>.Model` и `Service.Model.EF.SelectParam`. Defaults: `<Service> = Monitor`, SQLite, Code First, `netcoreapp3.1`, EF Core 3.1.9, SQLite provider 3.1.9, Logging 3.1.9, namespace `<Service>.Sqlite.CodeFirst`, `<Service>DbContext`. Имя БД и имя/путь файла SQLite определяются отдельными обязательными вопросами при старте, если ещё не заданы; из имени сервиса не выводятся. В Model включается готовый `CommandResult` с коллекцией, перечислениями и интерфейсами; в ExportImport — его Entity, конфигурация, `DbSet`, MappingEF и EF-репозиторий. После сборки выдаются отдельные команды `InitialCreate` и создания отсутствующей БД. |
| Объекты из входного описания без перечисления этапов | Сначала нормализованная `.xlsx`, совместимая с Excel 2013: лист на объект, строка на свойство, отдельно исходные и предлагаемые значения. После возврата утверждённой книги выполняется цепочка DomainObject + коллекция → Entity + конфигурация + DbContext → MappingEF → Repository + интерфейс. |
| Явно «только Entity» | Только Entity, его конфигурация и подключение к существующему DbContext. DomainObject, MappingEF и Repository не запускаются. При отсутствии EF-проекта или контекста требуется вопрос о существующих путях либо расширении состава. |
| Дополнить существующую пару | Используются существующие классы. При запросе синхронизации поля дополняются Entity, DomainObject, конфигурация и маппер; уже существующая часть не создаётся заново. Repository меняется только если включён в запрос или затронут его согласованный контракт. Существующие поля не удаляются и не переделываются; migration не создаётся. |

Для всех новых пар обязательны первое свойство `long ID`, `ID = 0` в конструкторе DomainObject, PK по `ID`, обязательный логический `Code`, парная коллекция и независимые таблицы без автоматически переносимых связей. Это согласованные предпочтения Parad, а не ошибки архитектуры.

Инженерное решение допустимо для предлагаемых типов/defaults, внутреннего выделения методов, использования подходящих шаблонов .NET, реализации достаточно описанных дополнительных методов и добавления уже согласованной функции в подходящий интерфейс. Согласование обязательно для предметного смысла, конфликтов модели, политики дубликатов `Code`, изменения библиотек и версий, отступления от паттерна, расширения этапов, изменения существующих полей и любых migrations.

## Что блокирует первое применение

Общих нерешённых решений по замечаниям 1–5 больше нет. Состав нового ExportImport, перенос `SelectParam`, способ ведения рабочего контекста и границы полной/точечной генерации определены. Тестовые проекты и автоматизированные тесты вынесены за границы текущего этапа.

Обычные вопросы конкретного применения:

- интеграция или отдельный solution и его путь;
- источник и список объектов;
- выбор при несовместимости defaults с целевым solution;
- политика повторяющегося `Code` для чтения и удаления на этапе Repository;
- конфликт входного PK с обязательным `ID long`;
- пути отсутствующих зависимостей при частичной последовательности.

`ToSimpleDomainObject` не блокирует остальные этапы: документы разрешают явно обозначенную заглушку, пока его сокращённый состав не определён.

### Найденные ошибки и исправления

1. Правило согласовывать каждый объект каждого этапа действительно было в ответе Parad 21 сентября. После нового процесса через Excel оно устарело. Утверждение Машины «никогда не было решением Parad» исправлено в отчёте и журнале задачи; действующий процесс не меняется.
2. При сокращении D пропал минимальный шаблон полей для случая полного отсутствия описания и конкретные базовые значения конструктора. Они восстановлены по Git и включены в нынешнее согласование через Excel.
3. В F оставалось требование адресного теста. Оно удалено по прямому решению B; непроверенное поведение должно называться честно.
4. Дополнительный поиск нашёл прежние поклассные подтверждения в действующих разделах связанной [[Tasks/Items/dotnet_architecture_examples/TASK-20260921-001-create-data-object-cube]]. Они также заменены текущим процессом; исторические записи от 21 сентября сохранены с явным разграничением истории и текущих правил.

Проверены wikilink-цели и заголовки в 11 основных документах, парность блоков кода и все 6 уникальных входящих ссылок на разделы D: потерянных целей не найдено. `git diff --check` для затронутых отслеживаемых документов не выявил ошибок пробелов; предупреждения LF/CRLF не являются потерей содержимого.

Сверка подтверждает перенос перечисленных решений в указанные документы. Она не заменяет проверку Parad и не подтверждает, что все профили, последовательности и migrations уже выполнены. Код, проекты и БД при этой сверке не изменялись; новые commit/push не выполнялись.

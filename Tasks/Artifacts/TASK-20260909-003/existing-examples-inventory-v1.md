# SelectParam — инвентаризация существующих примеров, версия 1

Дата: 2026-09-09.

## Область исследования

- общая библиотека: `Sources/Architectures/LibProject/netstandard2.0/SelectParam`;
- историческое решение: `Sources/old/WebAPI.Monitor/WebAPI.Monitor.Model.sln`;
- предметная модель и контракт репозитория;
- реализации для SQL Server, SQLite и SQL Server Compact;
- ветки Code First и Database First;
- существующие тестовые данные и способы ручной проверки.

Исторические файлы исследованы без изменений.

## Главный вывод

Во всех EF-примерах повторяется одна логическая цепочка:

```text
SelectParams
    -> IQueryable сущности
    -> фильтрация запроса подсчёта
    -> TotalCount до paging
    -> фильтрация основного запроса
    -> сортировка и paging
    -> выполнение запроса провайдером EF
    -> преобразование EF-сущности в предметную модель
    -> коллекция результата с TotalCount
```

Эта цепочка является основой будущего руководства. СУБД, семейство EF, способ построения модели и конкретные классы являются вариантами вокруг неё.

## Слои исторического решения

### 1. Общая библиотека SelectParam

`Service.Model.EF.SelectParam` содержит параметры фильтрации, сортировки и paging, а также применение этих параметров к `IQueryable<T>`.

Библиотека не ссылается на проекты предметной модели или репозитория. При этом её текущий проект содержит package references на `EntityFramework` 6.4.0 и `Microsoft.Windows.Compatibility` 3.1.1; независимость от этих пакетов должна быть проверена отдельно, а не предполагаться.

### 2. Предметная модель и контракт

В `Monitor.Service.Shared` находятся:

- `Monitor.Service.Model.CommandResult` — предметная модель;
- `Monitor.Service.Model.CommandResults` — коллекция предметных объектов с `TotalCount`;
- `Monitor.Model.ServiceContract.Interface.ICommandResultRepository` — контракт репозитория, принимающий `SelectParams`.

Исторический проект `Monitor.Model.ServiceContract` почти не участвует в этой цепочке и не должен автоматически воспроизводиться в новом эталоне только из-за имени.

### 3. EF-модель конкретного профиля

Code First-примеры содержат отдельный класс EF-сущности `CommandResult`, конфигурацию таблицы и полей и `DbContext`.

Database First-пример подключает сгенерированные классы и EDMX из отдельного design-host проекта. Это отдельная ветка руководства, а не небольшое изменение Code First.

### 4. Преобразование моделей

Для каждого профиля есть `CommandResultMapper`, преобразующий:

- EF-сущность в предметную модель;
- предметную модель в EF-сущность;
- изменения предметной модели в существующую EF-сущность.

Следовательно, существующая архитектура разделяет предметную модель и модель хранения. В новом эталоне это разделение следует сохранить, пока Parad явно не выберет вариант с одной общей моделью.

### 5. Реализация репозитория

`BaseEFDbSetRepository.GetEntities` выполняет повторяемые действия:

1. применяет фильтр к запросу подсчёта;
2. получает `LongCount` до paging;
3. применяет фильтр к основному запросу;
4. применяет сортировку и paging;
5. материализует результат.

Конкретный `CommandResultEFRepository` создаёт или получает контекст, вызывает общий алгоритм, преобразует сущности и записывает `TotalCount` в возвращаемую коллекцию.

### 6. Host/API

Проекты `WebAPI.Monitor.Model.*` передают полученный `SelectParams` в репозиторий и возвращают результат. Web API является потребителем цепочки, но не обязателен для первого минимального эталона: автоматические интеграционные тесты могут вызывать репозиторий напрямую.

## Существующие тестовые данные

В реализациях репозитория метод `GetTestDataCommandResults` создаёт набор записей с `SessionCode` от `testSessionCode1` до `testSessionCode7`. В SQLite также есть `DbInitializer`, создающий базу и добавляющий начальную запись.

Контроллеры содержат ручные тестовые методы, которые создают `SelectParams` и проверяют фильтры по строковым полям и спискам.

Это полезные источники тест-кейсов, но они не являются достаточными автоматическими тестами:

- самостоятельные test-проекты с `Microsoft.NET.Test.Sdk` не найдены;
- Web API-проекты содержат ссылку на `MSTest.TestFramework`, но проверка выполняется кодом контроллеров и репозитория;
- тестовые данные смешаны с рабочей реализацией репозитория;
- ожидаемые результаты тестов формально не закреплены assertions.

В новом эталоне seed data, тестовые данные и проверяемые ожидания должны быть разделены.

## Инварианты для будущего руководства

- `SelectParam` применяется к `IQueryable` до `ToList` и других способов материализации.
- `TotalCount` вычисляется после фильтрации, но до paging.
- Предметная модель отделена от EF-сущности и связывается явным маппером.
- Контракт репозитория не зависит от конкретной СУБД.
- EF-пакеты и провайдер находятся в проекте конкретной реализации.
- Реальный провайдер проверяется интеграционным тестом, а не только LINQ to Objects.
- Тестовые записи детерминированы, а ожидаемые результаты заданы явно.
- Неподтверждённая комбинация EF и провайдера не считается поддержанной.

## Переменные части

- семейство runtime и target framework;
- EF6 или EF Core и версия;
- СУБД, provider package и версия;
- Code First или Database First;
- способ создания и обновления базы;
- имена solution, проектов, namespace, сущностей и таблиц;
- состав полей, ключи, значения по умолчанию, связи и индексы;
- тестовые данные;
- способ запуска проверки: test runner, Console либо host/API.

## Важные ограничения, найденные в текущей библиотеке

- При отсутствии `SortParams` библиотека сортирует по `ID ASC`. Модель должна иметь доступное поле `ID`, либо вызывающий код должен всегда задавать сортировку, либо поведение библиотеки должно быть отдельно пересмотрено.
- Имена полей фильтрации и сортировки передаются строками. Руководство должно сверять их с нормализованной моделью до запуска теста.
- Совместимость выражений нельзя считать одинаковой для всех EF-провайдеров; её подтверждает только выполнение интеграционных тестов.

## Предлагаемый путь от примеров к цели

1. Инвентаризация существующих примеров — выполнена в версии 1 этого документа.
2. Согласовать минимальную каноническую цепочку проектов на основе найденных слоёв.
3. Согласовать нормализованный формат описания модели и технологического профиля.
4. Создать первый чистый эталон: EF Core в приоритете, SQLite и Code First как минимальный локальный профиль.
5. Перенести в автоматические тесты полезные сценарии исторических примеров: простой фильтр, строковый список, сортировка, paging и `TotalCount`.
6. Повторить тот же процесс с другой моделью, полученной из внешнего описания, и проверить, что руководство действительно воспроизводимо.
7. Добавить второй EF Core-провайдер, прежде всего SQL Server.
8. Описать отдельную ветку EF6 на основании SQL Server и SQL Server Compact примеров.
9. Описать Database First как отдельную ветку после Code First.
10. После повторной успешной проверки решить, нужен ли автоматизированный шаблон или навык Codex.

## Следующее решение

Перед созданием архитектурной карточки нужно выбрать модель первого чистого эталона:

- сохранить полный исторический `CommandResult` для максимально прямого сравнения;
- использовать уменьшенную нейтральную модель с теми же типами полей и сценариями SelectParam, чтобы эталон не зависел от большой предметной области старого приложения.

# TASK-20260909-003 — Спроектировать управляемый сценарий SelectParam

## Проект: dotnet_architecture_examples

- [r] Создать пошаговое руководство и проверенные эталоны применения SelectParam 🆔 TASK-20260909-003

## Цель

Версия 1 от 2026-09-09.

Уточнение текущего этапа от 2026-09-20: сейчас обсуждаются и исправляются отдельные правила workflow. Окончательная общая цель и границы полного выполнения будут определены отдельно позднее; ниже сохранён исходный замысел задачи. Команда «сделай всё» в текущий процесс не вводится, и определять её состав или точку завершения на этом этапе не требуется.

Создать управляемый сценарий проектирования решений на основе паттернов Parad и входной модели данных, а не механического повторения образца. Машина дополняет согласованные паттерны инженерным опытом и подходящими средствами .NET/Microsoft, сохраняет понятность кода для Parad, спрашивает о предметных неоднозначностях и показывает предлагаемый код. Фактическое состояние определяется по solution, названиям проектов, `.csproj` и коду; дополнительный рабочий контекст Машина при необходимости хранит в существующей задаче или своих заметках без обязательного формата.

Текущий процесс — Code First; существующая БД или Entity-модель может служить входом для Excel, затем после утверждения модели применяется обычный процесс. EF6 или EF Core и совместимые версии определяются для конкретного проекта; API и провайдер подбираются соответственно. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Code First и выбор семейства EF]].

## Описание

Решение должно разделять три уровня:

1. Постоянное архитектурное руководство с порядком этапов, вопросами, вариантами и критериями проверки.
2. Нормализованную спецификацию конкретного применения, содержащую выбранные технологии, модель данных и тестовые данные.
3. Эталонные проекты и поэтапные проверки: сначала успешная сборка solution, затем проверка БД после создания и применения `InitialCreate`.

Исходное описание данных может поступать в свободном тексте, Markdown-таблице, CSV или Excel, JSON, SQL DDL, классах C#, EF-конфигурации либо другом доступном формате. Перед генерацией кода Codex должна преобразовать его в единую спецификацию, разделить подтверждённые, предполагаемые и отсутствующие сведения и согласовать неоднозначности с Parad.

Состав работы определяется запросом Parad и фактическим состоянием проекта: названные части создаются или дополняются, существующие части используются без дублирования. 11 последовательностей кубика — примеры, а не закрытый список команд. После возвращения утверждённого Excel весь запрошенный комплект создаётся одним проходом: по умолчанию в Model и ExportImport, а при явно ограниченном запросе — только в названном проекте или составе. При недостающих зависимостях уточни существующие пути либо расширение состава до генерации. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]].

При создании объектов из описания сначала верни разобранную модель в Excel для проверки Parad. Продолжай только по возвращённой и утверждённой книге; нерешённые вопросы уточни до генерации. Возвращённый Excel подтверждает описанную в нём модель: после него создай все классы согласованного объёма одним проходом в обоих проектах либо, если Parad ограничила запрос, только в названном проекте или составе. Не вводи дополнительных подтверждений для каждого объекта, класса или этапа. Обязательные поля должны быть явно видны в Excel.

Если для утверждённой Excel-модели Parad не ограничила состав этапов, выполняется полная цепочка DomainObject с коллекцией → Entity с конфигурацией и DbContext → MappingEF → Repository с интерфейсом. При точечном запросе выполняются только прямо названные этапы или типы. Готовые HTTP request/response-контракты находятся вне `Domain`, не входят в Excel-цепочку и добавляются только по прямому выбору Parad; их связанные базовые типы предварительно показываются и также требуют прямого запроса или отдельного выбора.

Дополнение существующих объектов определяется запросом и найденным кодом. Используй существующие классы; не создавай пару заново и не запускай не запрошенные части автоматически. При запросе синхронизации поля одним проходом дополни все входящие в запрос Entity, DomainObject, конфигурации и мапперы. Если отсутствует необходимая часть, уточни её путь либо создание до генерации. После возвращения утверждённого Excel отдельные подтверждения по объектам и этапам не требуются. Существующие поля автоматически не удаляются и не переделываются; migrations остаются отдельными запрошенными действиями.

Для каждого нового `DomainObject` обязательное первое свойство — `public long ID { get; set; }`. Оно добавляется автоматически, если отсутствует во входном описании; корректный `ID long` из источника не дублируется. В парном `Entity` `long ID` также объявляется первым и является первичным ключом таблицы. В конструкторе `DomainObject` явно устанавливается `ID = 0`; типовые методы репозитория по `ID` используют `long`. `Code` остаётся обязательным логическим ключом сравнения.

Нормализованное описание сущности должно учитывать как минимум:

- отдельные имена класса и таблицы;
- отдельные имена свойства и столбца;
- CLR-тип и тип СУБД;
- nullable, первичный ключ и способ генерации значения;
- длину, precision и scale, когда применимо;
- отдельные значения по умолчанию C# и базы данных;
- комментарии к свойствам и столбцам;
- атрибуты свойств DomainObject в опциональном столбце Excel `Attributes`, включая исключение `[NoEntity]`;
- связи и индексы источника как исходные сведения; в этой архитектуре таблицы независимы, реляционные связи в целевую модель не переносятся;
- seed data и тестовые данные отдельно от значений по умолчанию.

Перед созданием определяются все необходимые для запрошенного состава параметры: уже заданные Parad, найденные в текущем проекте или ранее согласованные используются без повторных вопросов; остальные спрашиваются по одному с предложенным вариантом и свободным вводом по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]:

- режим: отдельный эталон или интеграция в существующий solution;
- семейство runtime и target framework;
- семейство EF (`EF6` или `EF Core`) и его точная версия;
- СУБД, пакет провайдера и его точная версия;
- подход: Code First; БД или Entity-модель могут быть источником входных данных для Excel;
- состав и имена проектов;
- модель, репозиторий, способ создания базы и набор тестовых данных.

Эти настройки независимы: `SQLite` и `MSSQL` — разные СУБД; `EF Core` и `EF6` — разные семейства EF; пакет провайдера выбирается для их конкретной пары. Сегмент `Sqlite` или `MSSQL` в имени проекта и namespace обозначает СУБД, а не семейство EF.

Параметры первого готового образца теперь служат предложениями в начальных вопросах, а не автоматически применяемыми defaults. Каждый необходимый незаданный параметр спрашивается до создания: вариант образца или своё значение. Примеры предложений: имя сервиса `Monitor`, Model/SelectParam — `netstandard2.0`, EF-проект — `netcoreapp3.1`, EF Core 3.1.9, SQLite и `Microsoft.EntityFrameworkCore.Sqlite` 3.1.9. При интеграции выбранный профиль проверяется на совместимость; версии других проектов solution автоматически не перенимаются. Полное правило и порядок выбора СУБД/провайдера: [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]. Это не вводит команду «сделай всё».

Базовый состав solution определяется запросом: для `<Service>.Model` — Model и SelectParam; для `<Service>.Model.Sqlite.CodeFirst.ExportImport` — ExportImport, Model и SelectParam. Общего запрета включать другие проекты в solution нет. Необходимые проекты и зависимости создаются или подключаются в рамках запрошенной работы; ограничения зависимостей конкретного проекта не ограничивают перечень проектов solution.

В рабочем Git-репозитории приложения `Service.Model.EF.SelectParam` хранится как скопированный проект с исходным кодом и включается в `<Service>.sln`. Он не подключается внешней ссылкой на checkout `Sources/Architectures` и не заменяется пакетом. Если локального проекта ещё нет, копируется эталон без `bin`, `obj` и Git-метаданных; существующая копия не дублируется. `ProjectReference` на локальный `Service.Model.EF.SelectParam.csproj` добавляется каждому проекту, где используются типы `SelectParam`, и не добавляется неиспользующим проектам.

Новый автономный solution называется именем сервиса, выбранным в начале: `<Service>.sln`. Имя БД и имя ExportImport-проекта это имя не меняют. Запрос создать `<Service>.Model.<DataStore>.CodeFirst.ExportImport` включает готовый стартовый `CommandResult` в двух проектах. В Model создаются DomainObject `CommandResult`, `CommandResults`, необходимые перечисления и интерфейсы; в ExportImport — Entity, Fluent-конфигурация, `DbSet`, MappingEF и EF-репозиторий. Гибкий выбор этапов применяется к последующим объектам и дополнениям, но не сокращает этот стартовый комплект.

Тестовые проекты и автоматизированные тесты на текущем этапе не создаются. После создания solution Машина обязана собрать его и сообщить результат. Затем проверяется design-time готовность и выдаются две точные отдельные команды: создание `InitialCreate` и применение migrations для создания отсутствующей БД. По умолчанию их запускает Parad; Машина может выполнить каждую по отдельному явному запросу. После применения migration проверяются существование БД, запись migration history и ожидаемая схема. Существующая БД автоматически не обновляется.

При старте ExportImport отдельно определяются имя сервиса, СУБД, совместимый провайдер, логическое имя БД и имя/расположение файла для файлового подключения. СУБД спрашивается в начале, затем показывается список предлагаемых совместимых провайдеров с семейством EF, пакетом и версией. Имя файла вводится без расширения (`monitor` или своё значение); расширение определяется СУБД, для текущего SQLite-профиля `.db`. Имя сервиса задаёт проекты, namespaces и solution; Model называется `<Имя сервиса>.Model`. Контекст называется `<ИмяБД>Context` по выбранному логическому имени БД. Для одного Model вопросы о БД не нужны. Начальные вопросы и правило использования уже заданных значений: [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]].

`SQLite` и `MSSQL` служат примерами, а не закрытым перечнем СУБД. Для другой СУБД сценарий требует найти и проверить провайдер и его версию по документации для выбранного семейства EF и целевого .NET до создания проекта.

На текущем этапе автоматизированные тесты и их проектная архитектура не рассматриваются. До создания migration проверяется успешная сборка всего solution. После создания и применения `InitialCreate` к отсутствующей БД проверяются существование БД, регистрация migration и ожидаемая схема.

Исторические проекты в `Sources/old/WebAPI.Monitor` используются как источники решений и примеров данных, но не копируются целиком как новый эталон. Автоматизированный шаблон или навык создаётся только после согласования руководства и успешной проверки повторного применения.

Готовые `CommandResult`/`CommandResults` из текущего образца `Monitor.Model` служат примером стиля кода для Машины при генерации нового класса и для программиста. При переносе в новый сервис используются готовый состав и необходимые перечисления без повторного согласования адаптации; namespaces и ссылки на типы приводятся к текущему `<Service>`. Предметные поля образца не навязываются другим моделям: новые классы формируются по своим входным данным и общим правилам, а их разбор согласуется возвратом проверенного Excel.

### Внутренняя организация кода

При внутренней организации кода следуй согласованному ориентиру: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Внутренняя организация кода]]. Приоритет — быстрое чтение и понимание кода Parad. Общие методы выделяются по единому смыслу и контракту, а не только из-за совпадения строк; похожие участки с независимым развитием допустимо оставлять отдельно. Это ориентир, а не жёсткий запрет на повторение или выделение методов.

При явно запрошенном переходе проверяй совместимость и сохранение работоспособности. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Библиотеки и смена версий]].

Неиспользование не является основанием убрать их на этом этапе. Удаление ненужного выполняется позднее, на этапе бизнес-правил, по отдельному запросу Parad. ### Согласованные правила развития и вычитки

Таблицы этой архитектуры независимы. Повторы Code допустимы; поведение согласуется по операциям проекта, без универсального выбора минимального ID. Равенство состава DomainObject/Entity относится к стартовому шаблону с исключением свойств DomainObject, помеченных `[NoEntity]`; последующие бизнес-различия описываются и отображаются явно. Достаточно описанные дополнительные методы реализуются, неизвестное поведение оставляется явно обозначенной заглушкой. Подробности: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

После создания согласованного комплекта показывай созданные из описания или интерфейса файлы/классы целиком для вычитки. Перед классом и новыми/изменёнными членами ставь комментарии с датой генерации и статусом вычитки. Новый код требует Full, изменение ранее вычитанного — проверки Changes с отметкой участка; ранее невычитанное не считается прочитанным. Read ставится только по проверке Parad. Рабочий формат: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Показ кода и отметки вычитки]].

## Критерии приёмки

- Согласована архитектурная карточка с обязательными вопросами и последовательностью этапов.
- Создание и дополнение объектов следует составу запроса и существующему коду. После проверки и возврата Excel весь согласованный комплект создаётся одним проходом в обоих проектах либо только в прямо указанном проекте или составе; отдельные подтверждения по объектам и этапам не требуются.
- Определён единый формат нормализованной спецификации технологии и модели данных.
- Каждый новый `DomainObject` и парный `Entity` объявляют обязательное `long ID` первым свойством; в EF-конфигурации `ID` назначен первичным ключом БД, типовые методы репозитория по `ID` используют `long`.
- Семейство EF6 или EF Core выбирается для конкретного проекта с проверкой совместимости; ещё не проверенные профили явно обозначены.
- Процесс использует Code First; существующая БД или Entity-модель преобразуется в Excel для утверждения Parad, а не запускает отдельный Database First workflow.
- Создан и успешно собран как минимум один чистый эталон на EF Core.
- После создания и применения `InitialCreate` к отсутствующей БД проверены создание БД, регистрация migration и ожидаемая схема.
- Фактический состав и состояние можно определить по solution, названиям проектов, `.csproj` и коду; при необходимости следующий шаг кратко сохранён в существующей рабочей задаче или заметках Машины.
- Неподтверждённые комбинации технологий не выдаются за проверенные.

## Ограничения

- Не изменять исторические проекты в `Sources/old/`.
- Не выводить обязательные характеристики схемы только из тестовых значений без явной пометки предположения.
- Не создавать автоматизированный шаблон до проверки эталона и повторного использования.

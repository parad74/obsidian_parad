# Create Project Domain Model by Step

## Назначение

Эта рабочая инструкция применяется, когда Parad просит создать, продолжить или наполнить независимую библиотеку общих контрактов данных приложения, спрашивает следующий шаг для `<Service>.Model` либо использует близкую по смыслу формулировку.

Пользовательская инструкция и источник текущего процесса:

- `Wiki/HowToDo/Create Project Domain Model by Step.md`.

Точные согласованные шаблоны и каталог исторических примеров:

- `Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md`;
- `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared`.

Перед практическим действием полностью прочитай пользовательскую инструкцию и только необходимые разделы документа с точными шаблонами. Исторический проект исследуй точечно; не загружай и не переноси его целиком.

## Результат

Создать и последовательно наполнить проект `<Service>.Model`, который представляет чистый контракт внутренних данных приложения и может использоваться всеми более высокими слоями решения.

По умолчанию `<Service> = Monitor`, поэтому первый вариант называется `Monitor.Model` и использует namespace `Monitor.Model`.

## Инварианты

- Проект не ссылается на другие проекты решения.
- В проекте нет EF, `Entity`, `DbContext`, migrations, provider-specific кода и выбора СУБД.
- В проекте нет ASP.NET-, SignalR-, frontend- и другой инфраструктурной реализации.
- Сторонние NuGet-пакеты по умолчанию не добавляются.
- Разрешены стандартные типы выбранного target framework и операции, принадлежащие самой модели и не зависящие от внешней технологии.
- EF6/EF Core, Code First/Database First, СУБД и provider выбираются позже для проекта доступа к данным, а не для `<Service>.Model`.
- Исторические исходники не изменяются.
- Не добавляй демонстрационные модели, test data, связанные типы или другие проекты без решения Parad.

## Стиль интерактивной работы

1. Сначала назови текущий этап, уже известные параметры и один следующий вопрос или действие.
2. Не заставляй Parad помнить последовательность и не выдавай большую анкету, если достаточно одного вопроса.
3. Если значение можно надёжно получить из существующего solution или карточки применения, покажи найденное значение. Не угадывай неоднозначное.
4. До изменения кода показывай нормализованный предварительный разбор входных данных и планируемые файлы.
5. Не превращай предложение Машины в правило до явного решения Parad.
6. После каждого выполненного шага обновляй карточку применения: выполненное, нерешённые вопросы и одно следующее действие.
7. При фразе «Продолжим `<Service>.Model`» или «Что дальше по `<Service>.Model`?» сначала восстанови только названную карточку применения, затем продолжай с сохранённого следующего шага.

## Последовательность

### 1. Составить паспорт

Определи:

- `<Service>`;
- имя проекта и namespace `<Service>.Model`;
- путь к solution или место проекта;
- target framework;
- отсутствие project references и сторонних packages по умолчанию.

Не спрашивай на этом этапе EF, approach, СУБД и provider.

### 2. Создать пустую библиотеку

- Создай только согласованный проект.
- Не добавляй модели по умолчанию.
- Проверь ссылки, packages и сборку.
- Создай или обнови связанную задачу и карточку применения по действующим правилам vault.

Если точное место карточки применения ещё не согласовано, предложи его Parad до создания нового соглашения о структуре.

### 3. Добавлять DomainObject из чата или файла

Источник может описывать один или несколько объектов в любом читаемом формате. Перед генерацией покажи для каждого объекта:

- имя класса;
- поля, типы, defaults и комментарии;
- добавленный по умолчанию `string`;
- обязательное поле `Code`;
- планируемую папку, основной и парный классы;
- все неоднозначности.

Применяй согласованный именованный шаблон `DomainObject` из документа обсуждения:

- папка `<Имя>`;
- `<Имя>.cs`;
- `<Имя>s.cs`;
- namespace `<Service>.Model`;
- `Code` всегда присутствует и является логическим ключом;
- отсутствующий тип означает `string`;
- конструктор явно инициализирует все поля;
- `Equals` и безопасный `GetHashCode` строятся по `Code`;
- полный парный класс всегда содержит `FromEnumerable`, `CurrentItem`, `CurrentChanged` и `TotalCount`.

Для типов, defaults, комментариев или конфликтов имён, правила которых ещё не согласованы, не придумывай решение: покажи вопрос Parad.

### 4. Находить request/response по назначению

По фразе «найди тип данных для `<назначение>`»:

- предложи прямые и близкие варианты;
- покажи точные классы, полноту пары, зависимости и исходную папку;
- объясни различия;
- предложи выбрать;
- ничего не добавляй до выбора.

Выбранная пара переносится без изменений, кроме namespace по контексту. Связанные типы не добавляются автоматически.

### 5. Предлагать наборы стандартной функциональности

Распознавай только точные согласованные упоминания:

- `SignalR`;
- `Claim` или `Claims`;
- `JwtService` или `Jwt`;
- `ValidationStartupFilter` или `StartupFilter`;
- `Urls`.

Покажи фактические файлы и точный путь из каталога исторического примера. Само упоминание ничего не добавляет.

Перед переносом классифицируй содержимое. SignalR hubs и repositories, `JwtService` и `StartupFilter` являются технологической реализацией и по умолчанию не входят в чистую `<Service>.Model`. `Claim`, `Urls` и новые кандидаты оценивай по фактическому коду; не делай вывод только по имени.

### 6. Завершить библиотеку

Проверь:

- успешную сборку;
- project references и package references;
- namespace и структуру папок;
- обязательный `Code` и парный класс каждого `DomainObject`;
- явную инициализацию;
- отсутствие технологического кода;
- актуальность карточки применения.

Зафиксируй завершение `<Service>.Model` и назови один следующий архитектурный этап. Не создавай следующий проект без запроса Parad.

## Поддержка инструкции

Если Parad согласовала изменение процесса или шаблона, синхронно обнови:

1. `Wiki/HowToDo/Create Project Domain Model by Step.md`;
2. этот файл;
3. текущую карточку задачи или применения, если правило влияет на неё.

Не изменяй инструкции на основании только предложения или предположения Машины.

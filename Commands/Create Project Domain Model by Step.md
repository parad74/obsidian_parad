# Create Project Domain Model by Step

При создании и дополнении объектов используй [[Commands/Create Data Objects by Step]] для определения состава по запросу и существующему коду; слова «по кубику» не обязательны. Сначала подготовь Excel, дождись его проверки и возврата Parad, затем создай весь запрошенный комплект классов одним проходом: по умолчанию в Model и ExportImport, а при явно ограниченном запросе — только в названном проекте или составе. Отдельного подтверждения каждого класса, объекта или этапа после утверждения Excel не требуется. 11 последовательностей служат примерами и не расширяют запрос автоматически.

## Назначение

Эта рабочая инструкция применяется, когда Parad просит создать, продолжить или наполнить независимую библиотеку общих контрактов данных приложения, спрашивает следующий шаг для `<Service>.Model` либо использует близкую по смыслу формулировку.

Пользовательская инструкция и источник текущего процесса:

- `Wiki/HowToDo/Create Project Domain Model by Step.md`.

Точные согласованные шаблоны и каталог исторических примеров:

- `Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md`;
- `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared`.

Перед практическим действием полностью прочитай пользовательскую инструкцию и только необходимые разделы документа с точными шаблонами. Исторический проект исследуй точечно; не загружай и не переноси его целиком.

## Результат

Создать и последовательно наполнить проект `<Service>.Model`, который представляет чистый контракт внутренних данных приложения и может использоваться всеми более высокими слоями решения.

По умолчанию `<Service> = Monitor`, поэтому первый вариант называется `Monitor.Model` и использует namespace `Monitor.Model`.

Имя сервиса `<Service>` выбирается при создании `<Service>.Model` и задаёт общий префикс связанных проектов и namespaces. При последующем создании EF-проекта используй это же имя сервиса для `<Service>.<DataStore>.<Approach>` и `<Service>DbContext`. Имя БД выбирается отдельно на этапе доступа к данным и не переопределяет `<Service>`: для `Inventory.Model` БД `WarehouseDb` сохраняет префикс `Inventory` и контекст `InventoryDbContext`.

## Состав solution

При старте создания solution с ExportImport, до создания проектов, отдельно определи имя сервиса и имя БД. Если имя БД не указано и не было согласовано для этого применения, обязательно спроси Parad; не выводи его из имени сервиса и не подставляй `<Service>Db` по умолчанию. Для SQLite отдельно определи имя/путь файла в строке подключения: если они не заданы, спроси, не подставляй `command.db` или имя сервиса автоматически. Логическое имя БД и файл могут различаться. Задавай по одному вопросу с вариантами и возможностью своего ответа; уже заданное не спрашивай повторно. В стартовой сводке покажи эти значения раздельно. Для запроса только Model без БД эти вопросы не нужны.

Для запроса создать `<Service>.Model` базовый состав — Model и SelectParam. Для запроса создать `<Service>.Model.Sqlite.CodeFirst.ExportImport` базовый состав — три проекта: ExportImport, Model и SelectParam. Новый автономный solution называй именем сервиса, выбранным в начале: `<Service>.sln`. Имя БД и имя ExportImport-проекта это имя не меняют. Если необходимого проекта нет, создай или подключи его в рамках запрошенной работы. Эти составы не задают общий запрет включать другие проекты в solution; ограничения `ProjectReference` конкретной библиотеки описывают её зависимости, а не членство проектов в solution.

В рабочем репозитории приложения `Service.Model.EF.SelectParam` должен находиться как скопированный проект с исходным кодом, а не как ссылка на checkout `Sources/Architectures` и не как опубликованный пакет. Если проекта ещё нет в рабочем репозитории, скопируй `.csproj` и исходники эталона из `Sources/Architectures/LibProject/netstandard2.0/SelectParam/` без его отдельного `.sln`, `bin`, `obj` и чужих Git-метаданных, включи проект в `<Service>.sln` и добавь `ProjectReference` во все проекты solution, где фактически используются типы `SelectParam`. Если проект уже присутствует, используй существующую локальную копию и не создавай дубликат. Проектам, не использующим `SelectParam`, ссылку не добавляй.

Запрос создать `<Service>.Model.<DataStore>.CodeFirst.ExportImport` означает создание готового стартового solution по образцу, а не пустой инфраструктурной оболочки. В `<Service>.Model` включаются готовые `CommandResult`/`CommandResults`, необходимые перечисления и пять интерфейсов. В ExportImport для `CommandResult` создаются или адаптируются `Entity`, Fluent-конфигурация, `DbSet` в `<Service>DbContext`, MappingEF и EF-репозиторий; интерфейс репозитория находится в Model. Этот стартовый комплект переносится без повторного согласования состава `CommandResult`. Гибкий выбор этапов кубика применяется к последующему созданию и дополнению других объектов и не сокращает стартовый комплект нового ExportImport solution. Тестовые проекты и автоматизированные тесты на текущем этапе не создаются.

## Параметры по умолчанию и совместимость

Для нового применения сначала используй явно указанные или ранее согласованные параметры, а для неуказанных бери соответствующие значения первого образца из раздела «Параметры по умолчанию» пользовательской инструкции. Для Model это `netstandard2.0` и `System.ComponentModel.Annotations` 4.7.0 вместе с готовым образцом; при отдельном запросе EF-проекта — `netcoreapp3.1`, EF Core 3.1.9, SQLite, Code First, `Microsoft.EntityFrameworkCore.Sqlite` 3.1.9 и `Microsoft.Extensions.Logging` 3.1.9.

При добавлении нового проекта в существующий solution также исходи из первого образца. Покажи краткую сводку применяемых параметров и проверь совместимость; при несовместимости покажи конкретный конфликт и спроси Parad до создания зависящего от него проекта. Не заменяй версии автоматически версиями других проектов solution и не обновляй их самостоятельно. Явно выбранная другая СУБД или EF требует соответствующего проверенного провайдера. Это правило определяет параметры запрошенного шага и не создаёт команду «сделай всё»; существующие проекты не перенастраиваются по defaults нового проекта.

## Сборка, migrations и создание БД

После создания стартового solution собери его. Если сборка успешна, сообщи Parad, что solution собирается, с фактическим результатом сборки. Если сборка не прошла, не переходи к migrations и БД до устранения относящихся к созданному решению ошибок. Отдельные тестовые проекты и автоматизированные тесты на текущем этапе не создавай.

После успешной сборки проверь готовность выбранного EF-профиля к design-time-командам: наличие совместимого инструмента, необходимых design-time packages и способа создать `<Service>DbContext`. Не добавляй отсутствующие packages или фабрику контекста молча; покажи недостающее изменение и получи согласие Parad.

Когда профиль готов, выдай Parad две точные команды с фактическими путями, проектом, startup project и контекстом: сначала создание migration `InitialCreate`, затем применение migrations для создания отсутствующей БД. Для EF Core это соответственно `dotnet ef migrations add InitialCreate ...` и `dotnet ef database update ...`; для EF6 — команды выбранного поддерживаемого инструмента `Add-Migration InitialCreate` и `Update-Database`. Покажи рабочую папку и полный набор параметров, а не только сокращённые имена команд.

По умолчанию только покажи команды. Машина может выполнить каждое действие сама по отдельному явному запросу Parad. Создание migration изменяет исходники, а применение migration создаёт или изменяет БД, поэтому это два раздельных действия. Перед применением проверь целевое подключение и наличие БД; существующую БД без отдельного явного разрешения не обновляй. После создания `InitialCreate` и отсутствующей БД проверь, что БД создана, migration применена и ожидаемая схема присутствует, затем сообщи результат Parad.

## Инварианты

- `Service.Model.EF.SelectParam` находится внутри рабочего репозитория приложения. `ProjectReference` на него добавляется в каждый проект, где используются его типы; в стартовом комплекте такие ссылки нужны Model для интерфейсов с `SelectParams` и ExportImport для реализации выборки. Проектам без использования `SelectParam` ссылка не добавляется. Другие ссылки на проекты по умолчанию не добавляются.
- В собственном коде Model нет EF-реализации, Entity, DbContext, migrations и provider-specific реализации; соответствующие выбранные этапы выполняются в проекте доступа к данным.
- В проекте нет ASP.NET-, SignalR-, frontend- и другой инфраструктурной реализации.
- Прямой NuGet-пакет по умолчанию — `System.ComponentModel.Annotations` 4.7.0 для атрибутов `[Display]` перечислений готового образца. Другие прямые пакеты без необходимости не добавляются; зависимости `SelectParam` сохраняются как в первом образце и учитываются отдельно при проверке сборки.
- Разрешены стандартные типы выбранного target framework и операции, принадлежащие самой модели и не зависящие от внешней технологии.
- Семейство EF (EF6 или EF Core), версии, СУБД и совместимый провайдер определяются для проекта доступа к данным; текущий подход — Code First. Создание Model само по себе не требует выбора EF.
- При последующем запросе ExportImport не ограничивай выбор СУБД примерами `SQLite` и `MSSQL`. Для СУБД вне текущего каталога сначала проверь в актуальной документации наличие провайдера для запрошенного семейства `EF Core` или `EF6`, точное имя и версию пакета, совместимость с EF, .NET и СУБД, а также поддержку выбранного подхода и операций со схемой. Покажи источники и подтверждённые параметры перед созданием проекта; при отсутствии совместимого провайдера предложи варианты и уточни решение Parad. Для `<Service>.Model` этот поиск не нужен.
- Исторические исходники не изменяются.
- При создании проекта добавь готовый образец `CommandResult`/`CommandResults` и все пять интерфейсов из исторической папки `Monitor.Service.Shared/Interface`; их namespace — `<Service>.Model.Interface`, а имена с `Monitor` адаптируются под выбранное `<Service>`. `CommandResult` служит образцом стиля кода для Машины при генерации новых классов и для программиста. Повторно не согласовывай состав его полей, перечислений и уже выполненную адаптацию: используй готовый образец из `Sources/Architectures/LibProject/netstandard2.0/Monitor.Model/` и описание в его архитектурной карточке. При включении в новый проект приводи namespaces и ссылки на типы к текущему `<Service>`; имена `CommandResult` и `CommandResults` и готовый состав сохраняй. Другие демонстрационные модели и test data без решения Parad не добавляй. Необходимые проекты и зависимости создавай или подключай в рамках запрошенной работы; общего запрета добавлять проекты в solution нет.
- В готовом образце зависимость от `ICount4uContext` уже исключена и конструктор адаптирован. Используй эту готовую адаптацию и её необходимые перечисления; не восстанавливай исключённые исторические зависимости и не открывай повторное обсуждение перечислений при обычном переносе образца.
- Для первого образца `Monitor.Model` сохраняй поля исторического `CommandResult`, кроме `AdapterType`/`ImportDomainEnum`, `IturCodes`, `DocumentHeaderCodes` и зависимости от `ICount4uContext`. `Files` и `UnsureFiles` в первом образце — строки. `Code` — основное логическое свойство для сравнения объектов; историческое `CommandResultCode` хранит отдельное значение. Сравнение и hash code строятся по `Code`.
- Дополнение существующих объектов определяется запросом и найденным кодом. Используй существующие классы; не создавай пару заново и не запускай не запрошенные части автоматически. При запросе синхронизации поля одним проходом дополни все входящие в запрос Entity, DomainObject, конфигурации и мапперы. Если отсутствует необходимая часть, уточни её путь либо создание до генерации. После возвращения утверждённого Excel отдельные подтверждения по объектам и этапам не требуются. Существующие поля автоматически не удаляются и не переделываются; migrations остаются отдельными запрошенными действиями.
- Никогда автоматически не создавай EF migration после изменения Domain Model и не применяй migration к существующей БД; каждое из этих действий требует отдельного явного запроса Parad либо выполняется вручную Parad. Первоначальное создание отсутствующей БД из заранее подготовленных migrations является отдельным разрешённым сценарием Entity-проекта.

## Стиль интерактивной работы

1. Сначала назови текущий этап, уже известные параметры и один следующий вопрос или действие.
2. Не заставляй Parad помнить последовательность и не выдавай большую анкету, если достаточно одного вопроса.
3. Сначала используй явный выбор Parad, текущий запрос, фактические solution/проекты и существующую рабочую задачу, если она есть; для неуказанных параметров нового проекта покажи defaults первого образца. Существующий solution используй для определения контекста и проверки совместимости; другие версии его проектов не подставляй автоматически. При несовместимости спроси Parad.
4. При добавлении DomainObject или Entity из входных данных до изменения кода подготовь Excel с разбором всех классов: имена, поля с типами, defaults, ограничения, вопросы и планируемые проекты. Дождись, пока Parad проверит, при необходимости исправит и вернёт книгу. Возвращённый утверждённый Excel разрешает создать весь указанный в запросе комплект одним проходом без дополнительных поклассных или поэтапных согласований.
5. Не превращай предложение Машины в правило до явного решения Parad.
6. После каждого выполненного шага при необходимости кратко обновляй существующую рабочую задачу или свои рабочие заметки: выполненное, нерешённые вопросы и одно следующее действие. Отдельную карточку применения и фиксированный формат не создавай.
7. При фразе «Продолжим `<Service>.Model`» или «Что дальше по `<Service>.Model`?» сначала проверь названный solution, проекты, `.csproj`, код и связанную рабочую задачу, если она есть. Этого достаточно для восстановления состояния; отдельный паспорт не требуется.

## Последовательность

### 1. Определить начальные параметры

Определи:

- `<Service>`;
- имя проекта и namespace `<Service>.Model`;
- путь к solution или место проекта;
- target framework: `netstandard2.0` по умолчанию;
- обязательную ссылку на `Service.Model.EF.SelectParam`, отсутствие других project references и пакет `System.ComponentModel.Annotations` 4.7.0 для готового образца по умолчанию.

Не спрашивай на этом этапе семейство EF, подход, СУБД/хранилище и пакет провайдера.

### 2. Создать стартовую библиотеку

- Создай запрошенную библиотеку Model и создай или подключи необходимые проектные зависимости.
- Если `Service.Model.EF.SelectParam` отсутствует в рабочем репозитории приложения, скопируй туда его `.csproj` и исходники из `Sources/Architectures/LibProject/netstandard2.0/SelectParam/` без отдельного `.sln`, `bin`, `obj` и Git-метаданных.
- Включи `<Service>.Model` и локальный `Service.Model.EF.SelectParam` в `<Service>.sln`.
- Добавь `ProjectReference` на локальный `Service.Model.EF.SelectParam` в Model и остальные проекты, где фактически используются его типы.
- Добавь все пять интерфейсов в `Interface`, готовые `CommandResult`/`CommandResults` и необходимые перечисления из текущего образца. Используй их как пример стиля без повторного согласования полей и адаптации; при переносе в новый сервис приводи namespaces и ссылки на типы к текущему проекту.
- Не добавляй другие модели и тестовые данные по умолчанию.
- Проверь ссылки, packages и сборку.
- Создай или обнови связанную рабочую задачу по действующим правилам vault, если практическая работа требует задачи.

Не создавай отдельную карточку или паспорт применения. Обязательного шаблона хранения параметров нет: источником истины служат solution, названия проектов, `.csproj` и код; для собственного удобства Машина может кратко сохранить недостающий рабочий контекст в существующей задаче или рабочих заметках.

### 3. Добавлять DomainObject из чата или файла

Источник может описывать один или несколько объектов в любом читаемом формате. Перед генерацией покажи для каждого объекта:

- имя класса;
- поля, типы, defaults и комментарии;
- предлагаемый тип, если во входе тип отсутствует, с объяснением для согласования в Excel;
- обязательное первое поле `ID long` и обязательное поле `Code`;
- планируемую папку, основной и парный классы;
- все неоднозначности.

При создании объектов из описания сначала верни разобранную модель в Excel для проверки Parad. Продолжай только по возвращённой и утверждённой книге; нерешённые вопросы уточни до генерации. Возвращённый Excel подтверждает описанную в нём модель: после него создай все классы согласованного объёма одним проходом в обоих проектах либо, если Parad ограничила запрос, только в названном проекте или составе. Не вводи дополнительных подтверждений для каждого объекта, класса или этапа. Обязательные поля должны быть явно видны в Excel.

Готовый `CommandResult` используй как образец оформления и реализации класса. Его предметные поля и перечисления не становятся обязательными полями каждого нового DomainObject: состав нового класса определяется входными данными и общими правилами шаблона. Разбор новых классов согласуется в Excel; после возврата книги отдельное подтверждение кода каждого класса не требуется.

Применяй согласованный именованный шаблон `DomainObject` из документа согласованных решений:

- папка `Domain/<Имя>`;
- `<Имя>.cs`;
- `<Имя>s.cs`;
- namespace `<Service>.Model`;
- `ID` всегда присутствует как первое объявленное свойство `public long ID { get; set; }`; если его нет во входе, добавь без отдельного вопроса, если есть корректное `ID long` — не дублируй;
- в парном `Entity` первое свойство также `long ID`; `ID` является первичным ключом таблицы и явно задаётся в EF-конфигурации;
- `Code` всегда присутствует и является логическим ключом сравнения, а не первичным ключом БД;
- отсутствующий тип обычного поля предложи при разборе и согласуй в Excel; обязательное ID всегда имеет тип long;
- конструктор явно инициализирует все поля, включая `ID = 0`;
- `Equals` и безопасный `GetHashCode` строятся по `Code`;
- полный парный класс всегда содержит `FromEnumerable`, `CurrentItem`, `CurrentChanged` и `TotalCount`.

Если описание полей нового DomainObject отсутствует целиком, покажи в Excel минимальный набор шаблона: `long ID`, `string Code`, `string Name`, `string Description`, `string Tag`. Это не замена полей предоставленного описания и не сокращение готового стартового `CommandResult`. Базовая явная инициализация в конструкторе — `0` для `int`/`long` и `""` для `string`; заданные источником или предлагаемые отличия отражай в Excel отдельно от DB defaults.

Все `DomainObject`, создаваемые из описания в чате или файле, предназначены для хранения в БД. Не спрашивай для каждого объекта, нужно ли сохранять его в БД. Папка `Domain` является границей последующей генерации `Entity`; типы, находящиеся вне неё, автоматически не преобразуются.

Дополнение существующих объектов определяется запросом и найденным кодом. Используй существующие классы; не создавай пару заново и не запускай не запрошенные части автоматически. При запросе синхронизации поля одним проходом дополни все входящие в запрос Entity, DomainObject, конфигурации и мапперы. Если отсутствует необходимая часть, уточни её путь либо создание до генерации. После возвращения утверждённого Excel отдельные подтверждения по объектам и этапам не требуются. Существующие поля автоматически не удаляются и не переделываются; migrations остаются отдельными запрошенными действиями.

Для неуказанных типов и defaults предложи вариант при разборе Excel, отличая его от исходных сведений. Конфликты имён, смысл полей и предметное поведение согласуй с Parad до генерации. Внутреннюю организацию реализации выбирай по читаемости и единому смыслу операций в рамках уже согласованных правил.

### 4. Находить request/response по назначению

Этот раздел относится к готовым HTTP request/response-контрактам вне `Domain` и не изменяет правила цепочки объектов из Excel. Для утверждённой Excel-модели без явного ограничения этапов выполняется полная цепочка DomainObject с коллекцией → Entity с конфигурацией и DbContext → MappingEF → Repository с интерфейсом. При точечном запросе выполняются только прямо названные этапы или типы.

По фразе «найди тип данных для `<назначение>`»:

- предложи прямые и близкие варианты;
- покажи точные классы, полноту пары, зависимости и ссылки на конкретные исходные файлы в `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared`;
- объясни различия;
- предложи выбрать;
- ничего не добавляй до выбора.

Выбранная request/response-пара переносится без изменений, кроме namespace по контексту. Необходимые связанные базовые типы показывай отдельно и добавляй только по прямому запросу или отдельному выбору Parad; сама просьба добавить пару не разрешает перенос остальных связанных типов.
Опциональные типы, включая `Login`, `EmailSender` и другие сохранённые примеры, добавляй в `<Service>.Model` только по запросу Parad. Размещай выбранную пару в её собственной папке по назначению; не собирай разные типы в один общий файл. После добавления покажи точные целевые файлы и ссылки на исходники; при необходимости сохрани их в существующей рабочей задаче.
Если Parad просит показать, как использовать тип, найди фактический пример его применения в старом коде и дай ссылки на исходный файл типа и файл с примером вызова. Каталог полных пар и непарных типов находится в `Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md`.

### 5. Предлагать наборы стандартной функциональности

Распознавай только точные согласованные упоминания:

- `SignalR`;
- `Claim` или `Claims`;
- `JwtService` или `Jwt`;
- `ValidationStartupFilter` или `StartupFilter`;
- `Urls`.

Покажи фактические файлы и точный путь из каталога исторического примера. Само упоминание ничего не добавляет.

Перед переносом классифицируй содержимое. SignalR hubs и repositories, `JwtService` и `StartupFilter` являются технологической реализацией и по умолчанию не входят в чистую `<Service>.Model`. `Claim`, `Urls` и новые кандидаты оценивай по фактическому коду; не делай вывод только по имени.

### 6. Завершить библиотеку

Проверь:

- успешную сборку;
- наличие локального проекта `Service.Model.EF.SelectParam` в рабочем репозитории и solution, а также `ProjectReference` во всех использующих его проектах и отсутствие такой ссылки в неиспользующих проектах;
- namespace и структуру папок;
- обязательное первое свойство `ID long`, обязательный `Code` и парный класс каждого нового `DomainObject`;
- явную инициализацию;
- отсутствие технологического кода;
- возможность определить фактическое состояние по solution, проектам, `.csproj` и коду; рабочие заметки проверяй только там, где они использовались;

Зафиксируй завершение `<Service>.Model` и назови один следующий архитектурный этап. Состав создаваемых и подключаемых проектов определяется запросом и необходимыми зависимостями; общего запрета добавлять следующий проект в solution нет.

## Согласованные правила развития и вычитки

Таблицы этой архитектуры независимы. Повторы Code допустимы; поведение согласуется по операциям проекта, без универсального выбора минимального ID. Достаточно описанные дополнительные методы реализуются, неизвестное поведение оставляется явно обозначенной заглушкой. Подробности: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

После создания согласованного комплекта показывай итоговые файлы/классы целиком для вычитки. Перед классом и новыми/изменёнными членами ставь комментарии с датой генерации и статусом вычитки. Новый код требует Full, изменение ранее вычитанного — проверки Changes с отметкой участка; ранее невычитанное не считается прочитанным. Read ставится только по проверке Parad; возврат Excel сам по себе не означает вычитку кода. Рабочий формат: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Показ кода и отметки вычитки]].

# Add Code First Fields by Step

Для определения состава и входов используй [[Commands/Create Data Objects by Step]]. Карта ответственности: [[Documents/Architectures/Data Model Harness]].

## Когда применять

Применяй эту команду, когда Parad просит создать Code First `Entity`, добавить поля в существующий `Entity`, уже добавила свойство в `Entity` и просит довести изменение до конца либо передала описание полей или схемы БД в чате или файле. Источник может быть C#, SQL, JSON, таблицей, CSV, Excel, Markdown или другим доступным для чтения форматом. Один источник может описывать несколько объектов и полей.

Границы выбранных этапов определяет [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]]. Контракт новых DomainObject — [[Documents/Architectures/LibProject/netstandard2.0/Monitor.Model#Контракт новых DomainObject]]; единичные объекты и коллекции — [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Единичный объект и коллекция]]. Если источник задаёт другой тип ID или другой PK, покажи конфликт; существующее поле или ключ автоматически не переделывай.

## Разбор и подтверждение

До реализации выполняются [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Источники данных и нормализация]] и [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]]. Эта команда описывает реализацию уже выбранных частей, а не расширение запроса.

## Граница действия

- Добавляй только новые поля. Не удаляй, не переименовывай и не меняй тип, длину, nullable, значение по умолчанию или другую настройку существующего поля. Parad изменяет и удаляет существующие поля вручную.
- Если указанное для добавления поле уже есть в `Entity`, но отсутствует в `DomainObject` или маппере, дополни только недостающие части. Добавь его явную конфигурацию, если это новое поле текущего прохода. Не переписывай само свойство `Entity` и не добавляй конфигурации ко всем историческим полям только потому, что EF отображает часть из них по соглашениям.
- Если описание противоречит существующему полю, оставь его без изменений и покажи расхождение в разборе. Независимые новые поля добавляй только после согласия Parad на показанный набор; не считай отсутствие ответа разрешением на частичную запись.
- На старте Entity соответствует свойствам DomainObject без `[NoEntity]`; позднее согласованные бизнес-правила могут задать различия. Сохраняй явно описанный маппинг и назначение каждого свойства; не выравнивай существующие модели автоматически.
- Не создавай migration и не применяй её к БД в рамках добавления полей. Для каждого действия с migration нужен отдельный явный запрос Parad. Не изменяй старые исходники в `Sources/old/`.
- Дополнительные методы могут быть описаны в файле или интерфейсе. Если поведения достаточно, реализуй метод в общем проходе и покажи итоговый класс для вычитки. Если известна только сигнатура, предложи явно обозначенную заглушку и уточни поведение до генерации зависящего кода. Согласование интерфейса отдельно от уже согласованной функции не требуется.

## Как найти данные без лишних вопросов

1. Найди по названному solution, проекту или файлу `Entity`, парный `DomainObject`, `<Имя>Configuration.cs`, `MappingEF/<Имя>Mapper.cs`, `RepositoryEF/<Имя>EFRepository.cs`, `<Service>.Model/Interface/I<Имя>Repository.cs` и связанную карточку архитектуры. Если путь не назван, используй текущую задачу и фактические `ProjectReference`; не выбирай между несколькими возможными проектами наугад.
2. Прочитай переданный источник целиком в относящейся к запросу части. Не изменяй входной файл только ради извлечения полей. Если Parad уже изменила `Entity`, сравни его свойства с парным `DomainObject`, конфигурацией и маппером. Сопоставляй и имена свойств, и явно заданные имена столбцов, чтобы не создать второй кодовый доступ к уже существующему столбцу.
3. Составь краткую нормализованную таблицу: `Entity`, новое свойство, CLR-тип в `Entity` и `DomainObject`, имя и тип столбца, nullable, длина или precision/scale, defaults, источник значения. Отдели прямо заданное от вывода по существующему коду и неизвестного. Сгруппируй результат по классам, подготовь список или код классов с полями и перечисли все файлы будущего добавления; на этом шаге код не записывай.
4. Если тип обычного поля не указан, предложи подходящий по смыслу и согласуй в Excel до генерации. Для новой пары ID имеет тип long и является PK. Длину, nullable, defaults и другие параметры из источника отделяй от предложений; нерешённые вопросы уточняй до записи.
5. После возвращения утверждённого Excel создай все классы и изменения согласованного объёма одним проходом. По умолчанию синхронизируй оба проекта; при явно ограниченном запросе измени только названный проект или состав. После создания покажи итоговые файлы и изменения для вычитки без промежуточных вопросов по каждому объекту или этапу.

Опциональный столбец Excel `Attributes` задаёт атрибуты соответствующего свойства DomainObject. `[NoEntity]` исключает свойство из Entity, конфигурации и всех методов маппера. Формат, перенос атрибутов и обработка конфликтов: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]].

## Один проход добавления

Следующие действия описывают возможные части синхронизации. Выполняй одним проходом только части, входящие в запрос. Отсутствие зависимости требует уточнения до генерации, а не автоматического создания не запрошенного комплекта.

1. На выбранном этапе Entity добавь свойство, если его ещё нет и соответствующее свойство DomainObject не отмечено `[NoEntity]`. Для `[NoEntity]` свойство и конфигурация столбца не создаются. Сохрани namespace, стиль и типы действующего Code First проекта.
2. На выбранном этапе DomainObject добавь свойство по утверждённой модели и действующим бизнес-правилам пары. Добавь атрибуты из `Attributes` перед соответствующим свойством. На старте совпадают свойства без `[NoEntity]`; в развившейся модели учитывай согласованные различия. Инициализацию и копирование дополни по контракту; существующие поля автоматически не меняй.
3. На выбранном этапе Entity для сохраняемых свойств без `[NoEntity]` дополни единственный файл конфигурации объекта, используя API выбранного семейства/версии EF. Укажи только известные или согласованные параметры столбца, nullable, длину, precision/scale и DB default. Схемные Data Annotations в Entity не добавляй; реляционные связи между таблицами в этой архитектуре не создаются.
4. На выбранном этапе MappingEF обнови маппер: покажи перенос нового сохраняемого поля в согласованных направлениях. Свойства с `[NoEntity]` не добавляй ни в один метод маппера. Если нужного маппера нет, уточни его путь либо создание. При различии типов используй согласованное преобразование и проверь его поведение.
5. Проверь зависимые участки по фактическому коду. Интерфейс и реализацию репозитория создавай или дополняй, когда Repository включён в состав работы; новая пара сама по себе не запускает этот этап.

Поле, присутствующее во входном файле и уже полностью реализованное, пропускай. Неподдерживаемый или неоднозначный тип, связь либо конфликт оставляй отдельным нерешённым пунктом; выполняй только однозначные добавления из подтверждённого Parad набора.

## Обязательный шаблон MappingEF

На выбранном этапе MappingEF создавай отдельный MappingEF/<Имя>Mapper.cs для пары DomainObject/Entity. Используй namespace EF-проекта <Service>.<DataStore>.<Approach> и адаптируй RoomMapper из [[Documents/Architectures/Data Model Examples]] к выбранным семейству EF, модели и правилам проекта.

Во всех методах маппера свойства DomainObject с `[NoEntity]` исключаются по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. В каждом маппере нужны четыре метода:

1. `ToDomainObject(this Entity entity)` — null → null, иначе перенос по согласованному отображению; стартовый шаблон переносит сохраняемые свойства без `[NoEntity]`, последующие бизнес-различия обрабатываются явно.
2. `ToSimpleDomainObject(this Entity entity)` — сокращённое представление с определённым проектом составом (например, Code, Name, Description). До определения состава допустим NotImplementedException. При достаточном описании реализуй; отдельно проверь пригодность для выполнения через выбранный LINQ-провайдер.
3. `ToEntity(this DomainObject domainObject)` — null → null, иначе новый Entity по согласованному отображению, включая ID; вычисляемые свойства и иные поздние бизнес-различия не переносятся в БД автоматически.
4. `ApplyChanges(this Entity entity, DomainObject domainObject)` — перенос свойств, не имеющих атрибута `[NoEntity]`, в существующий `Entity`. Атрибут проверяется у исходного свойства DomainObject; отмеченное свойство исключается из Entity и всех методов маппера, а не только из `ApplyChanges`. Для остальных свойств учитывай согласованное отображение и преобразования. ID существующей Entity сохраняется: ApplyChanges не присваивает ему ID входного DomainObject. Это сохраняет технический ID при обоих способах обновления; ToEntity переносит ID отдельно при создании нового объекта. Полная политика — [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

Общий extension `CutLength` из старого маппера храни один раз в `MappingEF/StringLength.cs`, в namespace EF-проекта. Он удаляет крайние пробелы и обрезает строку до указанной длины. Вызывай его для конкретного поля только по явному правилу Parad или источника, не для всех полей с `HasMaxLength` автоматически.

## Обязательный шаблон RepositoryEF

На выбранном этапе Repository создай `I<Имя>Repository.cs` в папке `Interface` проекта `<Service>.Model` и `<Имя>EFRepository.cs` в папке `RepositoryEF` EF-проекта. Реализация возвращает наружу `DomainObject` и его парную коллекцию `<Имя>s`, а работу с `Entity` и `MappingEF` оставляет внутри EF-проекта. Для новой пары используй `long` в параметре UpdateById и для возвращаемого `ID` вставленной записи (сохраняя `Task<long>` для асинхронной сигнатуры). Для уже существующего объекта с другим типом `ID` сохраняй его текущие сигнатуры и показывай расхождение с правилом нового шаблона; не меняй существующий ключ автоматически. Имена методов образуются от имени объекта; типовой набор:

| Метод | Поведение |
| --- | --- |
| `Get<Имя>s()` | Получить все записи и вернуть `<Имя>s` с `TotalCount`. |
| `Get<Имя>s(SelectParams)` | Фильтрация, сортировка, paging и `TotalCount` до paging через `BaseEFDbSetRepository` и `SelectParam`. |
| `Get<Имя>ByCode(string code)` | Одиночное чтение по политике Code. |
| `Insert(<Имя>)` | Добавить запись по политике вставки и вернуть сгенерированный ID. |
| `Insert(<Имя>[])` | Добавить массив записей. |
| `Update(<Имя>)` | Сокращение для обновления по Code входного объекта. |
| `UpdateById(long id, <Имя>)` | Обновление по отдельному ключу ID. |
| `UpdateByCode(string code, <Имя>)` | Обновление по отдельному ключу Code. |
| `DeleteByCode(string code)` | Удаление по Code; сокращение — Delete(string code). |
| `DeleteAll()` | Удалить все записи этого Entity. |

Точная семантика этих методов, повторных Code, отсутствия записи и сохранения технического ID имеет один источник: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]]. При реализации и проверке прочитай этот раздел полностью.

Сохраняй асинхронные `Task` и синхронные сигнатуры по образцу `RoomEFRepository` из [[Documents/Architectures/Data Model Examples]], если конкретное применение не задаёт другое. `GetTestData<Имя>s()`, выборки по `ParentCode`, другим кодам и любые специфичные запросы в типовой набор не входят; существующие методы сохраняй.

Если Parad передала описание или интерфейс, восстанови сигнатуры и поведение. Достаточно определённые методы реализуй в общем проходе и покажи итоговый класс для вычитки. Неопределённое поведение оставь явной заглушкой и вопросом; не выдавай такую операцию за готовую. Чтение/удаление по ID и специфичные методы не входят в новый типовой набор; существующие сигнатуры сохраняются для совместимости. UpdateById входит в типовой набор наряду с UpdateByCode.

`RepositoryEF/PaginatedList.cs` создавай один раз на EF-проект, а не на каждый Entity. Адаптируй namespace исторического `PaginatedList<T>` к namespace EF-проекта. Он остаётся общим примером; типовая выборка продолжает использовать `SelectParams` и `<Имя>s.TotalCount`.

## Проверка и результат

- Проверь, что созданные и дополненные файлы соответствуют подтверждённому разбору по классам; неподтверждённые части не записаны.

- На старте сравни имена свойств Entity и DomainObject, исключив из сравнения свойства DomainObject с `[NoEntity]`; для поздних согласованных различий проверь явное отображение/обработку. Проверяй перенос добавленных сохраняемых полей по контракту, а не механическое копирование любого нового свойства во все слои.
- Для новой пары проверь первое свойство ID long и назначение PK; сигнатуры репозитория должны соответствовать интерфейсу. Методы с определённым поведением реализованы, неизвестное поведение явно обозначено; политика Code соответствует проекту. Общий PaginatedList не дублируется.
- Собери целевой solution и сообщи фактический результат. Автоматизированные тесты на текущем этапе не создавай и не требуй. Непроверенное поведение преобразований укажи явно; успешная сборка сама по себе его не подтверждает. После отдельно запрошенного применения migration проверь БД, migration history и ожидаемую схему.
- Обнови текущую карточку задачи или применения: источник данных, добавленные поля и файлы, пропущенные конфликты, результат сборки и необходимость будущей migration.
- Сообщи Parad, что добавлено, что осталось неясным и что схема существующей БД не менялась. Следующий шаг с migration называй отдельно.

Пример запроса: «Добавь в `CommandResult` поля из этого файла» или «Я добавила `StatusText` в `Entity CommandResult`; доведи поле до `DomainObject`, конфигурации и маппера».

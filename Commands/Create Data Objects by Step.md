# Create Data Objects by Step

## Когда применять

Применяй при создании и дополнении DomainObject, Entity, MappingEF и Repository по запросу Parad, независимо от упоминания кубика. Состав работы определяется запросом Parad и фактическим состоянием проекта: названные части создаются или дополняются, существующие части используются без дублирования. 11 последовательностей кубика — примеры, а не закрытый список команд. После возвращения утверждённого Excel весь запрошенный комплект создаётся одним проходом: по умолчанию в Model и ExportImport, а при явно ограниченном запросе — только в названном проекте или составе. При недостающих зависимостях уточни существующие пути либо расширение состава до генерации. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]].

Полная цепочка по умолчанию относится к объектам утверждённой Excel-модели. Явно ограниченный запрос выполняется только в названном составе. Готовые request/response-контракты вне `Domain` этой командой автоматически не добавляются.

Сначала прочитай [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]] и необходимые источники шаблонов. Общий процесс разбора и согласования сочетается с гибким составом этапов; не подгоняй запрос под одну из 11 формулировок.

## Выполнение

1. Определи источник, перечисленные Parad части работы и уже существующие объекты. При отсутствии указанного состава предложи цепочку по умолчанию; она выполняется после утверждения Excel. При неоднозначном запросе уточни состав. Запрос только Entity включает Entity, конфигурацию и подключение к DbContext. Если необходимый исходный файл не указан и не определяется однозначно, запроси путь.
2. Прочитай источник, подготовь нормализованную модель и Excel с опциональным столбцом `Attributes` для проверки по правилам [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]]. Дождись возвращённой и утверждённой книги до генерации; сохрани отличия исходных данных и предложений, defaults и неизвестные сведения. Для дополнения используй существующий код и согласованный объём изменений.
3. Восстанови существующие классы, проекты и пути из запроса, фактических solution/`.csproj`/кода, существующей рабочей задачи и ссылок. Спроси все необходимые недостающие или неоднозначные пути до папок и файлов до генерации. Не выдумывай целевой проект или базовые классы. При отсутствии необходимых зависимостей спроси: указать существующие файлы или расширить состав? Зафиксируй выбранные пути либо обновлённый состав; не расширяй его молча.
4. Определи выбранные этапы и технологии. Перед созданием проектов необходимые незаданные параметры спроси по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]: предложенный вариант образца или свободный ввод. При несовместимости уточни решение; не переписывай существующие версии и классы ради образца. Отдельный паспорт не создавай; дополнительный контекст при необходимости храни в существующей задаче или рабочих заметках.
5. После возвращения утверждённого Excel создай все объекты и файлы выбранного состава одним проходом. По умолчанию создай согласованные классы в Model и ExportImport; при прямо ограниченном запросе работай только в названном проекте или составе. Существующие части используй или дополняй без дублирования. DomainObject включает коллекцию; Entity — конфигурацию и подключение к DbContext; Repository — интерфейс и реализацию.
6. Проверь результат, собери затронутый solution, сообщи созданные и изменённые файлы и покажи итоговый код для вычитки. Не спрашивай отдельное разрешение перед каждым классом, объектом или этапом и не запускай исключённые из запроса части.

## Обязательные правила

- Новые DomainObject и Entity: первое свойство `long ID`, PK БД; обязательный Code остаётся логическим ключом сравнения.
- DomainObject всегда имеет полную парную коллекцию; при сценарии от Entity она также создаётся на этапе DomainObject.
- Проекты, namespaces и новый solution именуются по выбранному сервису; контекст — `<ИмяБД>Context` по выбранному логическому имени БД.
- Готовый CommandResult задаёт стиль, а не предметные поля всех новых классов.
- Атрибуты из `Attributes` переносятся на свойства DomainObject; `[NoEntity]` исключает свойство из Entity, конфигурации и всех методов маппера. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]].
- Существующие поля не удаляются и не изменяются автоматически; согласованные дополнения не дублируются.
- Migrations не создаются и не применяются автоматически.
- Нельзя объявлять все сценарии или провайдеры проверенными без фактического применения.

## Возобновление

При продолжении проверь фактические solution, `.csproj`, код, существующую рабочую задачу и заметки, если они использовались. Восстанови утверждённый Excel, согласованный состав и фактически созданные файлы. Не повторяй уже выполненную генерацию; незавершённый согласованный комплект закончи одним проходом.

## Внутренняя организация кода

При внутренней организации кода следуй согласованному ориентиру: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Внутренняя организация кода]]. Приоритет — быстрое чтение и понимание кода Parad. Общие методы выделяются по единому смыслу и контракту, а не только из-за совпадения строк; похожие участки с независимым развитием допустимо оставлять отдельно. Это ориентир, а не жёсткий запрет на повторение или выделение методов.

## Библиотеки и смена версий

Работающие библиотеки и их версии сохраняй, если задача не требует изменения. Предлагаемые Машиной изменения зависимостей сначала объясни и согласуй с Parad. При явно запрошенном переходе проверяй совместимость и сохранение работоспособности. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Библиотеки и смена версий]].

## Улучшение закреплённого паттерна

Машина может предлагать улучшения закреплённого паттерна с объяснением пользы и последствий. Применение требует согласия Parad; решение остаётся локальным для проекта. Общее правило меняется по отдельной просьбе Parad. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Улучшение закреплённого паттерна]].

## Интерфейсы по потребностям задачи

Интерфейсы развиваются по потребностям задачи: согласованную функцию добавляй в подходящий интерфейс и реализацию без отдельного вопроса об интерфейсе. Проверяй вызывающий код и другие реализации при изменении контракта. Итоговый код предоставляй для вычитки после создания всего согласованного комплекта. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Интерфейсы по потребностям задачи]].

## Образец как опора при создании модели

При создании модели сохраняй стартовые CommandResult/CommandResults, необходимые перечисления и все пять интерфейсов как опору Parad, адаптируя их к правилам проекта. Неиспользование не является основанием убрать их на этом этапе. Удаление ненужного выполняется позднее, на этапе бизнес-правил, по отдельному запросу Parad. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Образец как опора при создании модели]].

## Дополнение существующих объектов

Дополнение существующих объектов определяется запросом и найденным кодом. Используй существующие классы; не создавай пару заново и не запускай не запрошенные части автоматически. При запросе синхронизации поля одним проходом дополни все входящие в запрос Entity, DomainObject, конфигурации и мапперы. Если отсутствует необходимая часть, уточни её путь либо создание до генерации. После возвращения утверждённого Excel отдельные подтверждения по объектам и этапам не требуются. Существующие поля автоматически не удаляются и не переделываются; migrations остаются отдельными запрошенными действиями.

## Текущий подход и семейство EF

Текущий процесс — Code First; существующая БД или Entity-модель может служить входом для Excel, затем после утверждения модели применяется обычный процесс. EF6 или EF Core и совместимые версии определяются для конкретного проекта; API и провайдер подбираются соответственно. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Code First и выбор семейства EF]].

## Согласованные правила развития и вычитки

Таблицы этой архитектуры независимы. Повторы Code допустимы; поведение согласуется по операциям проекта, без универсального выбора минимального ID. Равенство состава DomainObject/Entity относится к стартовому шаблону с исключением свойств DomainObject, помеченных `[NoEntity]`; последующие бизнес-различия описываются и отображаются явно. Достаточно описанные дополнительные методы реализуются, неизвестное поведение оставляется явно обозначенной заглушкой. Подробности: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

После создания согласованного комплекта показывай созданные из описания или интерфейса файлы/классы целиком для вычитки. Перед классом и новыми/изменёнными членами ставь комментарии с датой генерации и статусом вычитки. Новый код требует Full, изменение ранее вычитанного — проверки Changes с отметкой участка; ранее невычитанное не считается прочитанным. Read ставится только по проверке Parad. Рабочий формат: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Показ кода и отметки вычитки]].

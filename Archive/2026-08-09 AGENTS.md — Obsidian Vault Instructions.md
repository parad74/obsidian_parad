# AGENTS.md — Obsidian Vault Instructions

Этот каталог является Obsidian Vault.

Codex используется как помощник для работы с заметками, документацией, ТЗ, спецификациями и задачами.

Главные правила:

1. Не повреждать существующую структуру vault.
2. Не изменять файлы в `.obsidian/`, если пользователь явно этого не попросил.
3. Сохранять Markdown, совместимый с Obsidian.
4. Для задач использовать формат, совместимый с плагином **Obsidian Tasks**.
5. Не придумывать отсутствующие сроки, приоритеты, исполнителей или требования.

---

# Tasks

Vault использует плагин **Obsidian Tasks**.

Задача должна быть обычным Markdown checkbox:

```markdown
- [ ] Текст задачи
```

Не создавать задачу как обычный bullet:

```markdown
- Сделать что-то
```

если пользователь явно имеет в виду задачу.

Не использовать `#task` автоматически.

Считать, что Global Task Filter в Obsidian Tasks не настроен, если в vault нет других явных правил.

---

# Создание задач по словам пользователя

Если пользователь использует формулировки:

- "добавь задачу"
- "создай задачу"
- "запиши в задачи"
- "надо сделать"
- "нужно не забыть"
- "напомни сделать"
- "добавь в todo"
- "поставь задачу"

считать это запросом на создание Obsidian Tasks task.

Пример.

Пользователь:

> Добавь задачу проверить договор.

Создать:

```markdown
- [ ] Проверить договор
```

---

# Куда записывать новые задачи

Если пользователь явно указал заметку или файл — добавлять задачу туда.

Например:

> Добавь в проект Alpha задачу проверить API.

Добавить задачу в соответствующую заметку проекта Alpha.

Если пользователь не указал место, использовать:

```text
Tasks/Inbox.md
```

Если папки `Tasks` или файла `Inbox.md` ещё нет — их можно создать.

Не создавать новый файл для каждой маленькой задачи.

---

# Даты

Если пользователь явно назвал deadline или срок выполнения, использовать due date Obsidian Tasks:

```markdown
- [ ] Подготовить отчёт 📅 2026-08-15
```

Использовать формат даты:

```text
YYYY-MM-DD
```

Например:

```markdown
- [ ] Отправить договор 📅 2026-08-20
```

## Относительные даты

Если пользователь говорит:

- сегодня
- завтра
- послезавтра
- в пятницу
- через неделю

преобразовывать это в конкретную дату `YYYY-MM-DD`, если дата однозначно определяется из текущей даты.

Например, вместо:

```markdown
- [ ] Позвонить завтра
```

предпочитать:

```markdown
- [ ] Позвонить 📅 2026-08-10
```

если завтра действительно 2026-08-10.

## Не выдумывать deadline

Если в запросе или исходном документе срока нет:

```markdown
- [ ] Проверить интеграцию
```

НЕ делать:

```markdown
- [ ] Проверить интеграцию 📅 <придуманная дата>
```

# Извлечение задач из ТЗ и спецификаций

Codex может создавать задачи из:

- ТЗ;
- спецификаций;
- требований;
- протоколов встреч;
- проектной документации;
- планов;
- заметок;
- acceptance criteria;
- списков TODO;
- документов с описанием будущих изменений.

При запросах вроде:

> Создай задачи из этого ТЗ.

> Разбери спецификацию и добавь задачи.

> Вытащи todo из документа.

нужно проанализировать документ и выделить **реальные исполнимые действия**.

---

# Что считать задачей в документе

Создавать задачу, если из текста следует конкретное действие.

Например:

Исходный текст:

> Необходимо добавить импорт пользователей из CSV.

Задача:

```markdown
- [ ] Добавить импорт пользователей из CSV
```

Исходный текст:

> Перед сохранением заказа система должна проверять наличие товара.

Возможная задача:

```markdown
- [ ] Реализовать проверку наличия товара перед сохранением заказа
```

Исходный текст:

> Добавить логирование ошибок интеграции и покрыть сценарий тестами.

Лучше разделить:

```markdown
- [ ] Добавить логирование ошибок интеграции
- [ ] Добавить тесты для обработки ошибок интеграции
```

---

# Что НЕ превращать автоматически в задачи

Не превращать в задачи:

- справочную информацию;
- определения терминов;
- описание существующей системы;
- вводный текст;
- примеры;
- историю проекта;
- архитектурные пояснения без требуемого действия;
- уже реализованные возможности;
- утверждения, из которых нельзя уверенно вывести необходимое действие.

Например:

> Система использует PostgreSQL.

Это НЕ задача.

Не создавать:

```markdown
- [ ] Использовать PostgreSQL
```

если документ просто описывает существующее состояние.

---

# Не придумывать требования

При извлечении задач строго отделять:

1. то, что действительно требует документ;
2. разумные технические предположения;
3. идеи Codex.

В Tasks записывать только пункт 1, если пользователь не попросил сделать техническую декомпозицию или предложить дополнительные работы.

Не добавлять самостоятельно:

- новые функции;
- дополнительные API;
- миграции;
- тесты;
- документацию;
- мониторинг;
- рефакторинг;

если необходимость этого не следует из документа или пользователь не попросил провести полноценную техническую декомпозицию.

---

# Декомпозиция

Одна задача должна описывать одно понятное действие.

Плохо:

```markdown
- [ ] Сделать авторизацию, регистрацию, восстановление пароля и тесты
```

Лучше:

```markdown
- [ ] Реализовать авторизацию
- [ ] Реализовать регистрацию
- [ ] Реализовать восстановление пароля
- [ ] Добавить тесты для сценариев аутентификации
```

Но не дробить задачу до бессмысленно мелких технических операций.

Например, обычно НЕ нужно автоматически создавать:

```markdown
- [ ] Создать класс
- [ ] Создать метод
- [ ] Добавить using
- [ ] Сохранить файл
```

---

# Связь задачи с исходным документом

При извлечении задач из конкретной заметки сохранять ссылку на источник.

Например, если источник:

```text
Specifications/Payments.md
```

задача может выглядеть так:

```markdown
- [ ] Реализовать возврат платежа [[Specifications/Payments]]
```

Если существует подходящий заголовок, разрешается использовать ссылку на него:

```markdown
- [ ] Реализовать возврат платежа [[Specifications/Payments#Refund]]
```

Ссылка должна помогать человеку быстро вернуться к контексту задачи.

Не добавлять ссылку, если задача уже находится непосредственно в исходной заметке и источник очевиден.

---

# Изменение исходных ТЗ и спецификаций

По умолчанию не переписывать ТЗ или спецификацию только ради создания задач.

Если пользователь говорит:

> Создай задачи из Specifications/Payments.md

то:

1. прочитать `Specifications/Payments.md`;
2. извлечь задачи;
3. записать задачи в `Tasks/Inbox.md`;
4. добавить к задачам ссылки на исходный документ.

Сам исходный документ оставить без изменений.

Если пользователь явно просит разместить задачи внутри документа — тогда добавить их туда.

---

# Дубли

Перед добавлением задач проверить место назначения на очевидные дубли.

Не создавать вторую практически идентичную открытую задачу.

Например, если уже существует:

```markdown
- [ ] Реализовать импорт CSV
```

не добавлять:

```markdown
- [ ] Сделать импорт из CSV
```

без причины.

Если неясно, являются ли задачи дублями, сохранить существующую задачу и сообщить пользователю о возможном совпадении.

---

# Сроки из документов

Deadline добавлять только когда он явно указан.

Например, из:

> Интеграция должна быть готова к 20 августа 2026 года.

можно создать:

```markdown
- [ ] Завершить интеграцию 📅 2026-08-20
```

Если в документе есть дата встречи, дата документа, дата релиза или другая дата, это НЕ означает автоматически deadline задачи.

---

# Приоритеты

Не назначать приоритет самостоятельно.

Если пользователь или документ явно говорит, что задача критическая, срочная или имеет конкретный приоритет, использовать существующий стиль Tasks в этом vault.

Перед первым добавлением приоритетов найти несколько существующих задач и определить используемый формат.

---

# Повторяющиеся задачи

Если пользователь просит создать повторяющуюся задачу, использовать формат повторения Obsidian Tasks.

Перед созданием первой recurring task проверить существующие recurring tasks в vault и использовать тот же стиль.

Не придумывать периодичность.

---

# Существующие соглашения vault

Перед массовым созданием задач сначала посмотреть:

- `Tasks/`;
- существующие файлы с задачами;
- несколько существующих `- [ ]` задач;
- ближайшие `AGENTS.md`, если они существуют.

Если vault уже использует соглашения для:

- тегов;
- проектов;
- контекстов;
- priority;
- scheduled dates;
- recurring tasks;
- source links;

следовать существующему стилю вместо создания нового.

Более специфичный `AGENTS.md` в дочерней папке имеет приоритет для файлов этой папки.

---

# Работа с большими документами

При анализе большого ТЗ или спецификации:

1. Прочитать весь релевантный документ.
2. Определить основные разделы.
3. Выделить требования, требующие действий.
4. Удалить дубли.
5. Разделить составные действия на разумные задачи.
6. Не потерять ограничения и важные детали.
7. Создать Tasks-compatible Markdown.
8. Добавить ссылки на источник.
9. Не придумывать сроки и требования.

Если задач много, можно группировать их заголовками в `Tasks/Inbox.md`.

Например:

```markdown
## Payments specification

- [ ] Реализовать возврат платежа [[Specifications/Payments#Refund]]
- [ ] Добавить обработку declined payment [[Specifications/Payments#Errors]]
- [ ] Сохранять идентификатор внешней транзакции [[Specifications/Payments#Storage]]
```

# Tasks/Inbox.md

Если файл создаётся впервые, использовать простую структуру:

```markdown
# Inbox

Задачи, созданные вручную или извлечённые Codex из документов.

## Tasks
```

Не добавлять сложную систему категорий без запроса пользователя.

---

# Безопасность vault

Без явного запроса пользователя:

- не удалять заметки;
- не переименовывать существующие заметки;
- не перемещать большие группы файлов;
- не менять `.obsidian/`;
- не переписывать ТЗ;
- не менять завершённые задачи;
- не менять структуру ссылок;
- не изменять frontmatter массово.

При создании задач делать минимально необходимые изменения.

---

# После выполнения

После создания задач кратко сообщить:

- сколько задач создано;
- в какой файл они записаны;
- из какого документа они были извлечены, если применимо;
- были ли пропущены неоднозначные пункты;
- были ли обнаружены возможные дубли.

Пример:

> Создано 7 задач в `Tasks/Inbox.md`.
> Источник: `Specifications/Payments.md`.
> Два описательных пункта не были превращены в задачи, так как не содержат конкретного действия.

---

# Основной принцип

Задачи должны оставаться полезными человеку.

Лучше создать 8 конкретных, подтверждённых исходным текстом задач, чем 25 задач, половина которых является догадками Codex.

Если пользователь явно просит провести более глубокую техническую декомпозицию, тогда можно предложить дополнительные задачи, но их следует отличать от требований, непосредственно содержащихся в исходном документе.

# Пошаговое создание библиотеки Domain Model

Дата создания: 2026-09-09.

Эта инструкция описывает интерактивное создание и постепенное наполнение общей библиотеки контрактов данных приложения. Машина ведёт процесс по шагам, сохраняет текущее состояние и сама сообщает следующий шаг.

## Что создаётся

Для приложения с именем `<Service>` создаётся библиотека:

```text
<Service>.Model
```

Имя проекта и корневой namespace совпадают. Для приложения `Monitor`:

```text
Проект: Monitor.Model
Namespace: Monitor.Model
```

Библиотека содержит внутренние данные приложения — `DomainObject`, контейнеры этих данных, перечисления, value objects и выбранные контракты request/response. Ими могут пользоваться все более высокие слои решения.

Это чистый контракт данных:

- нет ссылок на другие проекты решения;
- нет зависимости от EF, провайдера СУБД и классов `Entity`;
- нет зависимости от ASP.NET, SignalR, frontend и другой инфраструктуры;
- сторонние NuGet-пакеты по умолчанию отсутствуют;
- допустимы стандартные типы выбранного .NET framework и операции, принадлежащие самой модели и не требующие внешней технологии.

Любая .NET-библиотека зависит от выбранного target framework и его стандартной библиотеки. Поэтому выражение «не зависит ни от чего» означает отсутствие проектных и технологических зависимостей, а не отсутствие .NET runtime.

`Entity`, `DbContext`, EF-конфигурации, migrations и преобразование между `Entity` и `DomainObject` находятся в будущем проекте доступа к данным. EF6 или EF Core, Code First или Database First, СУБД и provider при создании `<Service>.Model` не выбираются.

## Как начать

Основная фраза:

```text
Создай библиотеку контрактов данных для приложения Monitor. Веди меня пошагово.
```

Можно сразу указать известные параметры:

```text
Создай библиотеку контрактов данных для приложения Monitor в <путь к solution> на <target framework>. Веди меня пошагово.
```

Если обязательных сведений не хватает, Машина задаёт только один следующий необходимый вопрос. Не нужно заранее помнить всю последовательность или отвечать на большую анкету.

## Шаг 1. Паспорт библиотеки

Перед созданием Машина показывает паспорт:

```text
Service: Monitor
Проект: Monitor.Model
Namespace: Monitor.Model
Расположение: <выбрано или не определено>
Target framework: <выбран или не определён>
Зависимости от проектов: запрещены
Сторонние NuGet-пакеты: по умолчанию запрещены
```

На этом шаге нужно определить:

1. Имя `<Service>`.
2. Путь к существующему solution или место нового проекта.
3. Target framework.

Если параметр можно надёжно определить из существующего solution, Машина показывает найденное значение. При неоднозначности она не выбирает его самостоятельно.

## Шаг 2. Пустой проект

После согласования паспорта Машина:

1. Создаёт библиотеку `<Service>.Model`.
2. Устанавливает корневой namespace `<Service>.Model`.
3. Не добавляет демонстрационные модели и тестовые данные.
4. Проверяет отсутствие запрещённых ссылок и пакетов.
5. Собирает пустой проект.
6. Сохраняет текущее состояние и следующий шаг в карточке применения, связанной с рабочей задачей.

Точное место карточки применения определяется по действующим правилам задач vault при создании первого реального проекта.

## Шаг 3. Добавление данных

После создания проекта начинается повторяемый цикл наполнения. Данные могут быть описаны в чате или переданы в приложенном файле.

Все `DomainObject`, добавляемые таким способом, предназначены для последующего хранения в БД и создаются внутри папки `Domain`. Машина не спрашивает для каждого объекта, нужно ли сохранять его в БД. Другие типы библиотеки, находящиеся вне `Domain`, автоматически в модель `Entity` не переносятся.

`DomainObject` является источником состава будущей модели БД. При его изменении Машина должна позднее синхронизировать соответствующие `Entity` и EF-конфигурацию. Создание migration никогда не выполняется автоматически. Применение migration к существующей БД также требует отдельного явного требования Parad либо ручного запуска. Исключение — первоначальное создание отсутствующей БД из заранее подготовленных migrations при первом запуске приложения.

### Описание в чате

```text
Добавь DomainObject Product: ID long, Code string, Name string, Price decimal.
```

Если поля не перечислены, применяется согласованный шаблон `DomainObject` по умолчанию.

### Описание в файле

```text
Добавь DomainObject из приложенного файла.
```

или:

```text
Разбери приложенный файл и добавь из него все контракты данных.
```

Формат файла может быть любым, если из него можно извлечь описание объектов и полей. Один файл может содержать один объект или список объектов.

### Предварительный разбор

До изменения кода Машина показывает распознанный результат, например:

```text
Найдено объектов: 2

Product
- ID: long
- Code: string
- Name: string
- Price: decimal

Category
- Code: string
- Name: string
```

В предварительном разборе указываются:

- имя каждого класса;
- имена и типы полей;
- значения по умолчанию, если они переданы;
- комментарии к полям, если они переданы;
- где использован тип `string` по умолчанию;
- где добавлено обязательное поле `Code`;
- какие папки, основные и парные классы будут созданы;
- неоднозначные или ещё не согласованные места.

Если тип поля не указан, используется `string`. Поле `Code` присутствует всегда и является логическим ключом `DomainObject`.

Для `string`, `int` и `long` используются уже согласованные явные значения конструктора: `""` и `0`. Значения для других типов не придумываются: если они не определены входными данными или действующим шаблоном, Машина показывает вопрос до генерации.

После проверки Parad подтверждает добавление либо исправляет распознанное описание.

### Результат для каждого DomainObject

Для каждого `<Имя>` создаются:

```text
Domain/
└─ <Имя>/
   ├─ <Имя>.cs
   └─ <Имя>s.cs
```

- основной класс использует namespace `<Service>.Model`;
- папка `Domain` не изменяет namespace;
- конструктор явно инициализирует все поля;
- `Equals` и `GetHashCode` строятся по `Code`;
- рядом всегда создаётся полный парный класс `<Имя>s : ObservableCollection<<Имя>>`;
- парный класс содержит `FromEnumerable`, `CurrentItem`, `CurrentChanged` и `TotalCount`.

Точный код шаблона хранится в документе `Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md`.

## Шаг 4. Готовые request/response-контракты из примера

Найти готовые контракты можно на любом этапе:

```text
Найди тип данных для логина.
```

Машина:

1. Ищет прямые и близкие варианты в `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared`.
2. Показывает точные имена классов.
3. Сообщает, образуют ли они полную пару `<Имя>Model`/`<Имя>Result`.
4. Показывает зависимости и точный путь исходной папки.
5. Объясняет различия между вариантами.
6. Предлагает Parad выбрать нужный вариант.
7. Ничего не добавляет до выбора.

После выбора исходный код пары переносится без изменений, кроме namespace целевого проекта. Необходимость связанных базовых типов показывается отдельно и не предполагается автоматически.

## Шаг 5. Наборы стандартной функциональности

Для следующего типа действует поиск только по точному имени или согласованному псевдониму:

| Упоминание | Также распознаётся | Исходная папка | Файл или набор |
| --- | --- | --- | --- |
| `SignalR` | — | `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared/SignalR` | набор файлов SignalR |
| `Claim` | `Claims` | `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared/Claim` | набор моделей Claim |
| `JwtService` | `Jwt` | `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared/Infrastructure` | `JwtService.cs` |
| `ValidationStartupFilter` | `StartupFilter` | `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared/StartupFilter` | `SettingValidationStartupFilter.cs` |
| `Urls` | — | `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared` | `Urls.cs` |

При точном упоминании Машина показывает найденные файлы и путь, но ничего не добавляет автоматически.

Перед добавлением каждый файл проверяется на соответствие чистому контракту данных. SignalR hubs и repositories, реализация `JwtService` и `StartupFilter` относятся к технологическому поведению, поэтому по умолчанию не помещаются в независимую `<Service>.Model`. Их можно сохранить как найденные примеры для обсуждения будущего инфраструктурного проекта. Для `Claim` и `Urls` решение принимается после проверки фактического содержимого.

## Карточка состояния

Чтобы не вспоминать следующий шаг, Машина сохраняет состояние конкретного применения. Карточка должна содержать как минимум:

```text
Приложение: Monitor
Текущий проект: Monitor.Model
Этап: наполнение контрактами
Проект создан: да
Сборка проходит: да

Добавлено:
- CommandResult / CommandResults
- LoginModel / LoginResult

Источники данных:
- описание из чата
- <имя приложенного файла>

Нерешённые вопросы:
- <вопросы, которые нельзя решить автоматически>

Следующий шаг:
- <одно конкретное действие>
```

Продолжить работу можно короткой фразой:

```text
Продолжим Monitor.Model.
```

или:

```text
Что дальше по Monitor.Model?
```

Машина читает карточку, кратко сообщает выполненное и ведёт к указанному следующему шагу.

## Завершение библиотеки

Перед завершением Машина проверяет:

- проект собирается;
- отсутствуют ссылки на EF, СУБД, транспортные технологии и другие проекты решения;
- namespace соответствует `<Service>.Model`;
- все `DomainObject`, предназначенные для БД, находятся в папке `Domain`;
- у каждого `DomainObject` есть `Code`;
- рядом с каждым `DomainObject` создан обязательный парный класс;
- конструкторы и значения по умолчанию согласованы;
- технологический код не попал в библиотеку контрактов;
- карточка содержит итоговый состав и следующий архитектурный этап.

Завершение или изменение Domain Model само по себе не разрешает Машине создавать migration либо применять её к существующей БД.

После завершения следующий этап формулируется явно, например:

```text
Monitor.Model завершён.
Следующий архитектурный этап: проект Entity для выбранного EF-профиля.
```

## Общая последовательность

```text
Начать библиотеку
    → согласовать минимальный паспорт
    → создать и проверить пустой проект
    → добавлять данные из чата, файлов или выбранных примеров
    → после каждого шага обновлять карточку состояния
    → проверить независимость и сборку
    → зафиксировать завершение и назвать следующий проект
```

## Как поддерживать инструкцию

Если в процессе обсуждения изменяется согласованное правило, нужно синхронно обновить:

1. Эту пользовательскую инструкцию.
2. Рабочий промт Машины `Commands/Create Project Domain Model by Step.md`.
3. Карточку текущей задачи или применения, если изменение влияет на уже созданный проект.

Новые правила не считаются согласованными только потому, что Машина их предложила. Они добавляются в инструкцию после решения Parad.

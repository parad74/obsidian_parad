# Пошаговое создание библиотеки Domain Model

Дата создания: 2026-09-09.

Эта инструкция описывает интерактивное создание и постепенное наполнение общей библиотеки контрактов данных приложения. Машина ведёт процесс по шагам, сохраняет текущее состояние и сама сообщает следующий шаг.

## Что создаётся

Для приложения с именем `<Service>` создаётся библиотека:

```text
<Service>.Model
```

Имя проекта и корневой namespace совпадают. Для приложения `Monitor`:

```text
Проект: Monitor.Model
Namespace: Monitor.Model
```

Библиотека содержит внутренние данные приложения — `DomainObject`, контейнеры этих данных, перечисления, value objects, все пять интерфейсов из исторической папки `Interface` и выбранные контракты request/response. Ими могут пользоваться все более высокие слои решения.

Это чистый контракт данных:

- есть ссылка на проект `Service.Model.EF.SelectParam`, потому что интерфейсы используют `SelectParams`; другие ссылки на проекты по умолчанию отсутствуют;
- в собственном коде нет EF-реализации, провайдера СУБД и классов `Entity`;
- нет зависимости от ASP.NET, SignalR, frontend и другой инфраструктуры;
- для атрибутов `[Display]` перечислений готового образца нужен `System.ComponentModel.Annotations`; версия 4.7.0 предлагается в начальных вопросах, если версия ещё не выбрана. Другие прямые пакеты без необходимости не добавляются;
- допустимы стандартные типы выбранного .NET framework и операции, принадлежащие самой модели и не требующие внешней технологии.

Помимо выбранного target framework и его стандартной библиотеки, у `<Service>.Model` есть согласованная проектная зависимость от `SelectParam`. При проверке сборки учитываются и её зависимости.

Entity, DbContext, конфигурации и migrations находятся в проекте доступа к данным. Семейство EF6 или EF Core, версии, СУБД и провайдер определяются для конкретного проекта; текущий подход — Code First. При создании только Model выбирать EF не требуется.

## Состав solution по запросу

| Запрос | Базовый состав solution |
| --- | --- |
| Создать `<Service>.Model` | `<Service>.Model` и `SelectParam` — два проекта |
| Создать `<Service>.Model.Sqlite.CodeFirst.ExportImport` | ExportImport, `<Service>.Model` и `SelectParam` — три проекта |

Это состав соответствующего сценария, а не общий запрет включать другие проекты в solution. В рамках запрошенной работы необходимые проекты можно создать или подключить. Ограничения зависимостей внутри конкретного проекта не ограничивают перечень проектов solution.

В рабочем репозитории приложения `Service.Model.EF.SelectParam` хранится как обычный проект с исходным кодом. Если его там ещё нет, Машина копирует `.csproj` и исходники из `Sources/Architectures/LibProject/netstandard2.0/SelectParam/` без отдельного `.sln`, `bin`, `obj` и чужих Git-метаданных, включает проект в `<Service>.sln` и добавляет `ProjectReference` во все проекты, где используются типы `SelectParam`. Внешняя ссылка на checkout `Sources/Architectures` и пакет вместо проекта не используются. Если локальная копия уже есть, она используется без дублирования. Проекты, которым `SelectParam` не нужен, ссылку не получают.

Новый автономный solution называется именем сервиса, выбранным в начале: `<Service>.sln`. Например, для сервиса `Inventory` создаётся `Inventory.sln`. Имя БД и имя ExportImport-проекта имя solution не меняют.

Запрос создать `<Service>.Model.<DataStore>.CodeFirst.ExportImport` создаёт не пустую оболочку, а готовый стартовый solution по первому образцу. `CommandResult` присутствует в двух связанных проектах: в `<Service>.Model` находятся DomainObject `CommandResult`, `CommandResults`, перечисления и интерфейс репозитория; в ExportImport находятся его Entity, Fluent-конфигурация, подключение к `<ИмяБД>Context`, MappingEF и EF-репозиторий. Состав готового `CommandResult` повторно не согласуется. Правила гибкого выбора этапов применяются к следующим предметным объектам и дополнениям, а не исключают части этого стартового комплекта. Тестовые проекты и автоматизированные тесты на текущем этапе не создаются.

## Параметры по умолчанию

Перед созданием приложения или нового проекта Машина по одному спрашивает каждый необходимый для запрошенного состава параметр, который ещё не задан Parad, не согласован для текущего применения и не определяется однозначно существующим проектом. Формат вопроса: предлагаемый вариант из первого образца и редактируемое поле для своего значения (свободный ответ). Значения таблицы ниже служат предложениями, а не разрешением применить их без ответа. Уже заданные параметры повторно не спрашиваются. Это правило действует и при добавлении нового проекта в существующий solution.

| Параметр | Предлагаемый вариант или правило определения |
| --- | --- |
| Имя сервиса, если ещё не определено | Вопрос: `Monitor` или своё значение |
| Проект и namespace Domain Model | `<Service>.Model` |
| Target framework Model и SelectParam | `netstandard2.0` |
| Пакет Model для готового образца | `System.ComponentModel.Annotations` `4.7.0` |
| Проект доступа к данным при его запросе | `<Service>.Model.Sqlite.CodeFirst.ExportImport` |
| Namespace EF-проекта | `<Service>.Sqlite.CodeFirst` |
| Target framework EF-проекта | `netcoreapp3.1` |
| Семейство EF и версия | EF Core `3.1.9` |
| СУБД и подход | SQLite, Code First |
| Пакет провайдера | `Microsoft.EntityFrameworkCore.Sqlite` `3.1.9` |
| Логирование EF-проекта | `Microsoft.Extensions.Logging` `3.1.9` |
| Зависимости SelectParam | `EntityFramework` `6.4.0`, `Microsoft.Windows.Compatibility` `3.1.1` |
| Логическое имя БД | Отдельный вопрос при старте ExportImport: `MonitorDb` из образца или своё значение; не выводится автоматически из имени сервиса |
| Контекст | `<ИмяБД>Context`, производное от выбранного логического имени БД; например, `WarehouseDbContext` для `WarehouseDb` |
| Имя файла БД и расположение, если СУБД использует файл | Имя вводится без расширения: `monitor` или своё значение; расположение определяется отдельно. Расширение зависит от выбранной СУБД; для текущего SQLite-профиля — `.db`, итоговый пример `monitor.db`. Для серверной СУБД без файла подключения такой вопрос не задаётся |
| Имя нового отдельного solution | `<Service>.sln` |

Состав файлов берётся из соответствующего готового образца и его архитектурной карточки. Значения сверены с текущими `.csproj` в `Sources/Architectures/LibProject/netstandard2.0/Monitor.Model/`, `Sources/Architectures/LibProject/netstandard2.0/SelectParam/` и `Sources/Architectures/LibProject/netcoreapp3.1/Monitor.Model.Sqlite.CodeFirst.ExportImport/`.

Сначала учитываются явно указанные параметры, фактические solution/проекты и ранее согласованные решения текущей работы. Остальные необходимые параметры выбираются через вопросы: вариант из образца или своё значение. Машина показывает краткую сводку выбранных параметров и проверяет совместимость с целевым solution. При несовместимости показывает конкретный конфликт и уточняет решение до создания зависящего от него проекта. Версии автоматически не подстраиваются под solution и не обновляются без решения Parad. Для другой СУБД или семейства EF выбирается и проверяется соответствующий провайдер; SQLite-пакет не подставляется для другой СУБД.

В режиме интеграции используется указанный существующий solution; имя нового solution к нему не применяется. Расположение берётся из запроса или однозначного рабочего контекста, а при их отсутствии уточняется. Состав solution определяется запросом и необходимыми проектными зависимостями; общего запрета добавлять проекты нет. Defaults не являются командой «сделай всё» и не отменяют отдельных правил migrations. Модель согласуется возвратом проверенного Excel, после чего весь запрошенный комплект создаётся одним проходом.

### Порядок вопросов перед созданием

Вопросы задаются по одному; перед созданием должны быть выбраны все необходимые параметры запрошенного состава. Предложенный вариант не считается ответом. Значения, уже заданные в запросе, согласованные для текущего применения или однозначно определённые существующим проектом, повторно не спрашиваются.

1. Имя сервиса и расположение нового проекта либо существующего solution.
2. До создания solution с ExportImport (или добавления ExportImport в существующий solution) спроси, какая СУБД нужна. Покажи список для выбора: SQLite, SQL Server (MSSQL), своё значение. Это примеры, а не ограничение допустимых СУБД; другие варианты проверяются по каталогу и документации. Дождись ответа. Для одного Model этот вопрос не нужен.
3. После выбора СУБД отдельным вопросом спроси, какой провайдер использовать, и дождись выбора до создания solution/проектов. Покажи список предлагаемых совместимых провайдеров и возможность своего значения: семейство EF, точное имя пакета, подходящая версия, совместимость с target framework, ограничения и состояние проверки. Например, каталог содержит для SQLite `Microsoft.EntityFrameworkCore.Sqlite` (EF Core), а для SQL Server — `Microsoft.EntityFrameworkCore.SqlServer` (EF Core) и провайдер из `EntityFramework` (EF6). Непроверенный новый профиль обозначай явно. Список зависит от выбранной СУБД и EF и не ограничивается одним default; другие варианты проверяй по актуальной документации разработчика. Выбор провайдера согласуй до создания проекта, не подставляй его молча.
4. Остальные необходимые настройки: семейство/версия EF и target framework в согласованной совместимой комбинации, версии пакетов, логическое имя БД, имя файла без расширения и его расположение для файлового подключения. Если семейство EF уже выбрано вместе с провайдером, повторный вопрос не нужен. Подход текущего процесса — Code First; производные имена проектов, namespaces, solution и контекста показываются по установленным правилам, без независимого переименования.
5. Покажи итоговую сводку и проверь совместимость до создания. Нового общего подтверждения поверх полученных ответов не требуется; нерешённые конфликты уточняются до зависящего от них действия.

Расширение файла определяется выбранной СУБД/профилем, а не добавляется пользователем к базовому имени. Для SQLite в этом workflow используется `.db`; для другой СУБД проверь применимый формат, не придумывай расширение. Серверной СУБД без файла в строке подключения имя файла и расширение не назначаются. Логическое имя БД и базовое имя файла остаются независимыми параметрами.

## Как начать

Основная фраза:

```text
Создай библиотеку контрактов данных для приложения Monitor. Веди меня пошагово.
```

Можно сразу указать известные параметры:

```text
Создай библиотеку контрактов данных для приложения Monitor в <путь к solution> на <target framework>. Веди меня пошагово.
```

Если обязательных сведений не хватает, Машина задаёт только один следующий необходимый вопрос. Не нужно заранее помнить всю последовательность или отвечать на большую анкету.

## Шаг 1. Начальные параметры

Перед созданием Машина показывает краткую сводку:

```text
Service: Monitor
Проект: Monitor.Model
Namespace: Monitor.Model
Расположение: <выбрано или не определено>
Target framework: netstandard2.0 — предлагаемый вариант, если ещё не выбран
Зависимости от проектов: Service.Model.EF.SelectParam; другие по умолчанию отсутствуют
Прямые сторонние NuGet-пакеты: System.ComponentModel.Annotations 4.7.0 для готового образца
```

На этом шаге нужно определить следующие параметры; `<Service>` означает запрошенное и выбранное Parad имя сервиса, поэтому имя проекта имеет вид `<Имя сервиса>.Model` без пробела перед `Model`:

1. Имя `<Service>`.
2. Путь к существующему solution или место нового проекта.
3. Target framework.

Параметры запрашиваемого нового проекта определяются по разделу «Параметры по умолчанию»: все необходимые незаданные значения спрашиваются до создания, по одному, с предложением из образца и свободным вводом. Вопросы охватывают имя сервиса, расположение и target framework; для ExportImport также СУБД, семейство и версию EF, провайдер и его версию, параметры БД и остальные настройки создаваемого профиля. Имена проектов, namespaces и solution выводятся из выбранного сервиса и профиля, имя DbContext — из выбранного логического имени БД; все имена показываются в сводке. Совместимость проверяется; другие версии .NET и EF в solution автоматически не перенимаются.

При запросе solution с ExportImport до создания проектов отдельно определяются логическое имя БД, а для файлового подключения — имя файла без расширения и его расположение. Расширение определяется выбранной СУБД; для текущего SQLite-профиля — `.db`. Пример вопросов: «Имя сервиса: 1. Monitor; 2. своё значение в редактируемом поле»; «Имя файла БД без расширения: 1. monitor; 2. своё значение в редактируемом поле». По этому же принципу задаётся вопрос по каждому остальному необходимому незаданному параметру. Уже заданное повторно не согласуется. Для запроса только Model вопросы о БД не нужны.

Выбранное здесь имя сервиса `<Service>` задаёт общий префикс связанных проектов и namespaces и имя `<Service>.sln`. Контекст называется `<ИмяБД>Context` по выбранному логическому имени БД: `WarehouseDb` → `WarehouseDbContext`. Имя файла и его расширение не входят в имя контекста. В стартовой сводке отдельно показываются имя сервиса, логическое имя БД, имя контекста, базовое имя файла, расширение и полный путь/строка подключения. Проект Model всегда называется `<Имя сервиса>.Model`; `Monitor` в примерах — предлагаемый вариант, а не фиксированное имя нового приложения.

## Шаг 2. Стартовый проект

После определения начальных параметров Машина:

1. Создаёт библиотеку `<Service>.Model`.
2. Устанавливает корневой namespace `<Service>.Model`.
3. Добавляет `ProjectReference` на `Service.Model.EF.SelectParam`.
4. Включает `<Service>.Model` и `Service.Model.EF.SelectParam` в один solution.
5. Добавляет все пять интерфейсов из `Monitor.Service.Shared/Interface` в namespace `<Service>.Model.Interface`, заменяя `Monitor` в именах на выбранное `<Service>`.
6. Добавляет готовые `CommandResult` и `CommandResults` и необходимые перечисления из текущего образца `Sources/Architectures/LibProject/netstandard2.0/Monitor.Model/`. Они нужны как пример стиля для Машины при генерации новых классов и для программиста, а также как типы для `ICommandResultRepository`. Состав готового образца и его адаптация повторно не согласуются. При переносе в новый сервис namespaces и ссылки на типы приводятся к текущему проекту; имена классов и готовый состав сохраняются.
   Зависимость исторического конструктора от `ICount4uContext` уже исключена в готовом образце. Необходимые перечисления берутся вместе с ним без повторного обсуждения.
   Первый образец `Monitor.Model` сохраняет поля старого `CommandResult`, кроме `AdapterType`/`ImportDomainEnum`, `IturCodes`, `DocumentHeaderCodes` и зависимости от `ICount4uContext`. `Files` и `UnsureFiles` в первом образце — строки. Обязательное свойство `Code` является основным логическим свойством для сравнения объектов; историческое `CommandResultCode` хранит отдельное значение. Сравнение и hash code выполняются по `Code`.
7. Добавляет в корень Model служебный `NoEntityAttribute.cs` с namespace `<Service>.Model`, чтобы свойства можно было помечать `[NoEntity]`; Entity для этого типа не создаётся. Не добавляет другие демонстрационные модели и тестовые данные.
8. Проверяет отсутствие других несогласованных ссылок и пакетов.
9. Собирает стартовый solution.
10. При необходимости кратко сохраняет текущее состояние и следующий шаг в существующей рабочей задаче или своих рабочих заметках.

Отдельный паспорт или карточка применения не создаются, обязательного формата нет. Для Parad источником истины служат solution, названия проектов, `.csproj` и код. Машина организует дополнительный рабочий контекст так, как ей удобно, не добавляя новый тип документа или шаблон.

### Сборка и команды создания БД

После создания стартового ExportImport solution Машина собирает его. При успешной сборке она сообщает Parad, что solution собирается, с фактическим результатом. Если сборка не прошла, переход к migrations и БД откладывается до исправления относящихся к созданному решению ошибок. Отдельные тестовые проекты и автоматизированные тесты на текущем этапе не создаются.

После успешной сборки Машина проверяет, можно ли выполнить design-time-команды выбранного EF: установлен ли подходящий инструмент, подключены ли необходимые design-time packages и существует ли согласованный способ создать `<ИмяБД>Context`. Если чего-то не хватает, Машина показывает необходимое изменение и не добавляет package или фабрику контекста без согласия Parad.

Затем Машина выдаёт две точные команды с рабочей папкой, путями проектов и именем контекста:

1. Создать migration `InitialCreate`.
2. Применить migrations для создания отсутствующей БД.

Для EF Core основа команд — `dotnet ef migrations add InitialCreate` и `dotnet ef database update`; для EF6 — `Add-Migration InitialCreate` и `Update-Database`. Конкретные параметры зависят от созданного solution, поэтому Машина подставляет фактические `project`, `startup project`, `DbContext` и выбранное подключение.

Parad может выполнить показанные команды вручную. Машина также может выполнить их по отдельному явному запросу: сначала создать и проверить migration, затем отдельно применить её к подтверждённой целевой БД. После этого Машина проверяет, что БД создана, migration применена и ожидаемая схема присутствует. Существующая БД автоматически не обновляется.

## Шаг 3. Добавление данных

После создания проекта начинается повторяемый цикл наполнения. Данные могут быть описаны в чате или переданы в приложенном файле.

Состав работы определяется запросом Parad и фактическим состоянием проекта: названные этапы создаются или дополняются, существующие части используются без дублирования. 11 последовательностей кубика — примеры, а не закрытый список команд. По умолчанию после утверждения Excel выполняется DomainObject с парной коллекцией → Entity с конфигурацией и подключением к DbContext → MappingEF → Repository с интерфейсом. Запрос только Entity не запускает остальные этапы. При недостающих зависимостях уточни существующие пути либо расширение состава работы. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]].

При создании объектов из описания сначала верни разобранную модель в Excel для проверки Parad. Продолжай только по возвращённой и утверждённой книге; нерешённые вопросы уточни до генерации. Возвращённый Excel подтверждает описанную в нём модель: после него создай все классы согласованного объёма одним проходом в обоих проектах либо, если Parad ограничила запрос, только в названном проекте или составе. Не вводи дополнительных подтверждений для каждого объекта, класса или этапа. Обязательные поля должны быть явно видны в Excel.

Все `DomainObject`, добавляемые таким способом, предназначены для последующего хранения в БД и создаются внутри папки `Domain`. Машина не спрашивает для каждого объекта, нужно ли сохранять его в БД. Другие типы библиотеки, находящиеся вне `Domain`, автоматически в модель `Entity` не переносятся.

Дополнение существующих объектов определяется запросом и найденным кодом. Используй существующие классы; не создавай пару заново и не запускай не запрошенные части автоматически. При запросе синхронизации поля одним проходом дополни все входящие в запрос Entity, DomainObject, конфигурации и мапперы. Если отсутствует необходимая часть, уточни её путь либо создание до генерации. После возвращения утверждённого Excel отдельные подтверждения по объектам и этапам не требуются. Существующие поля автоматически не удаляются и не переделываются; migrations остаются отдельными запрошенными действиями. Первоначальное создание отсутствующей БД из заранее подготовленных migrations описывается отдельно в выбранном профиле; этот шаг не следует из запроса создать объект.

### Описание в чате

```text
Добавь DomainObject Product: ID long, Code string, Name string, Price decimal.
```

Если поля не перечислены, применяется согласованный шаблон `DomainObject` по умолчанию.

`CommandResult` показывает стиль оформления и реализации класса; его предметные поля и перечисления не копируются автоматически в каждый новый DomainObject. Для нового класса используется его собственное описание и общие обязательные правила, включая первое поле `ID long` и `Code`. Предварительный разбор класса согласуется в Excel; после возврата утверждённой книги отдельное подтверждение кода не требуется.

### Описание в файле

```text
Добавь DomainObject из приложенного файла.
```

или:

```text

```

Формат файла может быть любым, если из него можно извлечь описание объектов и полей. Один файл может содержать один объект или список объектов.

### Предварительный разбор

До изменения кода Машина показывает распознанный результат, например:

```text
Найдено объектов: 2

Product
- ID: long
- Code: string
- Name: string
- Price: decimal

Category
- ID: long — добавлено по обязательному правилу, первичный ключ БД
- Code: string
- Name: string
```

В предварительном разборе указываются:

- имя каждого класса;
- имена и типы полей;
- значения по умолчанию, если они переданы;
- комментарии к полям, если они переданы;
- опциональный столбец `Attributes`: атрибуты будут добавлены перед соответствующим свойством DomainObject. `NoEntity` или `[NoEntity]` оставляет свойство только в DomainObject и исключает его из Entity, конфигурации и всех методов маппера. Пустая ячейка или отсутствие столбца во входной книге означает отсутствие дополнительных атрибутов; полный формат — [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]];
- какие типы предложены Машиной при отсутствии типа во входе;
- где добавлены обязательные поля `ID long` и `Code`; `ID` показывается первым и отмечается как первичный ключ БД;
- какие папки, основные и парные классы будут созданы;
- неоднозначные или ещё не согласованные места.

Первое объявленное свойство каждого нового `DomainObject` — обязательное `public long ID { get; set; }`. Если его нет в описании, Машина добавляет его без отдельного вопроса; уже указанное `ID long` не дублируется и ставится первым. В парном `Entity` `long ID` также стоит первым и является первичным ключом таблицы. Если тип обычного поля не указан, Машина предлагает его по смыслу и согласует в Excel; для `ID` всегда используется `long`. Поле `Code` присутствует всегда и остаётся логическим ключом сравнения `DomainObject`.

Стартовый шаблон явно инициализирует string пустой строкой, int/long нулём; в конкретной модели значения из источника и предложения Машины отдельно показываются в Excel. Утверждённые значения конкретного объекта имеют приоритет. Неуказанное, null, пустая строка и ноль различаются; defaults C# и БД показываются отдельно.

При создании объектов из описания сначала верни разобранную модель в Excel для проверки Parad. Продолжай только по возвращённой и утверждённой книге; нерешённые вопросы уточни до генерации. Возвращённый Excel подтверждает описанную в нём модель: после него создай все классы согласованного объёма одним проходом в обоих проектах либо, если Parad ограничила запрос, только в названном проекте или составе. Не вводи дополнительных подтверждений для каждого объекта, класса или этапа. Обязательные поля должны быть явно видны в Excel.

### Результат для каждого DomainObject

Для каждого `<Имя>` создаются:

```text
Domain/
└─ <Имя>/
   ├─ <Имя>.cs
   └─ <Имя>s.cs
```

- основной класс использует namespace `<Service>.Model`;
- папка `Domain` не изменяет namespace;
- первым свойством объявляется обязательное `long ID`, которое будет первичным ключом БД;
- конструктор явно инициализирует все поля, включая `ID = 0`;
- `Equals` и `GetHashCode` строятся по `Code`;
- рядом всегда создаётся полный парный класс `<Имя>s : ObservableCollection<<Имя>>`;
- парный класс содержит `FromEnumerable`, `CurrentItem`, `CurrentChanged` и `TotalCount`.

Точный код шаблона хранится в документе `Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1.md`.

## Шаг 4. Готовые request/response-контракты из примера

Это отдельный тип содержимого `<Service>.Model`, не относящийся к цепочке объектов из Excel. Если утверждённая Excel-модель запускается без ограничения этапов, выполняется полная цепочка DomainObject с коллекцией → Entity с конфигурацией и DbContext → MappingEF → Repository с интерфейсом. Если Parad просит отдельный этап, класс или готовую request/response-пару, добавляется только прямо запрошенное.

Найти готовые контракты можно на любом этапе:

```text
Найди тип данных для логина.
```

Машина:

1. Ищет прямые и близкие варианты в `Sources/old/WebAPI.Monitor/src/Monitor.Service.Shared`.
2. Показывает точные имена классов.
3. Сообщает, образуют ли они полную пару `<Имя>Model`/`<Имя>Result`.
4. Показывает зависимости и точный путь исходной папки.
5. Объясняет различия между вариантами.
6. Предлагает Parad выбрать нужный вариант.
7. Ничего не добавляет до выбора.

После выбора исходный код пары переносится без изменений, кроме namespace целевого проекта. Необходимость связанных базовых типов показывается отдельно; они добавляются только по прямому запросу или отдельному выбору Parad.

Дополнительные типы (`Login`, `EmailSender` и другие) не добавляются при создании стартового проекта. Их можно найти и добавить в `<Service>.Model` позже по прямому запросу. Каждая выбранная пара хранится в своей папке по назначению, например `Login/`, а не в одном общем файле. Состав доступных пар и отдельных типов записан в [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Каталог полных пар в историческом примере|каталоге исторических примеров]].

При поиске или добавлении Машина даёт ссылки на конкретные старые `.cs`-файлы. По просьбе показать использование она также находит и показывает файл старого проекта, где тип применяется. При необходимости имена добавленных файлов и ссылки на источники сохраняются в существующей рабочей задаче или рабочих заметках.

## Восстановление состояния

Parad как архитектор и разработчик ориентируется на код в solution. Машина восстанавливает состояние по solution, проектам, `.csproj`, исходному коду и существующей рабочей задаче. Для собственной преемственности она при необходимости сохраняет в этой задаче или рабочих заметках источники, утверждённый Excel, выполненное, нерешённые вопросы и следующий шаг. Отдельная карточка применения и обязательный формат не требуются; обычное сопровождение практической работы Obsidian-задачей сохраняется.

Продолжить работу можно фразой «Продолжим `<Имя сервиса>.Model`» или «Что дальше по `<Имя сервиса>.Model`?». Машина проверяет фактическое состояние файлов и существующую задачу, кратко сообщает выполненное и предлагает следующий шаг. Отсутствие отдельной карточки применения не блокирует продолжение.

## Завершение библиотеки

Перед завершением Машина проверяет:

- проект собирается;
- присутствует ссылка на `Service.Model.EF.SelectParam`, а других несогласованных project references и прямых package references нет;
- в собственном коде нет EF-реализации, СУБД и транспортных технологий;
- namespace соответствует `<Service>.Model`;
- все `DomainObject`, предназначенные для БД, находятся в папке `Domain`;
- у каждого нового `DomainObject` первое свойство — `ID long`, а также есть обязательный `Code`;
- рядом с каждым `DomainObject` создан обязательный парный класс;
- конструкторы и значения по умолчанию согласованы;
- технологический код не попал в библиотеку контрактов;
- итоговый состав подтверждён файлами solution, а следующий архитектурный этап назван явно; отдельная карточка применения не является условием завершения.

Завершение или изменение Domain Model само по себе не разрешает Машине создавать migration либо применять её к существующей БД.

После завершения следующий этап формулируется явно, например:

```text
<Имя сервиса>.Model завершён.
Следующий архитектурный этап: проект Entity для выбранного EF-профиля.
```

## Согласованные правила развития и вычитки

Таблицы этой архитектуры независимы. Повторы Code допустимы. Удаление по Code удаляет все совпадения; чтение и обновление по Code выбирают запись с минимальным техническим ID. Обновление по ID выбирает запись только по ID и переносит данные, включая Code, без проверки совпадения кодов. При обоих способах обновления ID записи в БД сохраняется. Политика не требует повторного согласования для каждого проекта. Равенство состава DomainObject/Entity относится к стартовому шаблону с исключением свойств DomainObject, помеченных `[NoEntity]`; последующие бизнес-различия описываются и отображаются явно. Достаточно описанные дополнительные методы реализуются, неизвестное поведение оставляется явно обозначенной заглушкой. Подробности: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Предметные правила и развитие шаблона]].

После создания согласованного комплекта показывай итоговые файлы/классы целиком для вычитки. Перед классом и новыми/изменёнными членами ставь комментарии с датой генерации и статусом вычитки. Новый код требует Full, изменение ранее вычитанного — проверки Changes с отметкой участка; ранее невычитанное не считается прочитанным. Read ставится только по проверке Parad; возврат Excel сам по себе не означает вычитку кода. Рабочий формат: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Показ кода и отметки вычитки]].

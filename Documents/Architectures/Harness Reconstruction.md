# Восстановление harness разработки — опыт Parad и Машины

Это руководство восстановления системы, если сохранились проекты с кодом и этот документ. Оно описывает устройство harness v2, основания решений и порядок построения нового экземпляра. Для ежедневной работы используется [[Documents/Architectures/Data Model Harness]]; этот текст не добавляет второй комплект технических контрактов.

## Исходная задача

Сохранять согласованные смыслы, паттерны и понятный Parad стиль между проектами, позволяя каждому приложению иметь собственную архитектуру. Первый практический набор — Model, SelectParam, Code First ExportImport и Book4U. Готовый проект даёт материал для исследования; его наличие не доказывает универсальность каждого решения.

Правило имеет одно основное место. Команды маршрутизируют к нему; примеры иллюстрируют. Задача хранит состояние работы. Историческое обсуждение сохраняет происхождение, но не участвует в обычном получении инструкций.

## Что мы решили и почему

1. **Сохранять версии.** Перед переработкой заморожена v1: тег model-harness-v1, коммит 6ac9c54d90bebb11a4e23f5d6087b99b32557dd5. V2 развивается в действующих путях. Это даёт возврат без двух одновременно действующих комплектов правил.
2. **Перенести нормативные решения из обсуждения.** Ранее организация методов, смена библиотек и развитие интерфейсов зависели от чтения материала задачи. Теперь это самостоятельные разделы действующих документов. При восстановлении из кода такой скрытой зависимости быть не должно.
3. **Разделить обязанности документов.** Изменение порядка вопросов, TODO и состава объектов прежде требовало править несколько подробных копий. Во время подготовки v2 найдена старая автоматическая маркировка вычитки в активном описании задачи. Повторы заменяются ссылками на основные разделы; история явно отделяется.
4. **Описывать устойчивые границы.** Model предоставляет данные и контракты и не зависит от потребителя. ExportImport знает обе формы данных и реализует сохранение. SelectParam предоставляет средства выборки. UI, бизнес-логика и подключение реализаций определяются приложением. Точный список полей читается из кода или утверждённой модели.
5. **Различать модули и кубики.** Модуль — ответственность внутри приложения; кубик — способ построить или расширить один либо несколько модулей. Повторное применение требует совместимости и известных входов; оно не означает допустимость подключения к любому solution.
6. **Выбирать небольшие вычитанные примеры.** Parad прочитала Book4U и выбрала его код как более чистую основу. Room, Rooms, Mapper и Repository показывают отдельные приёмы. CommandResult остаётся сложным стартовым примером. Примеры закреплены на 5c1aaced8d286cd7c6c894553621abf598ea98ab; сам репозиторий приложения продолжает развиваться независимо.
7. **Не превращать локальную особенность в общее правило.** В Book4U CommandResult сравнивается по OperationIndexCode; общий шаблон нового DomainObject использует Code. Непрошеное IEquatable ранее попало из адаптированного образца: сборка не выявляла отклонения от принятого контракта. Нужны объяснение назначения примера и проверка изменений публичного контракта.
8. **Разделить виды подтверждения.** Утверждённый Excel разрешает реализацию согласованного состава; вычитка относится к коду; сборка подтверждает техническую совместимость; наличие таблиц не подтверждает все CRUD-сценарии. Эти факты нельзя заменять друг другом.
9. **Улучшать систему по обнаруженной причине.** Если правило уже ясно, ошибка применения не всегда требует ещё одного запрета. Сначала проверить маршрут чтения, выбранный образец и доступность фактической проверки. Принятое локальное решение не становится общим без соответствующего решения Parad. Рабочий цикл обработки замечаний: [[Documents/Architectures/Data Model Principles#Накопление опыта без разрастания инструкций]].

## Как построить такой harness, имея только проекты с кодом

1. **Сохранить исходную точку.** Установить границы репозиториев, текущие изменения и версии. Не менять рабочие проекты в процессе инвентаризации. Снимок перед переработкой должен включать относящиеся к ней незакоммиченные договорённости, а не только прежний HEAD.
2. **Восстановить фактическую архитектуру.** Прочитать solution и .csproj, направления ProjectReference, интерфейсы и их реализации, точки создания зависимостей и движения данных. Выделить модули по ответственности. Не считать каждую папку модулем.
3. **Отделить наблюдение от решения.** Зафиксировать, что код делает сейчас, что явно требуется сохранить и что ещё непонятно. По коду можно установить зависимости и реализацию Equals; нельзя достоверно вывести, почему выбрана политика дубликатов, намеренна ли заглушка или требуется ли такой же контракт всем приложениям. Такие решения уточняются у архитектора, без повторного согласования уже известных ответов.
4. **Выбрать небольшой набор примеров.** Для каждого приёма найти понятный рабочий пример и связанного потребителя. Проверить его состояние и вычитку; записать точный файл/версию, чему он служит и какие детали предметные. Не копировать весь исходный проект ради одного приёма.
5. **Разложить правила по ответственности.** Создать минимальный указатель на общие ориентиры, архитектурные контракты, операции и примеры. Использовать существующие документы, если они подходят. У правила должно быть одно основное место; сведения, которые точнее читаются из .csproj или кода, не пересказывать во всех инструкциях.
6. **Описать расширение кубиками.** Для повторяющегося изменения определить входы, затрагиваемые модули, создаваемые части, зависимости, совместимость и границы. Условия выполнения ограниченного запроса важны не меньше полного сценария. Не переносить бизнес-правила одного кубика в другой только из-за общего слова Model или Service.
7. **Собрать маршрут выполнения.** Определить необходимые вопросы, входы, разрешённые действия и реальные точки остановки. Сохранять выбранные значения и использовать существующий код. Инструкция должна помогать выполнить задачу, не добавляя новые согласования технических мелочей.
8. **Проверить на представительном применении.** Пройти минимальный, полный и ограниченный сценарии, продолжение работы и изменение одного поля. Проверить результат по контракту, сборке и разрешённым операциям. Для ценных повторяющихся проверок позднее можно выбрать автоматизацию; само восстановление harness не разрешает создавать тестовые проекты или менять БД.
9. **Сохранить проверенный опыт.** Записать полученный результат, выявленные отклонения и границы проверки. Исправить основной источник или пример. При изменении модели агента или условий работы повторить показательные сценарии, а не объявлять прежнюю проверку бессрочной гарантией.

## Проверка и пределы текущего результата

V2 — переработка документации и маршрутов, без изменений Book4U. Проверка ссылок, переноса правил и мысленного прохождения сценариев не означает практического создания нового приложения по v2. Первое подключение WebAPI к готовому Book4U описано ниже. Создание нового комплекта Model/ExportImport по v2 этим не проверяется; уменьшение повторных вопросов и удобство вычитки ещё требуют оценки Parad.

Не все EF-профили, сочетания кубиков и операции с БД проверены. Описанные ограничения конкретной версии .NET/EF не распространяются на весь будущий harness. Старые проекты не обновляются автоматически при развитии правил.

## Первое извлечение опыта из другого проекта: SQLite WebAPI

2026-10-04 исследован существующий `WebAPI.Monitor.Model.Sqlite.CodeFirst`. Результат сохранён в [[Documents/Architectures/WebAPI/DotNet/WebAPI.Monitor.Model.Sqlite.CodeFirst|карточке исследования и предложения адаптации]], доступной через Catalog. Это первое применение v2 к извлечению опыта из другого проекта. Затем по решению Parad в Book4U создан потребитель WebAPI для Room и CommandResult; сборка и HTTP-проверки прошли, код передан на вычитку.

Полезной оказалась проверка всей цепочки потребителя: одинаковый `Delete(string)` скрывал разные ключи поиска, возврат Task в репозитории требовал проверки его ожидания контроллером, а коллекция с TotalCount теряла это свойство при JSON-сериализации. Первые два расхождения установлены по коду; последнее дополнительно воспроизведено в памяти на локальной сборке Book4U. При реализации API эти границы дополнительно проверены HTTP-запросами на временной БД; исходная модель и пользовательские данные сохранены.

Из источника выделены граница HTTP → интерфейс модели, настройка scoped-зависимостей в host и проверка типизированных настроек при запуске. Первоначальное отделение демонстрационного и неподключённого кода оказалось слишком грубым: не для каждой части было сохранено её назначение и место дальнейшего применения. Согласованные правила Model/ExportImport не переписаны под исторический host. Наблюдения о недостающих правилах и неоднозначностях ведутся в [[Tasks/Items/dotnet_architecture_examples/TASK-20261004-001-extract-sqlite-webapi-patterns#Наблюдения о работе harness|существующей задаче]] для последующего решения Parad.

Первое применение добавило конкретные наблюдения о внешних фильтрах SelectParam, зависимости логирования от Windows EventLog и запуске с относительным путём SQLite. Они сохранены в [[Tasks/Items/Book4U/TASK-20261004-002-add-book4u-webapi|задаче реализации]] вместе с исправлениями и проверками. Это подтвердило работоспособность ограниченного потребителя. Вычитка Parad от 2026-10-08 выявила, что полнота извлечения опыта источника этим не проверялась: были потеряны удобства разработки, заготовки и часть операций. Разбор сохранён в [[Documents/Architectures/WebAPI/DotNet/WebAPI.Monitor.Model.Sqlite.CodeFirst#Повторная вычитка — функции и заготовки|карте функций и заготовок]].

Причина пропуска — Машина применила критерий «нужно для текущего CRUD» к задаче извлечения опыта всего проекта. Parad уточнила: ценность имеют также заготовки для дальнейшего программирования. Повторный разбор связывает назначение каждой части с исходником, состоянием подключения, зависимостями и судьбой при переносе. Выявленный дефект реализации отделяется от полезного назначения приёма. Из этого пока не следует новый общий генератор или набор обязательных функций для всех проектов.

Показательный случай — CreateDbIfNotExists: опасения перенести старый EnsureCreated/seed привели к отказу от всего сценария инициализации, хотя в Book4U уже был вычитанный DbInitializer. По уточнению Parad он подключён к host; на временной БД проверены создание, сохранность при повторном запуске и пересоздание после удаления файла. На этом этапе остальные пропуски оставались видимыми в карте; успешное исправление одного не означало завершения всего извлечения. Результат последующего полного прохода указан ниже.

Повторное чтение комментариев и указанных в них статей добавило основания решений, которых не видно по исполняемым строкам: почему настройки доступны напрямую, зачем заготовка HostedService и какой action завершает обработку ошибок. В [[Documents/Architectures/WebAPI/DotNet/WebAPI.Monitor.Model.Sqlite.CodeFirst#Комментарии и источники пояснений|карточке WebAPI]] опробована связь «ссылка → место в коде → короткий вывод → граница применения». Достаточное объяснение сохраняется локально, без копирования статей и обязательного чтения интернета при каждом создании проекта. Непрочитанная ссылка помечается как непрочитанная; версия статьи не превращается в выбор runtime нового приложения.

## Повторное применение сохранённого опыта — 2026-10-08

Parad поручила пересоздать WebAPI на том же месте. Известные параметры повторно не спрашивались; единственный недостающий выбор о JWT/SignalR получен как «настраиваемые заготовки, внешние подключения выключены». Карта исследования использована для генерации функций и заготовок. [Текущая карта переноса](../../Sources/Book4U/WebAPI.Book4U.Model.Sqlite.CodeFirst/README.md#карта-переноса-исходного-проекта) связывает весь состав выбранного host с конкретным результатом или причиной адаптации; архитектурная карточка хранит основания, а README — текущую реализацию.

Проверка стала охватывать связанные комплекты: не только наличие AddSession, но сессию между запросами; не только IValidatable, но четыре набора настроек и отказ каждого при ошибке; не только файл XML, но его комментарий в Swagger; не только SignalR-регистрацию, но локально доставленное уведомление. Отключённая заготовка также имеет проверяемое поведение — отсутствие подключения и явное указание, что отправка не состоялась. Исходная модель и пользовательская БД сохранены по контрольным суммам.

Это практическая проверка цикла «исходный проект → сохранённое объяснение → повторная генерация → сравнение и проверка». Она улучшила покрытие по замечаниям Parad; окончательную полноту и удобство ещё подтверждает её вычитка. Для следующих применений сохранены наблюдения о границах HTTP-фильтров, различии построенного/опубликованного/установленного приложения и совместимости API конкретной версии. Они находятся в существующих задачах; новые общие обязательные правила, генератор и отдельные кубики автоматически не созданы. V1 остаётся замороженной.

Вычитка 2026-10-09 выявила ещё один пропуск: константы Urls были прочитаны, но не воспроизведены как общий контракт контроллера и клиента. Причина — слишком широкая граница «всё HTTP остаётся в host». По решению Parad общие строки перенесены в Model; реализация HTTP остаётся у потребителей. Действующее правило — [[Documents/Architectures/WebAPI/DotNet/WebAPI.Monitor.Model.Sqlite.CodeFirst#Общие маршруты WebAPI и клиента]]. Для извлечения опыта этот случай показывает необходимость прослеживать использование найденного приёма по обе стороны границы проекта: удобство автора может находиться в связанном общем коде, а не в выбранном host.

Другое замечание той же вычитки — пропущенные поля ILogger в контроллерах. Общее правило сохранять заготовки уже существовало, но Машина применила его непоследовательно: действующее логирование фильтров/middleware перенесла, место для будущего логирования контроллеров пропустила. Это ошибка применения и проверки сохранённого правила. Конкретный проверяемый комплект «поле → зависимость конструктора → инициализация» и его границы закреплены в [[Documents/Architectures/WebAPI/DotNet/WebAPI.Monitor.Model.Sqlite.CodeFirst#Логгер как заготовка контроллера]]; комплект восстановлен в шести контроллерах Book4U.

# DomainObject - Entity - MappingEF - Repository

## Назначение

Кубик создаёт объекты из файла описания данных по выбранной последовательности этапов. Он предназначен для повторного применения Машиной и программистом на основе текущих проектов Model, SelectParam и ExportImport. Рабочая инструкция — [[Commands/Create Data Objects by Step]].

Это управляемый процесс через согласование модели в Excel. После проверки и возврата книги весь запрошенный комплект создаётся одним проходом без отдельных подтверждений каждого класса, объекта или этапа. Карточка описывает процесс; самостоятельный программный генератор или устанавливаемый навык пока не создаётся.

## Этапы и последовательности

`mapperEF` и `MapperEF` в запросе обозначают этап `MappingEF`; `Repository` обозначает интерфейс репозитория в Model и реализацию в `RepositoryEF`.

| № | Последовательность |
| --- | --- |
| 1 | DomainObject |
| 2 | Entity |
| 3 | MappingEF |
| 4 | Repository |
| 5 | DomainObject → Entity |
| 6 | Entity → DomainObject |
| 7 | DomainObject → Entity → MappingEF |
| 8 | Entity → DomainObject → MappingEF |
| 9 | DomainObject → Entity → MappingEF → Repository |
| 10 | Entity → DomainObject → MappingEF → Repository |
| 11 | MappingEF → Repository |

Состав работы определяется запросом Parad и фактическим состоянием проекта: названные части создаются или дополняются, существующие части используются без дублирования. 11 последовательностей кубика — примеры, а не закрытый список команд. После возвращения утверждённого Excel весь запрошенный комплект создаётся одним проходом: по умолчанию в Model и ExportImport, а при явно ограниченном запросе — только в названном проекте или составе. При недостающих зависимостях уточни существующие пути либо расширение состава до генерации. Правила: [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Гибкий состав работы и согласование модели]].

Полная цепочка по умолчанию относится к объектам утверждённой Excel-модели. При явно ограниченном запросе выполняются только названные этапы. Готовые HTTP request/response-типы вне папки `Domain` в эту цепочку не входят и добавляются только по прямому выбору Parad.

Если объектов несколько, после возврата утверждённого Excel они создаются все вместе в согласованном объёме. Для DomainObject комплект включает основной класс и его парную коллекцию; для Entity — класс, его конфигурацию и подключение к DbContext; для Repository — интерфейс и реализацию. Промежуточные остановки между объектами и частями комплекта не требуются.

Если для выбранного состава не хватает DomainObject, Entity, коллекции, маппера либо другой необходимой зависимости, до генерации спроси: «Указать существующие файлы или расширить состав?» При выборе существующих файлов запроси недостающие пути и проверь соответствие классов. При расширении покажи обновлённый состав и зафиксируй выбор Parad. После этого создай все объекты согласованного состава одним проходом.

## Источники данных и нормализация

Принимается файл в любом доступном для чтения формате: текст, Markdown, CSV, Excel, JSON, SQL DDL, C#, EF-конфигурация и другие форматы. Если файл технически недоступен или его формат нельзя прочитать имеющимися средствами, назови проблему и запроси доступное представление. Не обещай разобрать неподдерживаемый или зашифрованный файл без необходимых средств.

Один файл может описывать один или несколько объектов. Исходный файл не изменяется. Для каждого объекта подготовь:

- имя объекта, имена классов DomainObject и Entity, таблицы, проектов и namespaces;
- свойства и соответствующие столбцы, CLR-типы обеих сторон, типы БД, nullable;
- ключ, генерацию значения, длину, precision/scale, индексы; связи входной схемы фиксируются как сведения источника, но не создаются между независимыми целевыми таблицами;
- значения конструктора и DB defaults раздельно, комментарии и отдельные тестовые данные;
- атрибуты свойств DomainObject в опциональном столбце `Attributes`, включая исключения `[NoEntity]` по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]];
- явные преобразования для маппера и предоставленные сигнатуры репозитория;
- источник каждого значения: файл, существующий код, согласованное правило либо ещё не определено.

Не все сведения нужны для каждого этапа: для DomainObject не требуется заранее выбирать путь DbContext. Недостающие сведения спрашиваются к тому этапу, которому они нужны. Не выводи ограничения схемы только из примеров значений.

## Рабочий контекст и пути

До первого добавления определи источник данных, последовательность, выбранные объекты, имя сервиса, solution/проекты, технологический профиль и известные пути. Сначала используй запрос, фактические solution/проекты, `.csproj`, код, существующую рабочую задачу и явно связанные файлы. Каждый найденный путь покажи. Если необходимый путь к файлу или папке отсутствует либо неоднозначен, спроси Parad; не выбирай между несколькими проектами наугад. Отдельный паспорт или карточка применения не нужны; дополнительный контекст Машина может хранить в существующей задаче или своих рабочих заметках в удобном ей виде.

Для этапов нужны следующие места:

| Этап | Необходимые пути |
| --- | --- |
| DomainObject | проект Model, целевая папка `Domain/<Имя>`, существующий парный Entity при использовании его как источника |
| Entity | EF-проект, папка `<ИмяБД>/<Имя>`, существующий DomainObject при использовании его как источника, файл `<Имя>Configuration.cs` и существующий DbContext |
| MappingEF | оба исходных класса, целевая папка `MappingEF`, общий `StringLength.cs`, если он нужен |
| Repository | DomainObject и коллекция, Entity, DbContext, маппер, базовые классы репозитория/SelectParam; папки `Interface` в Model и `RepositoryEF` в EF-проекте |

Необходимые незаданные параметры создаваемого проекта спрашиваются до создания по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]: предлагаемый вариант первого образца или свободный ввод. При интеграции выбранные параметры проверяются на совместимость; при конфликте задаётся вопрос, версии автоматически не подстраиваются. Уже существующие классы, проекты и согласованные параметры сохраняются.

Имя сервиса задаёт префикс проектов, namespaces и имя нового solution. Контекст называется `<ИмяБД>Context` по отдельно выбранному логическому имени БД; имя и расширение файла не входят в имя контекста. Необходимые проекты и зависимости можно создавать или подключать в рамках согласованного применения; это не разрешает автоматически расширять выбранный список этапов создания объектов.

## Порядок выполнения

1. Определи по запросу, какие проекты и части нужно создать или дополнить.
2. Проверь необходимые входные классы, параметры и пути; недостающие или неоднозначные сведения уточни до генерации.
3. Подготовь Excel со всей нормализованной моделью, обязательными полями, defaults, предложениями и вопросами.
4. Дождись, пока Parad проверит, при необходимости исправит и вернёт книгу.
5. По возвращённому утверждённому Excel создай весь согласованный комплект одним проходом: по умолчанию в Model и ExportImport, а при ограниченном запросе — только в названном проекте или составе.
6. Проверь и собери результат, затем покажи созданные и изменённые файлы для вычитки. Отдельного разрешения перед каждым классом, объектом или этапом не спрашивай.

`ID`, `Code` и другие согласованные defaults включаются в Excel и после его возврата записываются вместе со всем комплектом. Существующие поля не удаляются, не переименовываются и не меняются автоматически; конфликт показывается в Excel или уточняется до генерации.

## Результат этапов

### DomainObject

Создаются `<Имя>.cs` и полная парная коллекция `<Имя>s.cs` в `Domain/<Имя>` проекта `<Service>.Model`. Namespace — `<Service>.Model`. Атрибуты из `Attributes` добавляются перед соответствующими свойствами по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. Первое свойство — обязательное `long ID`, в конструкторе `ID = 0`; обязательный `Code` используется для `Equals` и `GetHashCode`. Коллекция содержит `FromEnumerable`, `CurrentItem`, `CurrentChanged`, `TotalCount`.

Если тип обычного свойства не указан, предложи подходящий тип при разборе и согласуй его в Excel; `ID` всегда имеет тип `long`. Предметные поля CommandResult не навязываются другим объектам. Для различающихся типов DomainObject и Entity требуется явное согласованное преобразование.

### Entity

Создаётся `<Имя>.cs` в `<ИмяБД>/<Имя>` EF-проекта. Namespace — `<Service>.<DataStore>.<Approach>`. Первое свойство — обязательное `long ID`; в БД это первичный ключ. Схемные Data Annotations не используются. При генерации от DomainObject используется согласованное соответствие свойств; свойства с `[NoEntity]` не добавляются в Entity и конфигурацию по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. Другой этап DomainObject автоматически не запускается.

Этот этап, включая «только Entity», содержит класс, конфигурацию и подключение к DbContext с API выбранного семейства EF. Для EF Core используй IEntityTypeConfiguration<T> и существующий механизм регистрации конфигураций; для EF6 адаптируй конфигурацию к EntityTypeConfiguration<T> и DbModelBuilder. Явно назначь ID первичным ключом. Существующие объявления не дублируй; при отсутствии контекста уточни путь или создание инфраструктуры до генерации. После возвращения утверждённого Excel создай классы, конфигурации и изменения контекста всех объектов одним проходом. Остальные части этим запросом не запускаются.

### MappingEF

Используются существующие или созданные ранее в этой последовательности DomainObject и Entity. Создаётся `MappingEF/<Имя>Mapper.cs` с `ToDomainObject`, `ToSimpleDomainObject`, `ToEntity`, `ApplyChanges`. Для двух преобразований `null` остаётся `null`; согласованные сохраняемые свойства переносятся, а свойства DomainObject с `[NoEntity]` исключаются из всех методов маппера по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. ToSimpleDomainObject даёт сокращённое представление; до определения состава допустима заглушка, при известном составе предлагается реализация. `ApplyChanges` учитывает то же исключение `[NoEntity]`; ID существующей Entity не меняется; ToEntity копирует ID отдельно при создании нового объекта. Это обеспечивает обновление по Code без смены технического PK.

`StringLength.cs` с `CutLength` хранится один раз; метод вызывается только по явному правилу поля. Маппер сам по себе не создаёт отсутствующие модели без решения о расширении последовательности.

### Repository

Создаются или дополняются `Interface/I<Имя>Repository.cs` в Model и `RepositoryEF/<Имя>EFRepository.cs` в EF-проекте. Используются Entity, DomainObject, его парная коллекция, маппер и DbContext. Внешний результат — DomainObject/его коллекция.

Типовой набор: чтение всех записей, выборка с SelectParams, TotalCount после фильтрации до paging, чтение по Code, вставка одного объекта/массива, обновление по ID или Code, удаление всех совпадений по Code, DeleteAll. Единая политика совпадений и сохранения технического ID находится в разделе «Предметные правила и развитие шаблона». Конфликт сигнатур удаления решается именем DeleteByCode. Дополнительные методы с достаточным описанием поведения включаются в общий проход генерации; если поведение неизвестно, вопрос уточняется до генерации либо остаётся явно обозначенная заглушка. Общий PaginatedList создаётся один раз согласно образцу, если отсутствует и нужен предусмотренный шаблоном файл.

Полные правила кода маппера и репозитория берутся из [[Commands/Add Code First Fields by Step]] только для выбранных частей работы. Состав определяется текущим запросом и возвращённым Excel. Запрос одной части не запускает не запрошенный комплект.

## Проверка и состояние

После добавления проверяются файлы, namespaces, порядок ID, соответствие показанному коду и зависимости. Сборка выполняется, когда все требуемые для проверяемого проекта зависимости доступны. Недостающая зависимость или ошибка фиксируется явно; завершение этапа генерации не выдаётся за успешную сборку или проверку БД.

Для маппера проверяется согласованное отображение в обоих направлениях, включая явно описанные бизнес-различия; все методы маппера исключают свойства DomainObject с `[NoEntity]` по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]. Для репозитория проверяются интерфейс, реализованные операции, согласованная политика Code и явный список заглушек. Реальная работа с провайдером подтверждается интеграционной проверкой; migrations и изменения существующей БД выполняются по отдельному запросу.

Фактическое состояние определяется прежде всего по solution, названиям проектов, `.csproj` и коду. Для продолжения Машина при необходимости хранит путь источника, утверждённый Excel, согласованный состав и нерешённые вопросы в существующей рабочей задаче или своих заметках без обязательного формата. Уже созданные файлы повторно не создаются.

## Внутренняя организация кода

При внутренней организации кода следуй согласованному ориентиру: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Внутренняя организация кода]]. Это ориентир, а не жёсткий запрет на повторение или выделение методов.

## Образец как опора при создании модели

При создании модели сохраняй стартовые CommandResult/CommandResults, необходимые перечисления и все пять интерфейсов как опору Parad, адаптируя их к правилам проекта. Неиспользование не является основанием убрать их на этом этапе. Удаление ненужного выполняется позднее, на этапе бизнес-правил, по отдельному запросу Parad. Полное правило: [[Tasks/Artifacts/TASK-20260909-003/project-structure-discussion-v1#Образец как опора при создании модели]].

## Гибкий состав работы и согласование модели

Перечисленные выше 11 последовательностей показывают возможные ситуации и не являются закрытым списком команд. Машина понимает запрос и состояние проекта и определяет нужные части шаблона. Прямо названный Parad состав имеет приоритет над полной цепочкой. Слова «по кубику» не обязательны.

По умолчанию после возврата утверждённого Excel все описанные объекты создаются одним проходом в Model и ExportImport: DomainObject с парной коллекцией, Entity с конфигурацией и подключением к DbContext, Mapper и Repository с интерфейсом. Можно запросить создание только в одном проекте или только прямо названных частей; существующие объекты используются либо дополняются. Необходимые отсутствующие зависимости уточняются до генерации и не запускают молча дополнительные части.

Отдельное правило действует для запроса создать новый `<Service>.Model.<DataStore>.CodeFirst.ExportImport`: это запрос на полный стартовый solution `<Service>.sln` из ExportImport, `<Service>.Model` и `Service.Model.EF.SelectParam` с готовой цепочкой `CommandResult` в Model и ExportImport. Она создаётся целиком без поэтапного согласования состава уже готового образца. Гибкий выбор этапов применяется к последующим объектам и дополнениям, а не сокращает стартовый комплект.

В рабочем репозитории приложения `Service.Model.EF.SelectParam` является скопированным локальным проектом с исходным кодом и входит в `<Service>.sln`. `ProjectReference` на его локальный `.csproj` добавляется каждому проекту, использующему типы `SelectParam`; проектам без такого использования ссылка не добавляется. Внешний `ProjectReference` на checkout `Sources/Architectures` и пакет вместо проекта не используются.

После разбора входного описания Машина возвращает книгу `.xlsx`, совместимую с Excel 2013: лист соответствует объекту, строка — свойству. В книге показываются исходные и предлагаемые имена и типы, исходное значение по умолчанию, предлагаемые defaults отдельно для C# и БД, исходная и предлагаемая длина строки в БД, комментарии и вопросы. Неуказанные значения отличаются от `null`, пустой строки, нуля и отсутствия ограничения длины. Если тип не задан, Машина предлагает его по смыслу для согласования, а не молча фиксирует `string`. Обязательные добавленные поля помечаются явно.

Parad проверяет, при необходимости исправляет и возвращает книгу. Возвращённая утверждённая книга разрешает создать весь указанный в запросе комплект без новых промежуточных согласований. Неясности возвращённой книги уточняются до генерации. После создания итоговые файлы и классы показываются целиком для вычитки.

При дополнении существующих объектов Машина определяет согласованный объём изменений и использует фактические файлы. Синхронизация нового поля не означает повторного создания пары или автоматического создания всех слоёв. Если отсутствует требуемый класс, Машина уточняет путь или необходимость его создания. Правила реализации выбранных дополнений находятся в [[Commands/Add Code First Fields by Step]].

### Attributes и NoEntity

В каждом листе Excel-описания предусмотрен опциональный столбец `Attributes` для атрибутов свойства DomainObject. При подготовке новой книги добавляй этот столбец; пустая ячейка или отсутствие столбца во входной книге означает, что дополнительные атрибуты не заданы. Заполненные значения входят в утверждаемую модель Excel и после возврата книги добавляются перед соответствующим свойством в файле DomainObject. Сохраняй аргументы атрибутов; несколько атрибутов можно записать отдельными строками ячейки в синтаксисе C#, например `[NoEntity]` и `[Display(Name = "Подпись")]`. Одиночное имя `NoEntity` без скобок также означает `[NoEntity]`. Если тип атрибута, его аргументы или необходимые зависимости не определены, уточни это до генерации зависящего кода; не добавляй пакеты молча.

`[NoEntity]` — свойство остаётся в DomainObject с этим атрибутом, но не добавляется в Entity, EF-конфигурацию столбца и код маппера. Исключение действует для всех четырёх методов: `ToDomainObject`, `ToSimpleDomainObject`, `ToEntity` и `ApplyChanges`. При чтении из Entity значение такого свойства не присваивается маппером; сохраняется инициализация или вычисление самого DomainObject. Остальные атрибуты переносятся на свойство DomainObject и сами по себе не означают его исключения из Entity. Наличие `NoEntity` определяется по самому атрибуту свойства, а не по тексту аргумента другого атрибута.

Класс `NoEntityAttribute` находится в корне проекта Model, namespace `<Service>.Model`, наследует `System.Attribute` и предназначен для свойств. Он включается в стартовый Model вместе с остальным готовым составом; это служебный тип вне `Domain`, Entity для него не создаётся. Атрибут служит меткой для этого workflow; он не заменяет EF-конфигурацию и сам по себе не переписывает существующий маппер.

На старте Entity соответствует сохраняемым свойствам DomainObject — за исключением помеченных `[NoEntity]`. В Excel должны быть видны эти исключения и объём создаваемых частей. Если `[NoEntity]` конфликтует с обязательным `ID`/`Code`, существующим сохраняемым полем или необходимой операцией репозитория, покажи конфликт до генерации и уточни решение; не удаляй существующие поля, столбцы и маппинг автоматически. Добавление атрибута не разрешает migration или изменение БД.

## Code First и выбор семейства EF

Текущий процесс — Code First. Источником может быть описание, существующая БД (её схема или доступные метаданные) либо Entity-модель БД. Сначала из источника создаётся Excel в согласованном формате; после проверки и утверждения Parad применяется тот же гибкий процесс генерации и дополнения. Excel показывает исходные сведения и предложения отдельно. Наличие БД на входе не запускает отдельный Database First workflow, автоматическую перегенерацию файлов или изменение исходной БД.

EF6 или EF Core, точные версии, провайдер и совместимость определяются для конкретного проекта. Уже согласованный или существующий профиль учитывается первым; незаданные параметры создаваемого проекта спрашиваются по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]], где значения образца служат предлагаемыми вариантами. До создания solution/проектов СУБД выбирается ответом на вопрос со списком вариантов и свободным вводом; затем отдельным вопросом выбирается провайдер из списка совместимых вариантов. Оба ответа ожидаются до создания. Нет обязательного перехода с EF6 на EF Core. Предложенные Машиной изменения библиотек и версий предварительно согласуются с Parad.

Общие роли DomainObject, Entity, MappingEF и Repository сохраняются; реализация контекста, конфигураций, запросов и migrations адаптируется к выбранному семейству и версии. Не переноси API EF Core в EF6 механически. Проверяй совместимость целого solution, включая netstandard2.0 и зависимости SelectParam, сборку и затронутые сценарии с реальным провайдером. Возможность адаптации не означает, что профиль уже проверен. Создание и применение migrations требуют отдельного запроса.

Примеры различий: EF Core использует IEntityTypeConfiguration<T> и поддерживаемый выбранной версией механизм регистрации; EF6 — EntityTypeConfiguration<T> и DbModelBuilder. Источники Microsoft: [настройка модели EF Core](https://learn.microsoft.com/en-us/ef/core/modeling/), [Code First Fluent API EF6](https://learn.microsoft.com/en-us/ef/ef6/modeling/code-first/fluent/types-and-properties).

## Предметные правила и развитие шаблона

Сводка согласованных решений Parad от 2026-10-01. Входное описание объектов и свойств является основой модели. Машина предлагает реализацию с учётом паттернов Parad и опыта .NET; конфликты имён, типов и предметного смысла согласуются до генерации. Стандартные шаблоны Visual Studio/.NET могут использоваться как техническая основа, если помогают задаче и соответствуют согласованному профилю; их применение не должно добавлять ненужную функциональность.

В этой архитектуре таблицы независимы: реляционные связи и внешние ключи между ними не создаются. Найденные во входной БД связи показываются как сведения источника и не переносятся автоматически в целевую модель. Code отслеживается в коде и запросах, допускает повторы и не является PK БД; PK — ID long. Эти правила относятся к данной архитектуре и не переносятся автоматически на другие архитектуры.

По решению Parad от 2026-10-02 основной прикладной ключ — `Code`, а технический PK — `ID`. Ключ поиска и новые данные обновления разделяются. Действует единая политика:

- Чтение по Code выбирает одну запись с точным совпадением Code; среди нескольких совпадений — с минимальным ID. При отсутствии возвращается null.
- `DeleteByCode(code)` удаляет **все** записи с указанным Code. При отсутствии совпадений ничего не меняется.
- `UpdateById(id, domainObject)` ищет запись только по отдельному аргументу id. Все данные объекта, включая Code, переносятся без проверки совпадения старого и нового Code. ID найденной записи в БД сохраняется; ID входного объекта не меняет выбранную запись.
- `UpdateByCode(code, domainObject)` ищет по отдельному аргументу code. При нескольких совпадениях обновляет одну запись с минимальным ID, переносит её данные, включая новый Code, и сохраняет ID найденной записи в БД. Это не массовое обновление.
- `Update(domainObject)` служит сокращением для UpdateByCode(domainObject.Code, domainObject). Для изменения Code с независимым ключом поиска используются явные UpdateById или UpdateByCode. Запасного поиска по CommandUID, CommandResultCode или ID нет. Если запись не найдена, оба способа обновления ничего не меняют и не выполняют вставку.
- `ApplyChanges` переносит согласованные сохраняемые свойства, кроме технического ID; исключение NoEntity остаётся в силе. `ToEntity` может отдельно копировать ID при создании нового объекта. Insert сбрасывает ID Entity в 0 перед добавлением, чтобы БД создала новую запись; повторный Code разрешён. Уникальный индекс Code автоматически не создаётся.
- Списочные запросы и DeleteAll сохраняют своё назначение. Существующие явно именованные методы по другим полям и чтение/удаление по long ID сохраняются для совместимости, но не входят в основной сценарий по Code и не генерируются для новых объектов без отдельного запроса. По текущему решению Delete(string code) переводится на Code и становится сокращением для DeleteByCode(code); CommandResultCode остаётся отдельным свойством данных, а не ключом этой операции.

Политика заменяет прежние отдельные согласования дубликатов для каждого проекта и копирование ID в ApplyChanges. Различие удаления и обновления уточнено Parad: удаляются все совпадения Code, обновление адресует запись по выбранному ключу. Выбор минимального ID для чтения/обновления при повторном Code — решение Машины в пределах предоставленного выбора. Особое поведение конкретной предметной задачи вводится только по её явным требованиям.

На этапе создания стандартного шаблона Entity соответствует свойствам DomainObject без `[NoEntity]` по [[Documents/Architectures/Cubes/DotNet/DomainObject - Entity - MappingEF - Repository#Attributes и NoEntity]]; различающиеся типы имеют явный маппинг. Позднее бизнес-правила могут потребовать различий, например вычисляемых свойств DomainObject или технических полей Entity. Такие различия согласуются, явно описываются и учитываются в маппинге; не нужно автоматически приводить развившиеся модели к полному совпадению. Существующие поля не меняются молча.

ToSimpleDomainObject сохраняется как часть шаблона: его смысл — сокращённое представление, например Code, Name, Description. Конкретный набор определяется проектом, а не этим примером. Пока состав/поведение не определены, допустима явно указанная заглушка NotImplementedException; при достаточном описании предлагается реализация. Для LINQ учитывается выполнение в памяти или через провайдер: пригодность обычного метода для LINQ сама по себе не гарантирует перевод в SQL или выбор только нужных столбцов.

Дополнительный метод репозитория, достаточно описанный в файле или интерфейсе с понятным контрактом, реализуется в общем проходе генерации. Если определена только сигнатура, а поведение неизвестно, остаётся явно обозначенная заглушка и вопрос о недостающем поведении. Наличие заглушки не означает готовность операции. Начальный набор вспомогательных файлов, включая PaginatedList, сохраняется как опора образца; неиспользуемое удаляется позднее по запросу Parad.

Читаемость и удобство отладки запросов имеют приоритет над усложнением ради предполагаемой производительности. В одном проекте могут применяться LINQ, динамические запросы SelectParam, ADO.NET, Bulk и хранимые процедуры подходящей СУБД. Это варианты для последующего архитектурного обсуждения, а не обязательный набор зависимостей и не жёсткая привязка технологии к размеру запроса. Для тяжёлой операции выбор обсуждается по реальной задаче и измерениям.

## Показ кода и отметки вычитки

После генерации из описания или интерфейса показывай итоговый файл или класс целиком, включая свойства, атрибуты и методы. Для изменений уже вычитанного кода сохраняй контекст класса и выделяй изменённые участки; показ всего класса не означает обязательную повторную вычитку всех методов.

Рабочий формат отметки — комментарий перед классом и перед новыми/изменёнными методами; аналогично отмечаются свойства и изменения атрибутов. Отдельный C#-атрибут или пакет для этого не требуется. Даты — YYYY-MM-DD, фактические даты соответствующих действий по Asia/Tomsk. Примеры ниже показывают формат, а не фактическую вычитку:

```csharp
// TODO: CodeReview | Generated=2026-10-01 | Status=Unread | Scope=Full
// TODO: CodeReview | Generated=2026-10-02 | Status=Unread | Scope=Changes
// CodeReview | Generated=2026-10-02 | Status=Read | Scope=Changes | Reviewed=2026-10-03
```

- Новый код получает Unread и Scope=Full. Ранее невычитанный код не становится Scope=Changes только потому, что очередная правка мала; отсутствие отметки не доказывает вычитку.
- При изменении ранее вычитанного участка он получает Unread и Scope=Changes; Generated обозначает дату текущей генерации/содержательного изменения, старая дата Reviewed больше не относится к этой версии. Неизменённые методы сохраняют отметки и даты.
- Перед классом находится сводная отметка. Она остаётся Unread, пока есть невычитанные изменения класса или его членов. Scope=Changes у класса допустим, когда класс ранее был вычитан; новый член при этом сам имеет Scope=Full.
- Read ставит Parad вручную либо Машина по явному сообщению Parad о вычитке конкретного метода/класса. Подтверждение записи, сборка и тесты сами по себе не означают вычитку. Явное подтверждение вычитки всего показанного класса охватывает его показанный состав.
- Возле небольшой правки оставляй понятную отметку REVIEW-CHANGE с датой и причиной; для нескольких строк можно ограничить начало/конец участка. Удаления показывай сравнением с предыдущей версией. Не накапливай путаные отметки поверх уже вычитанных изменений; актуальный участок должен быть различим.
- Если маленькое изменение влияет на поведение других частей метода, объясни, какую связанную часть проверить и почему. Не назначай полную повторную вычитку автоматически.
- В Visual Studio комментарии TODO видны в Task List; по CodeReview, Status=Unread и Generated=YYYY-MM-DD можно искать в решении. После вычитки TODO убирается, отметка Read остаётся в коде. Формат уточняется на первом реальном применении по удобству Parad, без установки расширений и автоматического изменения настроек IDE.

## Версии и совместимость при новом применении

Точные версии первого эталона сохраняются как предлагаемые варианты начальных вопросов по [[Wiki/HowToDo/Create Project Domain Model by Step#Параметры по умолчанию]]. netstandard2.0 для Model/SelectParam не требуется менять только из-за обновления потребителя; совместимость проверяется вместе с зависимостями. Проект на netcoreapp3.1 может быть кандидатом на переход в конкретном проекте по согласованию с Parad; могут потребоваться совместимые изменения EF и провайдера. Новизна версии сама по себе не основание для перехода. Эталон и остальные проекты автоматически не обновляются. Проверяется целый solution и затронутые операции, а непроверенные сценарии указываются явно.

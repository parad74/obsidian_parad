# Service - DIUnity

## Краткое описание

Кубик добавляет проект `Common.Service` с одной или несколькими парами «интерфейс — реализация». Сервис может хранить текстовое состояние и предоставлять минимальные операции `Save` и `Clear`; конкретное назначение и контракт уточняются перед созданием. Потребитель получает нужный интерфейс сервиса через DI-контейнер Unity.

Одна карточка поддерживает два режима:

1. интеграция `Common.Service` в существующий solution;
2. создание отдельного демонстрационного solution с тем же набором сервисов.

## Имена и количество сервисов

Перед применением кубика обязательно определить количество сервисов и спросить имя каждого сервиса, если пользователь его ещё не указал.

- Для согласованного базового имени `<Name>` создаётся класс `<Name>Service` и интерфейс `I<Name>Service`, например `TextService` и `ITextService`.
- Базовое имя запрашивается без префикса `I` и без суффикса `Service`. Если пользователь сразу указал полное имя класса или интерфейса, суффикс повторно не добавляется.
- Если предметное имя ещё не выбрано, используются нейтральные временные имена `Service1` и `IService1`, затем `Service2` и `IService2` и так далее.
- `MainService` и `IMainService` не являются именами по умолчанию.
- Один проект `Common.Service` может содержать несколько независимых сервисов. Для каждого создаются отдельные файлы интерфейса и реализации и отдельная регистрация в Unity.
- Codex не придумывает предметные имена сервисов. Временные имена разрешены именно для этапа, на котором решение о наименовании ещё не принято.

## Источник идеи

В проекте `Sources/old/PreTestWCF/` находятся:

- `Main/Interface/IMainService.cs` с методом `Test(string name)`;
- `Main/Service/MainSerivce.cs`, реализующий `IMainService`;
- регистрация `IMainService` → `MainSerivce` в `Main/Program.cs`.

Исходный класс называется `MainSerivce`. Это legacy-опечатка и историческое имя конкретного старого сервиса, а не шаблон именования нового кода. Имя `MainSerivce` сохраняется только тогда, когда пользователь явно требует совместимость с существующим кодом.

Старый метод `Test` в кубик не переносится: он лишь возвращает переданный аргумент и не относится к новому сценарию `Save`/`Clear`.

## Состав проекта Common.Service

```text
Common.Service/
├─ Interface/
│  ├─ I<Name1>Service.cs
│  └─ I<Name2>Service.cs
├─ Service/
│  ├─ <Name1>Service.cs
│  └─ <Name2>Service.cs
├─ Properties/
│  └─ AssemblyInfo.cs
└─ Common.Service.csproj
```

Если предметные имена не выбраны, первая пара файлов называется `IService1.cs`/`Service1.cs`, вторая — `IService2.cs`/`Service2.cs` и так далее.

- `Common.Service` — Class Library для .NET Framework 4.6.1.
- Каждый `I<Name>Service` или временный `IServiceN` является публичным контрактом и находится в `Interface/`.
- Каждая реализация `<Name>Service` или временная `ServiceN` находится в `Service/`.
- Проект сервиса не зависит от Form, View, Presenter или WinForms.
- Проект сервиса не зависит от Unity: регистрация выполняется composition root приложения.
- Логирование пользовательских действий остаётся в Presenter или вызывающем приложении и не добавляется в этот минимальный сервис.

## Общие правила .NET Framework для этого кубика

Карточка применяется самостоятельно и явно повторяет обязательные правила организации кода:

1. Каждый файл с объявлением `public interface` находится в папке `Interface/` соответствующего проекта.
2. Реализации `IView` и производных интерфейсов находятся в папке `View/` соответствующего проекта.
3. Реализации `IPresenter` и производных интерфейсов находятся в папке `Presenter/` соответствующего проекта.
4. Каждая реализация сервиса находится в папке `Service/` проекта `Common.Service`, а её публичный интерфейс — в `Interface/`.
5. В пользовательском коде закрытые поля имеют имя `_camelCase`.
6. Обращение к полю или свойству текущего экземпляра записывается с `this.`, например `this._service` и `this._savedText`.
7. Обращение из производного класса к доступному члену базового класса записывается с `base.`, например `base.RequireView()`.
8. Параметры методов и локальные переменные не получают префикс `_`.
9. Правила `_camelCase`, `this.` и `base.` не навязываются `*.Designer.cs`, другому сгенерированному коду, сторонним библиотекам и неизменяемым старым проектам.
10. Если отдельный solution содержит WinForms-host, для него также применяются System DPI Aware manifest и `AutoScaleMode.Dpi` с базовым значением 96 DPI.

## Правило Lib для отдельного solution

В корне отдельного solution обязательно создаётся папка `Lib/` рядом с проектами:

```text
<Solution Root>/
├─ Lib/
│  ├─ Microsoft.Practices.Unity.dll
│  └─ Microsoft.Practices.ServiceLocation.dll
├─ Common.Service/
├─ Main/
└─ <Solution Name>.sln
```

- В `Lib/` помещаются все и только те сторонние DLL, которые фактически используются новым solution.
- Unity и его транзитивная зависимость ServiceLocation обязательны для автономного примера `Service - DIUnity`.
- Если выбранный host использует `IModule`, в `Lib/` дополнительно помещаются фактически требуемые DLL Composite.
- Проекты подключают DLL относительными путями, например `..\Lib\Microsoft.Practices.Unity.dll`.
- Для ссылок на DLL включается Copy Local, чтобы зависимости попадали рядом с запускаемым EXE.
- Папка называется именно `Lib/` с таким регистром и находится в корне solution, а не внутри отдельного проекта.

## Минимальный контракт

```csharp
public interface IService1
{
    string SavedText { get; }

    void Save(string text);

    void Clear();
}
```

`SavedText` нужен, чтобы потребитель и проверка могли получить фактически сохранённое значение.

## Поведение временного Service1

```csharp
public sealed class Service1 : IService1
{
    private string _savedText = string.Empty;

    public string SavedText
    {
        get { return this._savedText; }
    }

    public void Save(string text)
    {
        this._savedText = text ?? string.Empty;
    }

    public void Clear()
    {
        this._savedText = string.Empty;
    }
}
```

Правила поведения:

- `Save` заменяет предыдущее значение новым;
- `null` сохраняется как `string.Empty`;
- `Clear` устанавливает `SavedText` в `string.Empty`;
- состояние хранится только в памяти и не переживает перезапуск приложения;
- в пользовательском коде применяются правила `.NET Framework`: `_camelCase`, `this._field`, `base.Member` для унаследованных членов.

## Режим 1 — интеграция в существующий solution

Codex должен:

1. Прочитать целевую архитектурную карточку и существующий solution.
2. Убедиться, что целевой framework совместим с .NET Framework 4.6.1.
3. Создать проект `Common.Service` по структуре этой карточки и добавить его в существующий solution.
4. Добавить ссылку на `Common.Service` только в проекты-потребители, обычно в `Main`.
5. Зарегистрировать каждый сервис в существующем Unity composition root. Для временного имени первого сервиса:

```csharp
container.RegisterType<IService1, Service1>(
    new ContainerControlledLifetimeManager());
```

6. Передать нужные интерфейсы сервисов в Presenter или другие потребители через конструкторы.
7. Если Presenter сам хранит обслуживаемое сервисом состояние, удалить это дублирование и делегировать операции сервису.
8. Не создавать новый solution и не копировать существующие проекты.
9. Не менять View и визуальную разметку, если это не требуется для подключения сервиса.

### Интеграция с WinForms View–Presenter

При применении к текущему эталону ожидается:

- `MainPresenter` получает интерфейс выбранного сервиса через конструктор;
- поле `_savedText` удаляется из `MainPresenter`;
- `Save` вызывает `this._service.Save(view.GetInputText())`;
- `Clear` вызывает `this._service.Clear()` и очищает View;
- статус использует `this._service.SavedText`;
- существующее логирование через `ILog` сохраняется в Presenter;
- Unity отдельно регистрирует каждую пару интерфейса и реализации через `ContainerControlledLifetimeManager`.

## Режим 2 — отдельный solution

Codex должен:

1. Спросить название нового solution, если пользователь его не указал.
2. Создать отдельный solution, не изменяя существующие проекты.
3. Всегда создать проект `Common.Service` по этой карточке с согласованным количеством сервисов.
4. Для запуска и проверки по умолчанию создать минимальный Console-проект `Main` на .NET Framework 4.6.1.
5. Создать в корне solution папку `Lib/`, положить туда все используемые сторонние DLL и подключить их из проектов относительными `HintPath` с Copy Local.
6. В `Main` зарегистрировать через Unity каждую пару интерфейса и реализации и получить каждый сервис из контейнера.
7. Для минимального контракта последовательно проверить `Save`, чтение `SavedText`, `Clear` и пустое итоговое значение каждого сервиса.

Если пользователь явно попросит WinForms-host вместо Console, интерфейс host определяется отдельно и не считается частью кубика сервиса.

## Вопросы перед применением

Задавай только вопросы, ответы на которые ещё не известны:

1. Режим: интеграция в существующий solution или отдельный solution?
2. Сколько сервисов должно находиться в `Common.Service`?
3. Какое базовое имя имеет каждый сервис? Если решение о названиях ещё не принято, подтвердить временные пары `Service1`/`IService1`, `Service2`/`IService2` и так далее.
4. Каково назначение и какие операции нужны каждому сервису? Если других требований нет, использовать минимальный контракт `SavedText`, `Save` и `Clear`.
5. Для интеграции: какой точный путь к `.sln` и какой проект является composition root?
6. Для отдельного решения: как оно называется?
7. Нужен только собираемый сервис или запускаемый демонстрационный host?
8. Если нужен host, оставить стандартный Console или создать явно запрошенный WinForms-host?
9. Требуется ли совместимость с конкретным legacy-именем, включая `MainSerivce`? Без явного требования legacy-имена не использовать.

## Проверка результата

Для обоих режимов обязательно проверить:

- `Common.Service` нацелен на .NET Framework 4.6.1;
- количество созданных сервисов совпадает с согласованным;
- интерфейс каждого сервиса расположен в `Interface/`, реализация — в `Service/`;
- Unity разрешает каждую согласованную пару интерфейса и реализации;
- в автономном режиме все используемые сторонние DLL находятся в корневой `Lib/`, ссылки используют относительный `HintPath`, а необходимые DLL копируются рядом с EXE;
- два последовательных `Save` заменяют значение;
- `Save(null)` даёт `string.Empty`;
- `Clear` даёт `string.Empty`;
- `Debug` и `Release` собираются без ошибок;
- исходный `Sources/old/PreTestWCF/` не изменён.

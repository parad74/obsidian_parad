# Documents — инструкции для заметок и архитектур

## Область действия

Этот файл дополняет корневой `AGENTS.md` для работы внутри `Documents/`. Перед практическим изменением документа также прочитай `Tasks/AGENTS.md` и сопровождай результат карточкой задачи.

## Документы Obsidian

- `Documents/` хранит документы и обычные заметки vault.
- `Documents/Profile/Parad.md` является каноническим профилем личной преемственности и изменяется только по явному согласованию с Parad.
- Сохраняй обычный Markdown, совместимый с Obsidian, существующие wikilink-ссылки и frontmatter.
- Не изменяй ТЗ, спецификации и другие исходные документы только ради извлечения задач.
- Не создавай новые шаблоны, свойства, подпапки или служебные документы без явной необходимости.
- Локальные документы, изображения и другие артефакты конкретной задачи размещай по правилам `Tasks/AGENTS.md`, а не произвольно внутри `Documents/`.

## Каталог архитектур

- `Documents/Architectures/` хранит согласованные описания архитектурных решений; карточки являются источником истины для Codex.
- `Documents/Architectures/Catalog.md` служит точкой входа по словам запроса; перед составлением решения прочитай его и затем полные карточки выбранных проектов и кубиков. Добавляй в каталог новые карточки и проверенные сочетания, сохраняя точные правила в подробных карточках.
- Группируй решения сначала по типу приложения, затем по семейству runtime, например `Documents/Architectures/WinForms/DotNetFramework/` и `Documents/Architectures/WinForms/DotNet/`.
- Повторно используемые архитектурные кубики храни в `Documents/Architectures/Cubes/<Runtime Family>/` под точным названием, выбранным Parad.
- Не используй категории «старое» и «новое»: указывай конкретное семейство runtime и технологические ограничения.
- Одна Markdown-карточка описывает одно целостное архитектурное решение под точным названием, выбранным Parad.
- Не дублируй в карточке весь код. Ссылайся на исходный проект в `Sources/old/` и на эталонную реализацию в `Sources/Architectures/`, если она создана.
- Перед созданием проекта по архитектуре найди карточку по названию, прочитай её полностью и задай только отсутствующие обязательные вопросы из раздела `Вопросы перед созданием`.
- Не смешивай правила разных архитектур без явного решения Parad.
- Если кубик поддерживает интеграцию и автономное создание, сначала определи режим. В режиме интеграции изменяй указанный существующий solution и не создавай новый; в автономном режиме создавай отдельный solution и не изменяй существующие проекты.
- Сначала согласуй карточку, затем создавай и проверяй эталонную реализацию. Превращай её в автоматизированный шаблон только после успешной проверки и подтверждения повторного использования.
- Не дроби архитектуру на карточки-компоненты заранее. Выноси повторяемый компонент отдельно, когда он используется в нескольких решениях или получает независимые варианты.

## Связь с исходным кодом

Если изменение архитектурной карточки требует исследования или изменения кода, полностью прочитай `Sources/AGENTS.md` до работы с `Sources/`. Правила размещения интерфейсов, View, Presenter и общие требования читаемости находятся там; конкретные технологические требования остаются в соответствующей архитектурной карточке.
